# 2463 — http://127.0.0.1:3080/ 页面加载失败，Failed to load plugins web boot: 1 entry did not activate dsh-script-library: pending (waiting for service: remote.scriptLibrary)

## Verdict

**Not a bug — working as designed, plus a real documentation/discoverability gap.** [CONFIRMED]

The web shell is fail-loud by construction: one browser loader entry that never reaches ACTIVE keeps the whole page on the boot screen. The OP's own plugin declares `inject` on a service (`remote.scriptLibrary`) that nothing in the composition provides, so its fiber sits PENDING forever (cordis inject-waiting has no timeout) and the boot sweep reports it.

Two separate answers are needed and both exist:
- (A) Recovery is user-side and fully supported today: disable or remove the plugin's row from the profile patch layer and restart. [CONFIRMED]
- (B) `remote.<namespace>` services are **not** something a client plugin can conjure by declaring `inject`. They only exist after a *generated* Typert Remote contribution is mounted through `ctx.remote.$mount()`, which requires a Host-side `@Remote`-decorated service plus generated `./typert` + `./remote` artifacts. [CONFIRMED]

Honest caveat the OP must be told: for an **out-of-tree** plugin installed into `~/.dsh/profiles/web`, the shipped Client assembly's capability set is a fixed build-time list, so the "just add it to api-remotes" route is in-repo only; the out-of-tree route (self-mounting your own generated contribution) is mechanically available but has no in-repo precedent. [PLAUSIBLE, see Open questions]

## Research findings

### 1. The error string is the browser shell's boot sweep, and it is fail-loud by design

- `packages/client/web/src/boot.tsx:216-237` — `assertEntriesActive()` walks every loader entry after the tree quiesces; a PENDING fiber produces `` `${name}: pending (waiting for service${...}: ${missing.join(', ')})` `` (line 229) and the aggregate throw is `` `web boot: ${n} entr(y|ies) did not activate\n...` `` (line 235). Exact match for the reported text. [CONFIRMED]
- The JSDoc at `packages/client/web/src/boot.tsx:210-215` states the intent verbatim: *"a fiber not ACTIVE is FAILED (apply threw) or PENDING (a required service never arrived — cordis inject waiting has no timeout, so this sweep is the fail-loud compensation)"*. [CONFIRMED]
- `packages/client/web/src/boot.tsx:138-142` — a boot-chain failure resolves rather than rejects, and the message is pushed into the `error` signal so the loading page stays up.
- `packages/client/web/src/AppRoot.tsx:29-60` — renders `Failed to load plugins` plus each failed entry and the sweep message; the real UI is only rendered when `settled` is true (line 34). No partial UI. [CONFIRMED]
- `packages/client/web/README.md:25` (under `## Known Limitations and Deferred Work`) — *"**One-shot rendering by design** — the UI waits for the boot settle; a single entry failure keeps the loading page with a loud per-entry report, no partial availability (progressive rendering returns with its own project)."* This is the repo's own acknowledgement that one stuck entry blocks the page, and that changing it is a deferred project. [CONFIRMED]
- Repo rule alignment: `CLAUDE.md` → `## Conventions` → *"**Misconfiguration fails loud** at load when self-contained, otherwise at the earliest resolvable point; never silently skip a missing referent."* The behavior the OP hit is that rule applied to the browser plugin tree. [CONFIRMED]
- Host-side symmetry (same policy, different surface): `packages/boot/app-boot/src/index.ts:692-725` `assertEntriesActivated()` produces the identical wording for the Node process (`did not activate`, `pending (waiting for service...)`) — so the same class of mistake also kills `dsh --profile headless`. [CONFIRMED]

### 2. Where the failing entry comes from (why "the page force-loads this plugin")

- `packages/client/modules/src/index.ts:1-21` — the Node half scans the **host** Loader's entries for packages declaring `dsh.client` in package.json and composes `window.__DSH_BOOT__`. [CONFIRMED]
- `packages/client/modules/src/index.ts:386-388` — a package joins the graph only if a live loader entry has that name, has a fiber, **and `!entry.disabled`**. This is what makes `disabled: true` an effective removal from the browser roster. [CONFIRMED]
- `docs/subsystems/client-modules.md:49` — *"A package joins the table by declaring `dsh.client` (`platform: 'web'`, optional `inject` edges, optional `immediately`) in its package.json and exporting its built bundle at `exports["./client"]`."* [CONFIRMED]
- `packages/client/web/src/boot.tsx:189-204` — the shell creates one loader entry per graph row (`loader.create({ name })`); the entry name is the package name, and the fiber's `inject` comes from the plugin bundle's own `export const inject`. [CONFIRMED]
- `packages/client/modules/src/client/manifest.ts:47-60` — the wire row's `inject` field is explicitly *"informational graph metadata (the authoritative edges live in each package's `dsh.client` declaration and reach fibers through entry creation)"*. So editing `dsh.client.inject` does not fix a service-level `inject`. [CONFIRMED]

### 3. What `remote.*` actually is, and who registers it

- `packages/api/gateway/src/client/index.ts:509-511` — `remoteServiceKey(namespace)` returns the literal string `` `remote.${namespace}` ``. That is the entire origin of the `remote.scriptLibrary` service name. [CONFIRMED]
- `packages/api/gateway/src/client/index.ts:294-318` — `private async namespace(name)` lazily mounts a child plugin whose `apply` constructs a `RemoteNamespaceService` registered under `remote.<name>` (`super(ctx, remoteServiceKey(name))`, line 441). It is called **only** from `install()` (lines 263, 281), which is reached only from `mountContribution()` (line 178). [CONFIRMED]
- `packages/api/gateway/src/client/index.ts:100-107` — the only public door is `ctx.remote.$mount(contribution)`, taking a `TypertRemoteContribution`. [CONFIRMED]
- `packages/api/gateway/README.md:19` — *"`ctx.remote.$mount()` validates and registers a generated Host-for-Client contribution, then installs concrete direct and scoped methods for the calling Cordis fiber. Each namespace is a traced `remote.<namespace>` child Service and unloads after its last method is withdrawn."* [CONFIRMED]
- Therefore: **there is no way to make `remote.scriptLibrary` exist by writing YAML, by declaring `inject`, or by any browser-only code.** A generated contribution containing at least one descriptor with `namespace: 'scriptLibrary'` must be mounted. [CONFIRMED]

## Root cause

`remote.scriptLibrary` is not a name a plugin can claim — it is the service key the API Gateway *creates* (`remote.${namespace}`, `packages/api/gateway/src/client/index.ts:509-511`) when `ctx.remote.$mount()` installs a generated Typert Remote contribution whose descriptors carry `namespace: 'scriptLibrary'`. The OP's client plugin declared `inject: [... 'remote.scriptLibrary']` (the shape `docs/api-gateway.md:60` shows for a *consumer* of an existing namespace) without any Host-side `@Remote`-decorated service, without the generated `./typert` + `./remote` artifacts, and without a mount. Cordis inject-waiting has no timeout, so the fiber stays PENDING; `packages/client/web/src/boot.tsx:216-237` sweeps after the tree quiesces and, by the shell's one-shot design (`packages/client/web/README.md:25`), the page never leaves the boot screen. The blast radius — one bad entry, whole page down — is intended fail-loud behavior, not a cascade bug.

## Recommended next steps

### User-side recovery (do this first, nothing here needs a repo change)

1. `dsh web --dump-config` to print the composed tree and locate the row `id` whose `name` is the `dsh-script-library` package (boot-free, so it works while the page is broken).
2. Either disable it — add to `~/.dsh/profiles/web/cordis.patch.yml`:
   ```yaml
   - id: <the row id from step 1>
     disabled: true
   ```
   (form copied from `packages/bundle/web-app/cordis.patch.yml:21-23`) — or delete the `insert` row that added it. A disabled entry is skipped by the browser-roster scan at `packages/client/modules/src/index.ts:386-388`.
3. If it was installed as a profile dependency: `dsh plugin --profile web remove <package>` (`apps/cli/src/args.ts:172-180`), then check `~/.dsh/profiles/web/cordis.patch.yml` for a leftover row.
4. Restart `dsh web` and hard-reload the page. (`packages/client/modules/src/index.ts:14-19` — package verdicts are cached for the process lifetime; a file-watch reload of the patch layer is not guaranteed to drop the row.)
5. While iterating on the plugin, keep the row out of the composition and re-add it only after the Host side exists — or drop `'remote.scriptLibrary'` from the plugin's `inject` until you actually call `ctx.remote.scriptLibrary.*`.

### Repo-side: should one stuck entry be non-fatal?

**No — do not make it non-fatal.** `packages/client/web/README.md:25` already records one-shot rendering as a deliberate design with progressive rendering deferred to its own project, and `CLAUDE.md` → `## Conventions` requires misconfiguration to fail loud rather than silently skip a missing referent. Degrading a PENDING entry to a skipped one would ship a half-composed UI whose missing surfaces are invisible — exactly the failure mode the sweep exists to prevent. If anyone revisits this, it belongs to the deferred progressive-rendering project, not to a patch on `assertEntriesActive()`.

**Yes — make the message actionable.** Two low-risk, high-value improvements, both local to `packages/client/web/src/boot.tsx:227-229` (and its Host twin `packages/boot/app-boot/src/index.ts:710-713`):

1. When an unresolved service name matches `^remote\.`, append a one-line hint: this service is created by mounting a generated Typert Remote contribution, see `docs/api-gateway.md`. Today the message tells the user *what* is missing but gives no path to *why it can never arrive*. Cost is a regex and a string; it turns a dead end into a doc pointer.
2. Add a recovery line naming the concrete escape hatch — `dsh web --dump-config` plus `disabled: true` in `~/.dsh/profiles/web/cordis.patch.yml` — so a user whose page is bricked is not forced to search discussions. (The boot screen is the only surface they can still see.)

Both would need the usual treatment per `CLAUDE.md`: an Agent Note, a keyless snapshot for the changed user-visible text, and `pnpm run doc-sync` if `docs/api-gateway.md` gains the reciprocal "if you see `pending (waiting for service: remote.X)`" paragraph.

**A third, larger item worth filing separately:** `packages/api/remotes/README.md` already lists *"The capability set is fixed by explicit build-time value imports"* as a known limitation. Discussion [#2463](https://github.com/deepseek-ai/deepseek-harness/discussions/2463) is the first concrete external user hitting it. Whether an out-of-tree plugin should be able to contribute its own `remote.*` namespace (by self-mounting its own generated contribution, or by a discovery mechanism) is a real product question and should be an issue, not a patch.

## Draft response to the OP

---

你好，这个不是 bug，是 Web 外壳「一处不活就整页不启动」的刻意设计，同时你的插件缺了一半实现。先救急，再讲正确做法。

**一、先让页面恢复（不需要改仓库代码）**

1. 先找到你那条插件行的 `id`（这条命令不启动应用，页面坏着也能跑）：

   ```sh
   dsh web --dump-config
   ```

2. 在 `~/.dsh/profiles/web/cordis.patch.yml` 里把它禁用（或者直接删掉当初插入它的那条 `insert` 行）：

   ```yaml
   - id: <上一步查到的行 id>
     disabled: true
   ```

   `disabled` 是 loader patch 的正式字段，仓库自己就是这么用的，例如 `packages/bundle/web-app/cordis.patch.yml` 里禁用 hmr 那两行。被禁用的行不会进入浏览器插件清单（`packages/client/modules/src/index.ts` 的扫描会跳过 `entry.disabled`）。

3. 如果这个插件是用 `dsh plugin` 装进 profile 的，就再执行：

   ```sh
   dsh plugin --profile web remove <你的包名>
   ```

   然后回头确认 `~/.dsh/profiles/web/cordis.patch.yml` 里没有残留的行。

4. **重启 `dsh web`** 再硬刷新页面。只存盘不重启不一定生效：client-modules 的包扫描结果按包名缓存且不过期，文档明确说明「插件集合的变化要重启才生效」。

顺带提醒：`~/.dsh/profiles/web/cordis.yml` 每次启动都会被重写成空数组，改它没用；要改的是 `cordis.patch.yml`。另外还有一层机器级的 `~/.dsh/cordis.patch.yml`，它叠在每个 profile 的用户层之上，也可以在那里禁用。

**二、为什么会卡住 —— `remote.scriptLibrary` 不是你能自己起名的服务**

`remote.<namespace>` 这个服务名不是由插件声明出来的，而是 API Gateway **生成**出来的：`packages/api/gateway/src/client/index.ts` 里的 `remoteServiceKey(namespace)` 返回字符串 `` `remote.${namespace}` ``，而它唯一的调用路径是 `ctx.remote.$mount(contribution)` —— 也就是挂载一份由构建生成的 Typert Remote 贡献项，其中至少有一个描述符的 namespace 等于 `scriptLibrary`。

所以只在客户端插件里写 `export const inject = ['remote', 'remote.scriptLibrary']` 是永远等不到的：cordis 的 inject 等待没有超时，fiber 一直停在 PENDING，`packages/client/web/src/boot.tsx` 的启动巡检就报出你看到的那行。而 Web 外壳是「等到全部 entry 都 ACTIVE 才切到真实 UI」的一次性渲染（见 `packages/client/web/README.md` 的 Known Limitations），所以一个 entry 卡住 = 整页停在启动画面。这一条在仓库规范里叫「Misconfiguration fails loud」，是有意为之。

**三、正确做法：`remote.scriptLibrary` 要怎样才真的存在**

请以 **`docs/api-gateway.md`**（中文版 `docs/api-gateway.zh.md`）为准，它就是这件事的权威文档。仓库里 `goals` 这条链是完整的可抄样例：

Hi — this isn't a bug. It's the Web shell's deliberate "one entry not active ⇒ the whole page stays on the boot screen" design, plus a plugin that is missing half its implementation. Unblock first, then the correct way.

**1. Get your page back (no repo changes needed)**

1. Find your plugin's row `id` — this command is boot-free, so it works while the page is broken:

   ```sh
   dsh web --dump-config
   ```

2. Disable it in `~/.dsh/profiles/web/cordis.patch.yml` (or delete the `insert` row that added it):

   ```yaml
   - id: <the row id from step 1>
     disabled: true
   ```

   `disabled` is a real loader-patch field; the repo uses exactly this form itself (see the hmr row in `packages/bundle/web-app/cordis.patch.yml`). A disabled entry is skipped by the browser-roster scan in `packages/client/modules/src/index.ts` (`!entry.disabled`).

3. If you installed it into the profile, also run:

   ```sh
   dsh plugin --profile web remove <your-package>
   ```

   then check `~/.dsh/profiles/web/cordis.patch.yml` for a leftover row.

4. **Restart `dsh web`** and hard-reload the page. Saving the file alone is not enough: client-modules caches package verdicts per name and the docs state that plugin-set changes take effect on restart.

Note: `~/.dsh/profiles/web/cordis.yml` is rewritten to an empty list on every boot — editing it does nothing. Edit `cordis.patch.yml`. There is also a machine-wide `~/.dsh/cordis.patch.yml` applied on top of every profile's layer, which can disable a row too.

**2. Why it hangs — `remote.scriptLibrary` is not a name you can claim**

`remote.<namespace>` service keys are *generated*, not declared. In `packages/api/gateway/src/client/index.ts`, `remoteServiceKey(namespace)` returns the literal `` `remote.${namespace}` ``, and the only path that reaches it is `ctx.remote.$mount(contribution)` — mounting a build-generated Typert Remote contribution that contains at least one descriptor with `namespace: 'scriptLibrary'`.

So `export const inject = ['remote', 'remote.scriptLibrary']` on its own waits forever: cordis inject-waiting has no timeout, the fiber stays PENDING, and the boot sweep in `packages/client/web/src/boot.tsx` prints the line you saw. The shell renders the real UI only after every entry is ACTIVE (`packages/client/web/README.md`, Known Limitations: one-shot rendering by design), so one stuck entry keeps the whole page on the boot screen. In this repo's conventions that's the "misconfiguration fails loud" rule, not a cascade bug.

**3. The correct way to make `remote.scriptLibrary` exist**

Follow **`docs/api-gateway.md`** — it is the authoritative reference for this. The in-repo `goals` chain is a complete example to copy:

1. **Host service**: `packages/goal/goal/src/index.ts` — `class GoalService extends TypertRemoteService`, `super(ctx, 'goals')` binds the namespace, methods carry `@Remote('create')` etc. Unmarked methods never enter the generated artifacts and are not callable from the client.
2. **Package exports**: `packages/goal/goal/package.json` — `exports["./typert"] → lib/typert.host.js` and `exports["./remote"] → lib/typert.remote-client.js`, both listed in `files`. The generator only emits for packages that provide those entries.
3. **Client mount**: `packages/api/remotes/src/client/index.ts` — `import goalsRemote from '@deepseek-ai/dsh-goal/remote'`, then `await ctx.remote.$mount(contribution)`. **`remote.goals` exists only after this runs.**
4. **Consumer declaration**: `packages/client/ui-goal/src/client/index.ts` — `export const inject = ['slots', 'sessions', 'remote', 'remote.goals', 'locale', 'conversationEvents']`, with `@deepseek-ai/dsh-api-remotes` listed in that package's `dsh.client.inject`. Step 4 is what you wrote; steps 1–3 are missing.
5. **Build order**: after adding/changing a decorator, namespace, parameter, or return type, rerun `pnpm run build:lib` (Host generates the contract, then the Client compiles against it). `pnpm run dev:web` alone does not analyze Host decorators or generate the Remote client declarations.

**One limitation to know up front**: the Client capability set is a fixed build-time list — `packages/api/remotes/README.md` states plainly that "the capability set is fixed by explicit build-time value imports; the Client does not discover the Host's active Services or Remote definitions at runtime." In-repo, step 3 means editing `packages/api/remotes/src/client/index.ts`. If your plugin lives **outside** the repo under `~/.dsh/profiles/web`, there is no ready-made mount seat. In principle your client plugin can `inject: ['remote']` and call `ctx.remote.$mount(<your own package's generated /remote artifact>)` itself — `$mount` is public and scopes the mount to the calling fiber — but `api-remotes` is the only caller anywhere in the repo, so I can't promise that path is smooth.

If your script-library only does browser-side work and doesn't need to call the Host, the cheapest fix is to **drop `'remote.scriptLibrary'` from `inject`** and add it back once steps 1–5 are in place.

The Host half is third-party friendly, for what it's worth: `packages/typert/loader` auto-registers any mounted loader-entry package that exports `./typert` into `ctx.typert`, and the `typert-loader` row ships in the base bundle. It's only the Client-side mount that has no seat.
