## What the plugin is

<https://github.com/deepseek-ai/deepseek-harness/discussions/2553> — "dsh-budget: cost governance, budget caps and over-limit policies for DeepSeek Harness", author **PerryLink**, Aug 16 2026, category *Show Your Plugins!*, **0 replies** at time of reading.

A function plugin (`@deepseek-ai/dsh-*` conventions, but published unscoped as `dsh-budget`, Apache-2.0) that:

- aggregates token usage per session / UTC day / UTC month, prices it in USD through a built-in table merged with `config.prices`;
- enforces `budgets.session` / `.daily` / `.monthly` caps with a `warnRatio` threshold alert and an `overLimit` policy of `alert` | `block` | `degrade`;
- estimates a carbon footprint (`tokens × kWh/token × PUE × regional intensity`);
- samples per-model latency (min/p50/p95/max over a rolling window);
- exposes a `budget` Typert Remote (`status` / `setSettings` / `unblock`), a Settings tab, and a `/budget` command;
- appends `budget/alert` and `budget/block` session audit events;
- optionally POSTs threshold alerts to a webhook.

Declared peer: DeepSeek Harness `0.1.0-rc.6`. Install line advertised in the post: `dsh plugin --profile web add dsh-budget`.

## What it does well

These are real, and several show the author read harness source rather than guessing at it.

1. **Config discipline is better than most in-tree plugins.** Every deployment-varying value is a validated `Config` field with a bound (`src/config.ts`), and `resolveConfig` **re-judges every default and bound** so programmatic construction that bypasses Schemastery still fails loud — with a per-field `dsh-budget: config.<field> …` message. That is exactly the repo's "no hardcoded tunables in plugins" and "misconfiguration fails loud" pair, implemented as an explicit `resolve(request): Spec` step rather than `?? default` scattered through `run()`.

2. **The audit append correctly dodges the session reentrancy guard.** `session.append()` throws `session append cannot reenter while another append is being published` when called from inside a `session/event` callback — the guard is set at `packages/core/session/src/index.ts:636` and cleared in the `finally` at `:650-653`, while listeners are invoked at `:646`, i.e. still inside the `try`. The plugin defers its audit append with `queueMicrotask` and says why in a comment. That is correct, and it is not something you land without reading the source.

3. **Ignoring `reasoningTokens` is right, not an oversight.** `TokenUsage.reasoningTokens` (`packages/llm/llm/src/types.ts:135-141`) is a *subset* of `outputTokens` for the DeepSeek adapter — `mapUsage` sets `outputTokens: usage.completion_tokens` and reads reasoning from `completion_tokens_details` separately (`packages/llm/llm-deepseek/src/translate.ts:57-60`). The harness's own authoritative fold makes the same choice: `bucketsFrom` builds its four buckets from `inputTokens`/`outputTokens`/`cacheReadTokens`/`cacheWriteTokens` and omits reasoning (`packages/llm/token-meter/src/usage-projection.ts:31-36`). `recordUsage` matches it bucket for bucket. Counting reasoning would have double-billed it.

4. **Cache tokens are priced as their own buckets.** `estimateUsageCost` prices `cacheRead` and `cacheWrite` separately with `?? price.input` fallbacks (`src/estimate/prices.ts`), matching the harness's DISJOINT-counts convention documented at `packages/llm/llm/src/types.ts:128-133`. Many cost estimators fold cache traffic into input and are wrong by an order of magnitude; this one does not.

5. **`priceFor` resolves `${provider}/${model}` before the bare model id.** The plugin already understands that a model id alone does not identify a billed route. That instinct is correct and is exactly the thing [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470) is about — see Finding 4 for where the rest of the code does not follow through.

6. **The price table carries provenance and an honest drift warning.** Each `BUILTIN_PRICES` entry is tagged `source: 'vendor' | 'upstream-cny'`, the CNY→USD constant is documented as *"a conversion constant of the shipped DATA, not a runtime exchange rate"*, and the module doc says prices drift and the table is a starting point. Compare `packages/llm/llm-pi-ai/src/catalog.ts:26-30`, which quietly zeroes cost metadata — the plugin is more forthcoming about its numbers than the harness is about its own.

7. **Registrations follow the repo rule.** Everything goes through `ctx.on(...)` (auto-disposed with the plugin fork), `ctx.plugin(BudgetService, …)`, and — for the one registry handle that returns a disposer — `ctx.effect(() => commands.register(…), 'dsh-budget: /budget command')`, with a label. That is the "Registrations are effects" convention followed correctly, including the detail that a registry's `register()` return value is the disposer.

8. **The webhook is genuinely defensive.** `AbortController` + bounded timeout, `finally { clearTimeout(timer) }`, non-2xx treated as failure, errors swallowed and returned rather than thrown into the hot path, and `webhookDisplay()` strips credentials from the URL before logging. Timeout is a validated config field, not a constant.

9. **`/budget unblock` writes an audit event.** Lifting a block appends `budget/block { blocked: false }`, so the transition is reconstructable from the log rather than living only in process memory. The instinct matches the repo's "Model-visible ⟺ logged" rule — see Finding 1 for the mechanism that unfortunately turns this against the session.

10. **The blocking seam is the right one, and the author justified it in a comment.** `llm/stream` really is the single public streaming entry point — see Finding 6.

## Findings (each labelled, each cited)

### Where usage comes from, and what the harness considers authoritative

**Finding 0 — the plugin re-derives its own accounting rather than reading the harness's. CONFIRMED.**

The plugin's only input is `ctx.on('session/event', …)`, from which it takes `event.data.usage` on `assistant/message` and feeds `aggregator.recordUsage()` (`src/index.ts`).

The harness's authoritative durable accounting is `tokenUsageProjectionDefinition` in `packages/llm/token-meter/src/usage-projection.ts:98-140` — a registered session projection (`key: 'tokenUsage'`, `stateVersion: 1`) whose `view` yields `{ uncachedInputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`. Re-deriving is a legitimate choice (the projection yields whole-session totals, not the per-day/per-month/per-model buckets the plugin needs), and the bucket selection matches. But three behaviors of that projection are load-bearing and the plugin does not reproduce them — Findings 1a, 2, 3.

**Finding 1 — the audit events can make a session refuse to load. CONFIRMED. This is the most consequential finding in this note.**

`budget/alert` and `budget/block` are appended to the session log via the two-argument `session.append(type, event)` form, so they carry no `ignorable` marker.

The session envelope documents the default at `packages/core/session/src/types.ts:412-422`: *"Absent means required: a reader meeting an unrecognized type without this marker MUST refuse to reconstruct the session instead of silently dropping the event."*

The reader enforcing it is `assertEventsSupported` at `packages/session/session-persistence/src/coordinator.ts:1061-1066`:

```ts
if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue
throw this.unsupported(meta, `session "${meta.id}" contains event type "${event.type}" (seq ${event.seq}) unknown to this harness and not marked ignorable; refusing to interpret the log …`)
```

called on all three read paths (`:864`, `:884`, `:900`).

`KNOWN_SESSION_EVENT_TYPES` is **generated from this repository** (`packages/core/session/src/known-event-types.ts:1-19`), and its own doc names this exact situation: *"Downstream (out-of-repo) plugin events are outside this list by construction; a registration surface for them is deferred until such a consumer exists."* Installing dsh-budget does not add its types to that set.

The write side does not catch it either — deliberately. `packages/session/session-persistence/src/coordinator.ts:686-690`: *"The unknown-type guard is deliberately read-side only: an append-time refusal would stall a live session's durability mid-flight, which costs more than a loud refusal at the log's next load."*

So the sequence is: the alert appends cleanly → the write-behind path persists it (`:1123-1126`) → the next resume of that session throws `SessionFormatUnsupportedError`. With the shipped defaults (`alertsEnabled: true`, `warnRatio: 0.8`, `budgets.session: 10`), the first `budget/alert` fires at $8 of session spend.

**PLAUSIBLE, not confirmed:** that the failure is *reachable in a default web deployment*. It requires a persistence backend mounted and a subsequent cold resume of that session; I did not run it. The mechanism is confirmed line by line, the trigger is not.

Everything the fix needs already exists in the envelope: `ignorable?: true` at `packages/core/session/src/types.ts:422`, whose doc says a writer sets it *"only on purely informational records whose loss cannot affect reconstruction"* — which is precisely what a budget audit record is. The plugin's own JSDoc notes the pinned rc.6 peers expose no append-envelope option, so this may be a peer-version constraint rather than an oversight; worth confirming against the rc.6 `Session.append` signature.

**Finding 2 — usage from a failed request is never billed. CONFIRMED.**

Usage reaches the log twice: as an `assistant/chunk` whose `chunk.type === 'usage'` (`packages/llm/llm/src/types.ts:297`, appended at `packages/core/agent-loop/src/agent.ts:349`), and again on the `assistant/message` (`:382-388`). The harness projection reads **both** and replaces rather than adds when turn/step match (`packages/llm/token-meter/src/usage-projection.ts:113-140`), and states why at `:100-102`: *"Usage chunks provide an early sample that survives a later request failure; an assistant message provides the final sample for the same turn/step."*

The plugin reads only `assistant/message`. That correctly avoids double counting — but when a step fails, `packages/core/agent-loop/src/agent.ts:368` throws **before** the `assistant/message` append at `:373-382`. The usage chunk is in the log; no assistant message ever is. Those tokens were billed by the provider and are invisible to the cap.

This matters most for the failure modes that are expensive: a long prompt rejected at the provider after usage was reported, or the retry storms discussed in [#2379](https://github.com/deepseek-ai/deepseek-harness/discussions/2379). Reading `assistant/chunk` with `chunk.type === 'usage'` and applying the projection's same-turn/step replace rule would close it; `usage-projection.ts:113-140` is a working 25-line reference implementation.

**Finding 3 — accumulated spend is lost on resume, fork, and hot reload. CONFIRMED (mechanism).**

`Session.firstLiveSeq` documents it at `packages/core/session/src/index.ts:451-456`: *"Events with smaller seq values entered through construction — replay, fork, or resume — and were never published on the `session/event` firehose (constructor seeds do not emit), so consumers that replay the log as a publication substitute (telemetry adoption) start here."* The field is set at `:539`.

The plugin's sole input is that firehose. Consequences:

- resuming a session replays nothing, so its accumulated cost restarts at zero and a session cap never triggers on resumed work;
- a plugin mounted after sessions are already live (hot reload, or the advertised `dsh plugin --profile web add dsh-budget` against a running deployment) sees nothing from those sessions;
- the README's claim that *"daily/monthly buckets rebuild from session logs on restart"* is **UNVERIFIED and appears unimplemented** — there is no `session/created` listener, no `sessions.list()` sweep, and no log replay in `src/index.ts` or `src/aggregate/usage.ts`. It could live in a file I did not read, but those are the two files where it would have to be wired.

Compounding it: `recordUsage` buckets by `dayKey(this.now())` — wall clock, not `event.time` — so any future replay would file historical usage under today.

Two in-tree templates for exactly this: `packages/session/session-telemetry/src/coordinator.ts:80-110` and `:139` (`session/created` + a sweep of already-live sessions, replaying from `session.firstLiveSeq - 1`, with the reason spelled out at `:152-155`), and the persistence coordinator's own `session/created` + `session/event` pair at `packages/session/session-persistence/src/coordinator.ts:1118-1126`.

### Cost attribution across provider routes

**Finding 4 — attribution is one global mutable slot; it does not survive multi-provider routing. CONFIRMED.**

`BudgetAggregator` holds a single `provider` / `model` pair in its state, overwritten by `setAttribution()` on every `request/header` (`src/aggregate/usage.ts`). `session/event` is a firehose across all sessions in scope (`packages/core/session/src/index.ts:454`). So the pair is whichever request header arrived most recently *from any session*, and `recordUsage` prices the next `assistant/message` against it regardless of which session that message belongs to.

Consequences, all readable in `src/aggregate/usage.ts`:

- **Concurrent sessions cross-contaminate.** Session A on an expensive route and session B on a cheap one interleave; each message is priced by whoever emitted the last header. Per-session cost, and therefore the session cap, is wrong in both directions.
- **Subagent delegation is the same race, one process deeper.** A child agent's requests emit their own `request/header`, so the parent's next assistant message is priced at the child's route.
- **Per-model buckets are keyed by model id alone.** `addModel` uses `const model = this.state.model || 'unknown'` as the map key and stores `provider` only as a display field on first insert. Two providers serving the same model id merge into one bucket under whichever provider won the race. This is an unexplained asymmetry with `priceFor`, which does the right thing and tries `${provider}/${model}` first — the repo's "prefer symmetry for parallel values" rule reads this as a missed extraction, and it is the cheapest of these to fix.

Cross-check against our [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470) research (`.agents/discussions/2470.md`): `provider` is not a display preference — each registered route resolves its own credential reference and base URL (`packages/llm/llm-deepseek/src/index.ts:184`, `:225-245`, `:256`), so it decides which account is billed; the repo names the consequence in its own comment at `packages/llm/llm-pi-ai/src/index.ts:180-184`. Two things follow for this plugin:

1. On any released dsh, a delegated child could run on a *different provider* from its parent (`resolveChildAgentOptions` reads the creation snapshot — `packages/subagent/subagent/src/child-agent.ts:68-83`). Per-session cost attribution that assumes one route per session tree is wrong there for reasons outside the plugin's control.
2. **But dsh-budget's attribution would still be wrong after that bug is fixed**, because the defect here is independent: one global slot, no per-session keying. Keying attribution per session — or reading `session.requestHeader()?.config` at the point of use (`packages/core/session/src/index.ts:670-680`, an O(new events) incremental fold) instead of caching a global — fixes it regardless of [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470)'s outcome. The second is strictly better: it is the same authority the harness itself treats as the live route, and it needs no `request/header` listener at all.

**Finding 5 — `blockedScopes` is global, so one session's cap blocks every session. CONFIRMED.** The `llm/stream` listener reads `aggregator.blockedScopes` with no session filter (`src/index.ts`), and the set itself is a single `Set` on aggregator state with no session key (`src/aggregate/usage.ts`). A `session`-scope block triggered by session A short-circuits session B's model calls too, with a message naming A's cap. For `daily`/`monthly` that is intended; for `session` it is almost certainly not.

### How the cap is actually enforced

**Finding 6 — the seam is right; three things can silently unhook it.**

The repo rule (`packages/AGENTS.md:14`): *"Enforce a decision in the operation that makes it. Schema omission, prompt filtering, facades, wrappers, and listener order are not enforcement when direct or alternate callers can bypass them; test denial through the executor."*

**The good news, CONFIRMED:** `llm/stream` is not a facade. `LlmRuntime.stream()` at `packages/llm/llm/src/index.ts:913-915` is the only public streaming entry point, and it routes unconditionally through `ctx.waterfall(this, 'llm/stream', options, () => this.adapterStream(options, prepared))` at `:922-928`; `adapterStream` is `private` (`:843`). There is no `generate()` sibling that skips the waterfall. A short-circuiting `llm/stream` listener genuinely lands on the operation that makes the call. The author's comment defending the deliberate non-`next()` return is also correct per the waterfall semantics at `docs/cordis-primer.md:30`.

Three caveats, in descending confidence:

**6a — the blocker is installed conditionally and fails open. CONFIRMED.** `src/index.ts` declares `export const inject = ['sessions']` and then reads `const llm = ctx.get('llm')`, installing the blocker only `if (llm !== undefined)`. `llm` is not in `inject`, and the primer is explicit at `docs/cordis-primer.md:11`: *"A plugin that names required services waits until those services exist."* So the plugin does not wait for `llm`, and in any composition where it applies first, `overLimit: 'block'` silently degrades to no enforcement at all — no throw, no warn, and a Settings tab that still shows caps. This is the "misconfiguration fails loud" rule inverted: the failure is silent and the surface keeps claiming the cap is active. Adding `'llm'` to `inject`, or wrapping the blocker in `ctx.inject(['llm'], …)`, makes it deterministic.

**6b — the listener is not `global`, unlike the harness's own listener on the same event. CONFIRMED asymmetry, UNVERIFIED consequence.** The plugin registers `{ prepend: true }`. The harness's stream invariant registers `{ global: true, prepend: true }` on the identical event (`packages/llm/llm/src/invariant.ts:88`). Cordis filters non-global listeners against the emitting context at `vendor/cordis/src/events.ts:173` (`hook.global || !filter || filter.call(thisArg, hook.ctx)`). Whether an isolated context — a subagent isolate, a worker-thread workflow — can dispatch `llm/stream` past a non-global listener I did not test, so treat this as a question rather than a defect. The harness's choice of `global: true` for the invariant is the reason to ask it.

**6c — out-of-process subagent backends cannot be metered or blocked at all. CONFIRMED, and inherent.** `subagent-acp`, `subagent-codex`, `subagent-claude-code`, and `subagent-dsh-sdk` own their own routes and never call this process's `LlmRuntime` (`packages/subagent/subagent-dsh-sdk/src/index.ts:77` defaults to `deepseek-v4-flash`). Their spend is real, unmetered, and unblockable here. Not fixable by this plugin — worth one sentence in the README so nobody reads a $50 daily cap as covering delegated work.

**Finding 7 — over-limit blocking is nested inside the cooldown-gated alert branch. CONFIRMED. Most likely to surprise a user.**

In `checkBudgets` (`src/governance.ts`), per scope:

```ts
if (state === 'ok' || !config.alertsEnabled) continue
const age = aggregator.lastAlertAge(scope, state, at)
if (age < config.alertCooldownMs) continue
aggregator.recordAlert({ … })
hooks.onAlert(…)

if (state === 'over') {
  if (config.overLimit === 'block' || config.overLimit === 'degrade') {
    aggregator.blockScope(scope)
    hooks.onBlock(scope, degradationFor(config, aggregator, scope))
  }
}
```

`blockScope()` is reachable only past both guards, so:

- **`alertsEnabled: false` disables enforcement entirely.** A user who turns off notifications but keeps `overLimit: 'block'` gets no cap. Nothing in the config docs suggests `alertsEnabled` is an enforcement switch — it is described as the master switch for *alerts*.
- **`/budget unblock` cannot re-block for up to `alertCooldownMs`.** Default is `3_600_000` — one hour (`src/config.ts`). Unblock at the cap, keep spending, and the `over` state cannot re-arm until the cooldown on the `scope:over` key expires. That is an hour of uncapped spend after a single confirmation click, which inverts what an unblock button means.

Both dissolve if the block decision moves above the alert guards — the cap crossing and the notification are different decisions with different rate-limiting needs.

**Finding 8 — caps edited in the Settings tab are displayed and quoted but never enforced. CONFIRMED.**

Two cap sources exist. `effectiveCap(settings, config, scope)` prefers the runtime `RuntimeSettings` value and falls back to config (`src/service.ts`); `BudgetService.status()` uses it for every `ScopeLine.capUsd` and `ratio`, and `src/index.ts` uses it to compose the blocked-stream message text.

`checkBudgets` uses neither. It reads `config.budgets.session` / `.daily` / `.monthly` directly (`src/governance.ts`). `budget/setSettings` writes only `this.bindings.settings` (`src/service.ts`).

So lowering a cap in the Settings tab moves the progress bar, the ratio, and the text of any eventual block message — while the threshold that actually fires stays at the cordis.yml value. Raising it is worse: the UI reads unblocked while enforcement still trips at the old, lower number. Passing `settings` into `checkBudgets` and reading through `effectiveCap` makes one authority out of two.

### Prices

**Finding 9 — prices are hardcoded, and the harness offers nothing better. CONFIRMED (negative result).**

`BUILTIN_PRICES` in `src/estimate/prices.ts` hardcodes 16 models. Staleness risk is real and the plugin already carries the mitigations that matter (Finding 6 in *What it does well*), so this is context rather than criticism:

- `LlmModelInfo` carries `provider`, `id`, `name`, `description`, `inputModalities` — **no cost fields** (`packages/llm/llm/src/types.ts:233-244`). `LlmModelContext` carries only `contextWindow` (`:247-250`).
- `packages/llm/llm-deepseek/src/index.ts:50-51` publishes catalog entries with `contextWindow` and no pricing.
- The one price-shaped structure anywhere near the harness is pi-ai's `ModelCost` (`input`/`output`/`cacheRead`/`cacheWrite` — the same four fields as the plugin's own `PriceEntry`), and `packages/llm/llm-pi-ai/src/catalog.ts:26-30` states the harness deliberately does not use it: *"The harness never reads pi-ai's cost metadata — `replay.ts` zeroes it and no consumer reports spend — so this is the absence of a fact, not a configurable rate."* Confirmed at `packages/llm/llm-pi-ai/src/replay.ts:54`.

So there is no in-tree pricing source to read instead. For `llm-pi-ai` routes specifically, `getBuiltinModels()` from `@earendil-works/pi-ai/providers/all` does carry `ModelCost` per model in a field layout identical to `PriceEntry` — a possible upstream for part of the table, at the cost of a direct dependency on pi-ai's catalog. Untested by me.

Two smaller notes: the `defaultPrice` documented in the README as `{input: 1.0, output: 3.0}` gets `cacheRead: 1.0, cacheWrite: 1.0` from the schema but only `{input, output}` from `resolveConfig`'s fallback branch when `config.defaultPrice` is absent — an unknown model's cache traffic is then priced at `price.input` via `estimateUsageCost`'s `?? price.input`, which lands on the same number, so it is a readability asymmetry rather than a bug. And `src/estimate/cost.ts` — the ported LLM-Cost-Estimator-CN calculator, per-1k CNY, with a `'基准'` string literal and a `+` sign hardcoded onto negative percentages in `percentageDiff` — appears to be a parallel, unused pricing path next to `prices.ts`. I did not find a caller in the files I read.

### The [#2554](https://github.com/deepseek-ai/deepseek-harness/discussions/2554) connection

**Finding 10 — [#2554](https://github.com/deepseek-ai/deepseek-harness/discussions/2554) sits directly upstream of this plugin's headline number, at a 10× lever. CONFIRMED arithmetic, on an UNVERIFIED premise.**

<https://github.com/deepseek-ai/deepseek-harness/discussions/2554> (izz-BLUE) reports DSH-derived cache buckets diverging from the DeepSeek console — ~60M hit / ~396K miss in DSH against 59.3M hit / 1M miss in the console — and asks whether the adapter should prefer the native `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` fields over the OpenAI-compatible spellings.

The line reference in that report checks out exactly. `packages/llm/llm-deepseek/src/translate.ts:53-62`:

```ts
export function mapUsage(usage: WireUsage): TokenUsage {
  const cacheRead = usage.prompt_tokens_details?.cached_tokens ?? usage.prompt_cache_hit_tokens
  const reasoning = usage.completion_tokens_details?.reasoning_tokens
  return {
    inputTokens: usage.prompt_tokens - (cacheRead ?? 0),
    outputTokens: usage.completion_tokens,
    ...cacheRead !== undefined ? { cacheReadTokens: cacheRead } : {},
    ...reasoning !== undefined ? { reasoningTokens: reasoning } : {},
  }
}
```

Two facts worth handing to both authors:

- **`mapUsage` never sets `cacheWriteTokens`.** A repo-wide grep for `cacheWrite` under `packages/llm/llm-deepseek/src/` returns nothing. For DeepSeek routes, cache misses land in `inputTokens`, and the plugin's `cacheWriteTokens` bucket is permanently zero. The plugin's deepseek entries price `cacheWrite` equal to `input` (`0.27`/`0.27` and `0.55`/`0.55`), so no cost error follows from that — but the Settings tab's cache-write column will read zero on DeepSeek regardless of real cache-write traffic.
- **The hit/miss split is priced at 10× in the plugin's own table.** `'deepseek-chat': { input: 0.27, cacheRead: 0.027, … }`. The premise is [#2554](https://github.com/deepseek-ai/deepseek-harness/discussions/2554)'s, not mine: I have not seen raw wire captures where the two spellings disagree, which is exactly what FirmaSpring asked for in that thread.
