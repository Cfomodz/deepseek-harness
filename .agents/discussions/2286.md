# 2286 — 通过 Mise 安装 npm:@deepseek-ai/dsh 时 Aube 无法解析互递归 peer dependencies

## Verdict

**Both — but the weight is on the resolver, and the repo's graph is legal-but-hostile.**

- The mutually recursive peer edges are **real and CONFIRMED**, but they are **not** the `@deepseek-ai/cordis`-as-peer-of-every-package rule the OP's framing implies. That rule is a pure fan-in (225 packages → 1 peer), not a cycle. The actual cycle is a 3-node strongly connected component entirely inside the **vendored Cordis framework**, inherited verbatim from upstream `cordiverse/cordis`.
- The cycle is **intentional and inherited**, not a defect introduced here. npm, pnpm, and yarn all resolve it; the repo's own release gate installs the published tarballs with `npm install`.
- Aube's `apply_peer_contexts` fixed-point loop treats non-convergence as **fatal** (a deliberate v1.9.1 hardening that replaced a silent broken-graph warning). That is a third-party resolver limitation on a graph the rest of the ecosystem accepts.
- The two Smithy trust downgrades are a **separate, unrelated, and already-fixed upstream incident**: `@smithy/core@3.33.0/3.33.1` and `@smithy/node-http-handler@4.11.0/4.11.1` shipped **without SLSA provenance attestations**; the neighbouring versions on both sides have them. Fixed by `3.33.2` / `4.11.2`.
- **Mise is not a supported install path** — it appears nowhere in the repo's docs.

### B. The real cycle: a 3-node SCC inside vendored Cordis

- **CONFIRMED.** Tarjan SCC over the full workspace `peerDependencies` graph (236 manifests) yields **exactly one** SCC of size > 1, of size 3:

A pnpm-style resolver encodes peer resolutions as `dep_path` suffixes like `pkg@1.0.0(cordis@4.0.1)`. A cyclic peer group means each member's suffix must embed the others' suffixes, which is only well-defined as a fixed point. Aube's own docs acknowledge exactly this growth mode — see finding D.

### D. Aube's fixed-point limit and mise's npm backend

- **CONFIRMED.** Aube fails hard on non-convergence by design. From the v1.9.1 release notes, <https://github.com/endevco/aube/releases/tag/v1.9.1>: *"Resolver peer-context divergence is fatal"* — `apply_peer_contexts` hitting `MAX_ITERATIONS` *"used to log a warning and ship a broken graph"* and now *"returns a fatal `Error::PeerContextDivergence(usize)`"*. The OP's error text is this error surfacing.
- **INSUFFICIENT-DATA on the literal `16`.** No Aube document I could reach states the numeric `MAX_ITERATIONS`. The OP's message says 16; that is consistent with a compiled-in constant but I could not corroborate the value from a primary source. It is also not exposed as a tunable — <https://aube.jdx.dev/settings/> documents no max-iterations setting.
- **CONFIRMED — Aube knows mutual peer cycles are a growth hazard.** Its settings docs describe `peersSuffixMaxLength` (`int`, default `1000`): *"Max length of the peer-ID suffix in lockfile dep_paths"*, with the explanation that mutual-peer cycles can grow suffixes unboundedly across fixed-point iterations, and that oversized suffixes are replaced by a parenthesized SHA-256 short hash to match pnpm's format. <https://aube.jdx.dev/settings/>
- **CONFIRMED — Aube is mise's default.** <https://mise.jdx.dev/dev-tools/backends/npm.html>: `npm.package_manager` (`MISE_NPM_PACKAGE_MANAGER`), default `auto`, allowed `auto | npm | aube | aube_cli | bun | pnpm`; *"The default, `auto`, uses mise's embedded `aube` package manager."* Separately `npm.shell_out` (`MISE_NPM_SHELL_OUT`), boolean, default `false`.
- **CONFIRMED.** `trust_policy_excludes` corresponds to the documented `trustPolicyExclude` (`list<string>`, default `[]`, *"Packages exempt from `trustPolicy` checks"*), <https://aube.jdx.dev/settings/>. It gates trust only — it has no effect on the resolver, which is exactly the behaviour the OP observed.

## Root cause

Two independent causes were conflated in one report.

**Primary (install failure).** The vendored Cordis framework contains a 3-package strongly connected component in its `peerDependencies` graph — `@deepseek-ai/cordis ↔ @deepseek-ai/cordis-plugin-loader`, `@deepseek-ai/cordis ↔ @deepseek-ai/cordis-plugin-include`, plus `include → loader`. This is inherited unchanged from upstream `cordiverse/cordis` and is deliberately preserved by the vendoring policy. It is legal npm metadata that npm, pnpm, and yarn all resolve, and that `@deepseek-ai/dsh` closes at the root by depending on all three concretely. Aube encodes peer resolutions as pnpm-style peer-ID suffixes computed by a fixed-point iteration, and since v1.9.1 treats non-convergence as fatal rather than shipping a possibly-broken graph. A cyclic peer group at the sink of a 225-package fan-in is the pathological input for that algorithm. **So: a resolver limitation, triggered by a graph this project chose to inherit.** Neither side is simply wrong; the repo is not violating the npm spec, and Aube is not wrong to refuse to emit a lockfile it cannot prove complete.

**Secondary (trust warnings, unrelated).** `@smithy/core@3.33.0`/`3.33.1` and `@smithy/node-http-handler@4.11.0`/`4.11.1` were published without SLSA provenance attestations while their immediate neighbours on both sides have them. Aube's trust policy correctly flagged the regression. This is an upstream AWS/Smithy release-tooling lapse, already corrected in `3.33.2` and `4.11.2`, and reaches this project only transitively through `@earendil-works/pi-ai`.

## Recommended next steps (concrete and ordered)

1. **Answer the OP** with the draft below: mise is unsupported, `npx @deepseek-ai/dsh web` is the tested path, the Smithy warnings are upstream and already fixed.
2. **Point the OP at `npm.package_manager` rather than `npm.shell_out`.** `mise settings set npm.package_manager=pnpm` (or `=npm`) keeps mise as the version/tool manager and only swaps the resolver. Be honest that this also removes Aube's trust checks from the path — the difference from `shell_out` is ergonomic, not a security win.
3. **File the convergence failure upstream with Aube** (<https://github.com/jdx/aube>), attaching this minimal reproduction: `@deepseek-ai/cordis@4.0.1` + `@deepseek-ai/cordis-plugin-loader@1.0.2` + `@deepseek-ai/cordis-plugin-include@1.0.6`. It is a 3-package repro of a graph pnpm/npm accept, which is far more actionable for them than "installing dsh fails". Aube already ships `peersSuffixMaxLength` for suffix growth in mutual-peer cycles, so this looks like an adjacent unhandled case rather than a deliberate rejection.
4. **Consider adding `peerDependenciesMeta.optional` to `vendor/include/package.json`** for its `@deepseek-ai/cordis` and `@deepseek-ai/cordis-plugin-loader` peers, matching what `vendor/cordis/package.json:39-46` already does for its own two. That would make every edge of the SCC optional and may let a suffix-based resolver break the cycle. **Caveat: unverified — I did not test whether Aube converges with optional edges, and this diverges from upstream, which `vendor/README.md:34` says the vendoring deliberately avoids.** Treat as an experiment to run, not a fix to apply.
5. **Separately, evaluate whether `@deepseek-ai/dsh-llm-pi-ai` belongs in the shipped `dsh-base` bundle.** `packages/bundle/base/package.json:65` makes a package self-described at `packages/llm/llm-pi-ai/package.json:3` as a *"design-verification twin"* a hard runtime dependency, dragging the entire AWS SDK + Smithy subtree — and its supply-chain incidents — into every user install. This is orthogonal to [#2286](https://github.com/deepseek-ai/deepseek-harness/discussions/2286) but is why this project was exposed to a Bedrock-only dependency's provenance lapse at all. Worth a separate issue.
6. **Optional, low cost:** add a short "installing via third-party tool managers is not supported; use `npx`" line to the README so this recurs less.

> One clarification first: the repo does require every `packages/*/*` package to declare `@deepseek-ai/cordis` in both `peerDependencies` and `devDependencies` (enforced by `scripts/check-workspace-constraints.ts`), and 225 of 236 workspace manifests do. But that is pure **fan-in** (225 → 1) and introduces no cycle at all.
>
> The actual cycle lives inside the vendored Cordis framework. Running a strongly-connected-component analysis over the whole `peerDependencies` graph yields **exactly one** SCC of size > 1, of size 3:
>
> - `@deepseek-ai/cordis@4.0.1` → peers `cordis-plugin-include`, `cordis-plugin-loader` (both marked `optional`)
> - `@deepseek-ai/cordis-plugin-loader@1.0.2` → peer `cordis` (not optional)
> - `@deepseek-ai/cordis-plugin-include@1.0.6` → peers `cordis` and `cordis-plugin-loader` (neither optional)
>
> That is `cordis ↔ loader` and `cordis ↔ include`, plus the `include → loader` chord. These peer ranges are inherited **verbatim** from upstream `cordiverse/cordis` — upstream `cordis@4.0.0-rc.8` declares the same shape — and our vendoring policy explicitly preserves upstream dependency and peer ranges (`vendor/README.md`). So: intentional, and not introduced here.
>
> This is legal npm metadata. npm, pnpm, and yarn all resolve it, and `@deepseek-ai/dsh` closes the cycle at the root by declaring all three packages as ordinary `dependencies`, so every peer edge has a concrete satisfier. Our release gate `scripts/release/verify-packed-install.ts` installs the packed tarballs with `npm install` and drives the resulting binary on every release, so the npm path is continuously verified against this exact graph.
>
> The proximate cause is on Aube's side: it represents peer resolutions as pnpm-style peer-ID suffixes solved by fixed-point iteration, and since v1.9.1 `apply_peer_contexts` hitting `MAX_ITERATIONS` returns a fatal `Error::PeerContextDivergence` instead of warning and shipping a possibly-broken graph. A cyclic peer group at the sink of a 225-package fan-in is the worst case for that algorithm. Aube's own settings docs describe `peersSuffixMaxLength` and note that mutual-peer cycles can grow suffixes unboundedly, so this reads as an adjacent uncovered case rather than a deliberate rejection.
>
> Please do file the 3-package minimal reproduction with Aube (<https://github.com/jdx/aube>):
> ```
> @deepseek-ai/cordis@4.0.1
> @deepseek-ai/cordis-plugin-loader@1.0.2
> @deepseek-ai/cordis-plugin-include@1.0.6
> ```
> It is far more actionable for them than "installing dsh fails".
>
> **(2) There is no supported Mise install path today.**
>
> The documented paths are exactly two:
>
> - `npx @deepseek-ai/dsh web` (README)
> - From source: `git clone` → `pnpm install` → `pnpm run build` → `pnpm dsh web`
>
> `mise` appears nowhere in the README, CONTRIBUTING, or `docs/`, and we publish no mise registry entry.
>
> If you want to keep using mise for version management, a cleaner lever than `npm.shell_out=true` is to swap the resolver rather than the whole path:
> ```toml
> [settings.npm]
> package_manager = "pnpm"   # or "npm"
> ```
> (equivalently `mise settings set npm.package_manager=pnpm`). To be straight with you, though: this also takes Aube out of the resolution step, so its supply-chain trust checks do not run either. Compared with `shell_out` it is tidier, not more secure. Until Aube handles the cycle, there is no combination that both runs Aube's trust checks and completes the install.
>
> We are not planning to diverge from upstream Cordis's peer declarations to work around a single third-party resolver. There is one experiment worth trying: adding `peerDependenciesMeta.optional` to both peers in `vendor/include/package.json` (which `vendor/cordis` already does for its own), making every edge of the SCC optional. **I have not verified that Aube converges with that change**, and it diverges from upstream, so treat it as a candidate to test rather than a commitment.
