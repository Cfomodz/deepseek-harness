# 2402 — macOS exFAT 卷上 pnpm install 必现失败：install-lefthook 锁的 inode 所有权校验在 exFAT 上永不成立

## Verdict

**CONFIRMED as a real defect in this repository.** The reporter's reading of `scripts/install-lefthook.mjs` is accurate line for line: the installer captures the lock's identity with `fstatSync` on the open handle and re-verifies it with `lstatSync` after `closeSync`, and a mismatch is a hard failure that also orphans the lock file. Every step of the reported alternating loop is reproducible from the code without an exFAT volume. The only claim I cannot verify locally is the exFAT kernel behavior itself (no exFAT mount available here); that part is PLAUSIBLE and consistent with the reported inode values.

A fix belongs in this repo, and it should be **smaller than what the discussion replies propose**: rather than probing the mount for stable file IDs and degrading, the dev/ino comparison should be dropped entirely in favor of the random-UUID record the lock already carries, which is a strictly stronger and filesystem-independent ownership credential. No post-ready answer exists in the thread yet (all four replies converge on a probe-and-degrade design that nobody has implemented); the draft below is post-ready.

## What was reported

Environment: macOS 26.5 (Darwin 25.5.0, arm64), repository checked out on an exFAT-formatted Samsung T7 USB SSD at `/Volumes/SamsungT7/git/deepseek-harness`, master @ `47f943859b`, pnpm 11.7.0.

`pnpm install` fails in `postinstall` with exit code 1, alternating between two messages:

1. `[install-lefthook] stale Lefthook installer lock "/Volumes/SamsungT7/.../.git/dsh-lefthook-install.lock". Confirm no Lefthook installer is running, remove it manually, and retry.`
2. (after manually deleting the lock) `[install-lefthook] Lefthook installer lock ownership changed for /Volumes/SamsungT7/.../.git/dsh-lefthook-install.lock; refusing to remove it`

Claimed cause: on macOS exFAT, `fstat` on the open handle reports a synthesized file ID near `UINT64_MAX` (`18446744073709085000`), `lstat` on the same path while the handle is open reports the same synthesized value, and `lstat` after the handle closes reports a different, small, stable ID (`950466`); `dev` is unchanged. The installer's post-close identity check therefore can never hold on that volume.

Workarounds reported as effective: `CI=true pnpm install`, or moving the checkout to APFS.

Reporter's three questions: (1) should inode+path validation degrade on filesystems without stable file IDs; (2) should exFAT be documented as unsupported; (3) is there a stable credential that could replace the inode check.

Replies (moonquake2004 ×2, YuanyuanMa03, Electricitysheep) cross-checked the code at 47f9438, agreed the `'wx'` exclusive create plus PID+UUID record already prove ownership, and proposed a once-per-process probe — executed in the lock file's own directory, not `/tmp` — that compares `fstat`-open vs `lstat`-after-close and skips dev/ino validation when they disagree. Electricitysheep offered only workarounds and cross-referenced discussion #556 (Windows lefthook YAML UTF-8).

## Root cause

`acquireInstallLock` uses **file identity (`dev` + `ino`) as the lock's ownership credential across a close boundary**, taking one side of the comparison from `fstatSync` on the open descriptor (`scripts/install-lefthook.mjs:391`) and the other from `lstatSync` on the path after the descriptor closes (`:400`). POSIX guarantees that `fstat` and `lstat` agree on `st_ino` for the same file, but macOS's exFAT driver does not honor that guarantee: it hands out a synthesized placeholder ID while the directory entry is unflushed and a different, on-disk-derived ID afterwards. The comparison at `:405`–`:406` therefore fails unconditionally on that volume, and because the throw at `:408` escapes before `main`'s `try`/`finally` (`:708`, `:825`), the lock file it just created is orphaned — which converts a single failure into a permanent two-state loop between "ownership changed" and "stale lock".

The deeper design fault is that the identity check is **redundant and weaker than the credential the lock already carries**. The `'wx'` exclusive create proves the installer created the file; the `<pid> <uuid>` record proves *which* installer owns it, is already compared at release (`:367`), and is unforgeable by accident. `dev`/`ino` adds no atomicity (both checks are read-then-unlink), collides trivially via inode reuse, is truncated through a lossy `number` above 2^53, and — as this report shows — is not portable. It is the one part of the ownership contract that depends on filesystem semantics the code never established.

## Recommended next steps (concrete and ordered; name the files a fix would touch; state the test/snapshot evidence docs/testing.md would require)

I recommend **deleting the dev/ino credential** rather than the probe-and-degrade design the thread converged on. A probe adds a new failure mode (writing a scratch file into `.git` during `postinstall`), creates two behavior modes that must both be tested, and still leaves the weaker credential in charge on "good" filesystems. Removing the check is smaller, uniform across mounts, and strictly stronger — see F7.

1. **`scripts/install-lefthook.mjs` — `acquireInstallLock` publish path (`:387`–`:410`).** Delete `ownedStat = fstatSync(lockHandle)` at `:391` and the `fstatSync` import at `:6`. Keep `publishedStat = installLockStat(lockPath)` at `:400` and its `isFile()` / `!isSymbolicLink()` guards at `:403`–`:404`; replace the `dev`/`ino` comparison at `:405`–`:406` with `readInstallLock(lockPath) !== ownedRecord`. This makes the publish check verify the same credential the release check already verifies.
2. **`scripts/install-lefthook.mjs` — `releaseInstallLock` (`:359`–`:370`).** Drop the `currentStat.dev !== ownedStat.dev || currentStat.ino !== ownedStat.ino` clauses at `:365`–`:366` and the `ownedStat` parameter; ownership becomes the record comparison at `:367` alone. Update the closure returned at `:410` accordingly. Without this step the bug is not fixed (F5).
3. **`scripts/install-lefthook.mjs` — `EEXIST` wait path (`:411`–`:455`).** Remove the `verifiedStat`/`existingStat` dev/ino recheck at `:420`–`:425` (the incomplete-record handling at `:428`–`:447` already covers torn reads), and re-key `initializingLock` (`:432`–`:442`) on first sighting of an incomplete record instead of on dev/ino so the 1-second window cannot be re-armed forever. Add the `Date.now() >= deadline` check to the remaining `continue` paths at `:414` and `:419` so no filesystem can turn a failure into a hang (F8, F9) — this is what "misconfiguration fails loud" in `CLAUDE.md` requires.
