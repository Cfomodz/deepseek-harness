## What the plugin is

`dsh-background-agents` v0.5.1 by **PerryLink** — Apache-2.0, repo `https://github.com/PerryLink/dsh-background-agents`, npm `dsh-background-agents`, posted Aug 16 2026 in *Show Your Plugins!*, 0 replies at time of reading.

Two halves:

1. **Background agents.** Five model-facing tools — `background_agent`, `bg_message`, `bg_list`, `bg_result`, `bg_stop` — that start and steer *continuable* child agents on the official `ctx.subagents` seam. Progress from each child turn is injected back into the parent as a throttled notice; an idle sweep archives quiet children; a Web sidebar panel renders a `backgroundAgents` session projection.
2. **Team rooms (v0.5.0+).** A `/room` command family plus eight `room_*` tools building persistent multi-agent rooms (members, directed/broadcast message bus, shared task board, shared timeline) persisted in a `team_rooms` storage domain via `@deepseek-ai/dsh-storage-domain`, with cross-member task handoffs routed through the approval seam.

Install line in the post: `dsh plugin --profile web add dsh-background-agents`. That verb is real and documented in-tree — `packages/bundle/README.md:13` ("out-of-tree bundles install into a profile through `dsh plugin --profile <name> add <package>`") — so the post's install instruction checks out.

## What it does well

This is unusually disciplined for a community plugin — it reads like it was written against `AGENTS.md` rather than against the built `lib/`. Specifically:

- **Every tunable is a validated `Config` field with one source of truth.** `DEFAULTS` (`src/index.ts:122-141`) is materialized by the Schemastery schema (`:143-174`) *and* used as the `??` fallback for direct `apply()` callers (`:185-211`), with a comment saying exactly why both exist (`:182-184`). That is the repo's "no hardcoded tunables in plugins" rule honored on both entry paths, which most plugins get half-right.
- **Schema minimums that explain themselves.** `resultMaxChars` min 1 "0 would erase every bg_result answer" (`src/index.ts:148-149`), `idleTimeoutMinutes` min 1 "0 would archive any quiet child on the next sweep pass" (`:152-153`), `idleSweepIntervalMs` min 1 "0 would turn the sweep into a 1ms hot loop" (`:154-155`), `busRetention` min 1 (`:168-169`). Each names the failure the bound prevents rather than restating the bound.
- **Misconfiguration fails loud at the earliest *decidable* point, and only there.** Empty `provider` throws (`src/index.ts:212-214`); a provider that is registered but lacks `prepareContinuable` throws, because it can never serve `background_agent` (`:219-225`); a provider that is merely *absent* logs instead, because it may mount later (`:226-228`). The comment at `:216-218` states that distinction outright. This is the `CLAUDE.md` rule applied with a real judgement call, not copied.
- **Optional seams are gated, so the core still mounts without them.** `ctx.inject(['storageDomain'], …)` for rooms (`src/index.ts:242-257`), `ctx.inject(['sessionProjections'], …)` for the dashboard (`:280-283`), `ctx.inject(['systemPrompt'], …)` for guidance (`:289-308`) — with an explicit info log when rooms are dormant that names the package to add (`:239-241`). Headless assemblies keep the five `bg_*` tools. This mirrors `packages/todo/tool-todo/src/index.ts:135-149` exactly.
- **The structured fact channel is kept separate from the model-visible channel on purpose.** `src/events.ts:10-17` states that the dashboard folds `background-agents/fact` records "so dashboard facts never depend on parsing human-readable text back apart", and `src/lifecycle.ts:234-236` re-states it at the write site. Both channels are written for the same event (`src/lifecycle.ts:220-236`). Deliberately refusing to re-parse your own prose is a good call and rarely made.
- **The event is a properly typed, tagged union declared by merging.** `src/events.ts:26-57` is a five-arm union discriminated on `kind`, merged into `SessionEventMap` at `:59-63` against `@deepseek-ai/dsh-session/types` — which is a real export subpath (`packages/core/session/package.json` → `"./types"`).
- **Real concurrency thought at the cap.** `background_agent` takes a per-parent critical section so two concurrent starts cannot both pass the `maxBackgroundAgents` check (`src/tools.ts:314-322`), releases in `finally`, and reclaims the map slot only when its own gate is still the tail (`:364-369`) so parent ids do not leak for the fiber's lifetime.
- **Failures are contained per item, never per pass.** Progress-report failure cannot disturb the child's committed turn (`src/index.ts:266-271`); one archive failure never skips a sibling (`src/lifecycle.ts:313-318`); a sweep pass failure never kills the interval (`:375-379`). Every `catch` logs what it swallowed.
- **`stateVersion` is declared on both projections** (`src/projection.ts:268`, `src/room/projection.ts:253`), which is what lets the projection registry refuse an incompatible re-registration instead of silently sharing cells (`packages/session/session-projection/src/index.ts:205-211`).
- **The idle sweep does not archive a child that is mid-turn**, with the reason stated: a long tool execution emits no session events and would otherwise read as idle (`src/lifecycle.ts:246-247`, guard at `:258`).
- **Tool descriptions are written for the model, including the failure semantics.** `bg_message` tells the model the call returns no answer and that "A failure means the message was NOT delivered" (`src/tools.ts:376-381`), and `presentationMeta` is a pure function of `args`/`value` (`:293-298`) per the UI-render-intent rule.
- **System-prompt sections steer the model away from busy-polling** `bg_list` / `room_read` (`src/index.ts:289-308`) — the failure mode this class of plugin usually ships with.
- **Eight test files** including an integration spec and a manifest spec, and the explicit-route path is pinned (`tests/tools.spec.ts:271`, `:294`).

## Findings

### 1. CONFIRMED — the default "inherit the parent's route" path is exposed to the [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470) stale-route defect, and the *continuable* shape makes it stickier than usual

This is the one finding I think is worth the author's time.

**Plugin side.** `background_agent` builds `agentOptions` **only** when `childProvider` or `childModel` is configured, and otherwise omits the key entirely:

- `src/tools.ts:340-345` — `agentOptions` is `undefined` unless `config.childProvider !== undefined || config.childModel !== undefined`.
- `src/tools.ts:346-358` — the `startContinuable` request spreads it conditionally: `...(agentOptions !== undefined ? { agentOptions } : {})` (`:355`).
- The documented intent is inheritance: `README.md:30` — "children inherit the parent's route; `childProvider`/`childModel` override" — and `README.md:89-90` marks both config fields *(inherit)* by default. `src/index.ts:91-94` says the same in the `Config` JSDoc.

**Harness side, at `master @ 47f943859` (i.e. what a released `dsh` does).** With `request.agentOptions` absent, the route comes from the parent's **creation-time** `AgentOptions`, not from the route the parent's requests are actually using:

- `packages/subagent/subagent/src/continuation.ts:444` — `agentOptions: resolveChildAgentOptions(parent, request.agentOptions, childDepth)`.
- `packages/subagent/subagent/src/child-agent.ts:68-83` — the resolver; `:73-75` reads `parent.options.provider` / `parent.options.model` / `parent.options.maxTokens`.
- `packages/core/agent/src/runtime-types.ts:67-68` documents `Agent.options` as "the provider route and model this agent's requests use", which is what makes this look correct and is very likely why it was written this way. Under a Web host it is the deployment default captured at create/resume: `packages/host/apiproxy/src/api-proxy.ts:1111-1115` ("The seed model each create/resume declares"), call sites `:1659` (resume), `:1672` (create).
- The **live** route is the `agent/request` waterfall result, which is what dispatches and what is logged as `request/header` (`packages/core/agent-loop/src/agent.ts:437-472`), readable at `packages/core/session/src/index.ts:670`. The Web model picker writes only that layer, never `agent.options` (`packages/core/agent/src/model-selection.ts:54-70`; `packages/host/apiproxy/src/api-proxy.ts:1154-1180`, `:2314`).

So on a released `dsh`, after a user switches model in the Web picker, a `background_agent` started from that session runs on the route the session had **when it was created**, not the one the sidebar shows.

**Why this plugin is a sharper case than one-shot delegation.** Because `background_agent` starts *continuable* children, the resolved route is also frozen into the durable descriptor and re-applied on every cold resume, so the divergence outlives the process that caused it:

- `packages/subagent/subagent/src/continuation.ts:413-414` — `agentProvider` / `agentModel` snapshot `request.agentOptions?.… ?? parent.options.…`; stored on the descriptor at `:419-420`.
- `packages/subagent/subagent/src/continuation.ts:919-922` — a cold resume rebuilds `agentOptions` from that persisted descriptor.
- No model selection is installed on a child, so a child has no tier that could recover the correct route from its own log; a grandchild then inherits the child's now-wrong `options` faithfully.

**Why it is not only a model-choice question.** The `provider` string selects the credential and endpoint as well as the model: each route resolves its own `apiKeyEnv` and base URL (`packages/llm/llm-deepseek/src/index.ts:184`, `:225-245`, `:256`; pi-ai at `packages/llm/llm-pi-ai/src/index.ts:175-197`), and the repo names the consequence in its own comment — "billing another tenant for a request the deployment meant to authenticate differently" (`packages/llm/llm-pi-ai/src/index.ts:180-184`). In a single-provider deployment this is a wrong tier; in a multi-provider one it is a wrong account.

**This is a harness defect, not a plugin defect** — the plugin is using the documented seam exactly as documented, and the misleading JSDoc at `packages/core/agent/src/runtime-types.ts:67-68` is the proximate cause. Upstream reports: [#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581) (6 replies, carries a candidate patch), [#1472](https://github.com/deepseek-ai/deepseek-harness/discussions/1472), [#2006](https://github.com/deepseek-ai/deepseek-harness/discussions/2006), [#2053](https://github.com/deepseek-ai/deepseek-harness/discussions/2053), [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470). No upstream issue or PR was open for it when this fork last searched.

**The plugin already ships the mitigation**: setting `childProvider` / `childModel` (`src/index.ts:91-94`, `src/tools.ts:340-345`) makes the route explicit and takes the parent's snapshot out of the picture entirely. What is worth the author's time is that the README's *(inherit)* default currently promises the live route and delivers the creation snapshot on every released `dsh` — a documentation-level note, or making the explicit route the recommended setting for multi-provider deployments, would cover users until the harness side moves.

### 2. CONFIRMED — registrations are effects, done correctly, including the two cases that needed an explicit `ctx.effect()`

The plugin drops the disposer from `ctx.tools.register(…)` (`src/tools.ts:222`, `:374`, `:442`, `:594`, `:694`; `src/room/tools.ts:105`–`:553`) and from `sessionProjections.register(…)` (`src/index.ts:281-282`). That is correct here, because both registries are already effect-scoped to the calling context:

- `packages/core/tools/src/index.ts:1057-1061` — `register()` returns `this.layers.effect(this.ctx, …, { label: 'tools.register()' })`, documented at `:1030-1035` as "the exact disposer that unregisters the tool".
- `packages/session/session-projection/src/index.ts:213-221` — the registration is likewise created inside an effect and returns its disposer.

Where the harness does *not* own the effect, the plugin adds one:

- `src/index.ts:276` — `ctx.effect(() => startIdleSweep(…), 'dsh-background-agents: idle sweep')`, whose factory returns `() => { clearInterval(timer) }` (`src/lifecycle.ts:374-381`).
- `src/index.ts:248` — `roomCtx.effect(() => registerRoomCommand(roomCtx, hub) ?? (() => {}), 'dsh-background-agents: /room command')`.

Listeners are `ctx.on('session/event', …)` (`src/index.ts:261`) and `roomCtx.on('agent/session-start', …)` (`:252`); both are real harness events (`packages/core/session/src/index.ts:76`; `packages/core/agent-loop/src/index.ts:567`). The `session/event` handler is a global firehose (`packages/core/scope/src/scoped-events.generated.ts:27` maps it to `null`), and the plugin's first statement filters to tracked children only (`src/index.ts:262-263`), so the cost on untracked sessions is one map lookup.

### 3. CONFIRMED — durable state does not create a second writer, so the `seq gap` hazard from [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359) does not apply

Everything the plugin persists goes through the harness's own live, in-process objects rather than the session file:

- Parent-log facts: `parent.session.append(FACT_EVENT, …)` at `src/tools.ts:362` and `src/lifecycle.ts:236`, `:288`; room facts at `src/room/hub.ts:487`, `:662`.
- Model-visible deliveries: `parent.inject(…)` / `parent.followup(…)` (`src/lifecycle.ts:229-232`, `:260-275`; `src/room/hub.ts:496`, `:533`, `:695`) — real `Agent` methods (`packages/core/agent/src/runtime-types.ts:129`, `:148`).
- Room durable state lives in the harness storage domain, opened once by the hub (`src/room/hub.ts:131`) and closed with the fiber (`src/index.ts:242-249`), not in a plugin-owned file.
- The one persisted-session read is `ctx.get('sessionPersistence')` → `persistence.load(childId)` (`src/tools.ts:670-673`), which is the coordinator's own path — it returns the live snapshot when the session is attached and otherwise takes a serialized reservation (`packages/session/session-persistence/src/coordinator.ts:756-768`).

So there is no plugin-owned append path with its own cursor, which is the mechanism behind the `corrupt session log: seq gap` reports (see this fork's note on [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359): appends are a bare append + fsync at `packages/session/session-persistence-jsonl/src/index.ts:651-677` with an in-memory cursor at `packages/session/session-persistence/src/coordinator.ts:1354-1359`, and no cross-process lock). Nothing here adds to that exposure.

### 4. UNVERIFIED against this checkout — the `{ ignorable: true }` append option

The plugin appends its fact events with a third argument: `session.append(FACT_EVENT, data, { ignorable: true })` (`src/lifecycle.ts:236`, `:288`; `src/tools.ts:362`; `src/room/hub.ts:487`, `:662`), and documents the surface at `ARCHITECTURE.md:16` as "the harness's ignorable-append surface … open at the plugin's pinned baseline".

At `master @ 47f943859` I could not confirm that surface:

- `packages/core/session/src/index.ts:604-607` — `append<T>(type, data, ...opts)` accepts a third argument only when `T extends SurfaceEventType`, and its type is `SurfaceIntent` (`packages/core/session/src/types.ts:380`), whose fields are `sourceEventSeqs` / `surfaceOp`.
- `ignorable?: true` does exist on the event envelope (`packages/core/session/src/types.ts:405-422`) and is validated (`packages/core/session/src/index.ts:226`, `:239`) and round-tripped by the SQLite backend (`packages/session/session-persistence-sqlite/src/schema.ts:58`, `:209`), but **no in-repo caller sets it through `append()`** at this commit.

Since the plugin pins `HARNESS_COMMIT` `8c690c7cf885eeca723bbe46bd0502ecaddb3b12` (not an ancestor here) and declares `dshVersions: ["0.1.0-rc.6"]` (`package.json:82-86`) while this checkout is on the rc.5 lineage, **the most likely explanation is that our checkout lags the API the plugin targets**. I am recording this only so nobody reads it as verified either way; it is not a defect claim, and I would not raise it with the author without a newer harness in hand.

### 5. CONFIRMED — clean on credentials, network, and runtime code fetching

A repo-wide scan of `src/` for `fetch(`, `XMLHttpRequest`, `child_process`, `execSync`, `spawn(`, `new Function`, `eval(`, dynamic `import(`, `require(`, `process.env`, and credential/token/API-key reads returns **no hits** (the only matches are the word `token` used for command-line word splitting in `src/room/commands.ts:37-66`). Nothing fetches, executes, or self-updates at runtime.

`cordis.patch.yml` inserts only harness-owned storage rows plus its own plugin row, and its single `!!js` use is `dshHomePath('storages')` under a plugin `config` key (`cordis.patch.yml:25`) — the allowed form per `CLAUDE.md` (`!!js`, never `!js`, under plugin `config`).

The one thing a reader should know rather than assume: **`lib/` is committed and is what runs** (`cordis.patch.yml:16`, `package.json:29-43`). This scan covers `src/` only.

### 6. CONFIRMED, minor — the live tracked-children registry is not rehydrated on restart

`BackgroundAgentLifecycle` is populated in exactly two places: at `background_agent` start (`src/tools.ts:359`) and when `bg_message` re-registers a child (`src/tools.ts:436`). Nothing repopulates it at profile start or on `agent/session-start`. Since `reportProgress` and the idle sweep both key off that map (`src/index.ts:262-263`; `src/lifecycle.ts:307`), after a DSH restart an existing background agent's `autoReport` progress lines and idle archiving stay off until a `bg_message` re-registers it.

This looks deliberate and is documented — `src/lifecycle.ts:5-7` says the module "is a cache, never a second source of truth, so losing it only costs throttles and timers" — and the durable dashboard facts are unaffected because they live in the parent log. Noting it only because "recover after restarts" is the plugin's headline claim, and a user may reasonably expect the progress stream to resume by itself rather than after the next `bg_message`.

先说好话：这是我在社区插件里见过写得最扎实的一个，源码和 ARCHITECTURE.md 都放出来了，才让人读得动。

下面是我读代码时注意到的几点，仅以社区成员身份分享。我不代表项目方，这些都不是请求。

**做得好的地方**

- 配置纪律非常好。一个 `DEFAULTS` 常量同时喂给 Schemastery schema 和 direct-`apply()` 的兜底（`src/index.ts:122-141`、`:143-174`、`:185-211`），两边不可能漂移；而且每个下界都写清了它挡住的是什么故障 —— `resultMaxChars` 最小 1，"0 会抹掉每一条 bg_result 答复"（`:148-149`）；`idleSweepIntervalMs` 最小 1，"0 会把 sweep 变成 1ms 热循环"（`:154-155`）。
- 加载期校验把两种情况分开了：**已注册但不支持 continuable** 的 provider 直接抛（它永远服务不了 `background_agent`），而**尚未注册**的 provider 只打日志（它可能稍后才挂载）（`src/index.ts:216-228`）。这个区分两个方向都很容易做错。
- 把结构化 fact 通道和模型可见的 notice 通道分开，让 dashboard 永远不用把自己写的自然语言再解析回来（`src/events.ts:10-17`），是个好决定，而且少见。
- `maxBackgroundAgents` 检查外面的 per-parent 临界区，加上"只有当自己的 gate 还是队尾时才回收 map 槽位"（`src/tools.ts:314-322`、`:364-369`），是真的在想并发，而不是事后补一把锁。
- 小细节但值得一提：`bg_message` 的描述里那句 "A failure means the message was NOT delivered"（`src/tools.ts:376-381`），正好能拦住模型默认"发出去就成功了"。

**有一点可能值得知道，因为它正好落在你的默认路径上**

`background_agent` 只在配置了 `childProvider`/`childModel` 时才传 `agentOptions`，否则整个键都不传（`src/tools.ts:340-345`、`:355`），也就是走继承路径 —— 也正是 `README.md:30` 和 `:89-90` 描述的"继承父 agent 的路由"。

问题在于：在已发布的 `dsh` 上，这个继承读的是父 agent **创建时刻**的 `AgentOptions`，而不是父 agent 的请求实际在用的路由。按 `master @ 47f943859` 逐行看：`startContinuable` 调用 `resolveChildAgentOptions`（`packages/subagent/subagent/src/continuation.ts:444`），后者取的是 `parent.options.provider` / `.model`（`packages/subagent/subagent/src/child-agent.ts:73-75`）。而在 Web host 下，这两个值是在 create/resume 时刻从部署默认值播种的（`packages/host/apiproxy/src/api-proxy.ts:1111-1115`、`:1659`、`:1672`）；Web 的模型选择器只写请求层，从不更新 `agent.options`（`packages/core/agent/src/model-selection.ts:54-70`；`packages/host/apiproxy/src/api-proxy.ts:1154-1180`、`:2314`）。真正生效的路由是 `agent/request` waterfall 的结果，也就是写进日志的 `request/header`（`packages/core/agent-loop/src/agent.ts:437-472`，可通过 `session.requestHeader()` 读取，`packages/core/session/src/index.ts:670`）。

净效果是：用户在 Web 里切换模型之后，从该会话启动的 `background_agent` 跑的是会话**创建时**的路由，而不是侧边栏显示的那个。

有两个细节让它对 continuable 子 agent 比对一次性委派更难受：

- 解析出的路由会被固化进持久化 descriptor（`packages/subagent/subagent/src/continuation.ts:413-414`，存储于 `:419-420`），并在每次冷恢复时重新套用（`:919-922`），所以它比产生它的那个进程活得更久。子 agent 上没有安装 model selection，因此它自己没有任何一层能从自己的日志里把正确路由找回来。
- `provider` 决定的不只是模型，还有凭据和端点 —— 每条路由自带 `apiKeyEnv` 和 base URL（`packages/llm/llm-deepseek/src/index.ts:184`、`:225-245`、`:256`）。harness 自己在注释里就写过这个后果："billing another tenant for a request the deployment meant to authenticate differently"（`packages/llm/llm-pi-ai/src/index.ts:180-184`）。单供应商部署顶多是用错档位；多供应商部署就是静默记到了另一个账户上。

必须说清楚：这不是你的插件写错了 —— 你完全是按接缝自己的 JSDoc 在用（`packages/core/agent/src/runtime-types.ts:67-68` 至今仍把 `Agent.options` 描述为 "the provider route and model this agent's requests use"，我想大家都是这么被带过去的）。上游已有报告：[#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581)（带候选补丁）、[#1472](https://github.com/deepseek-ai/deepseek-harness/discussions/1472)、[#2006](https://github.com/deepseek-ai/deepseek-harness/discussions/2006)、[#2053](https://github.com/deepseek-ai/deepseek-harness/discussions/2053)、[#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470)；据我查到的，目前还没有对应的 issue 或 PR，所以已发布的 `dsh` 仍是这个行为。

我觉得值得一提的原因是：**你其实已经把出口做好了** —— 设置 `childProvider`/`childModel` 就把父 agent 的快照彻底排除在外了。所以这可能只是个 README 的事：目前 *(inherit)* 这个默认承诺的是活动路由，实际给的是创建时刻的种子。对跑多供应商的人来说，显式设置就是"用错模型"和"记错账单"之间的差别。

**另外两点小观察，供参考**

- 被跟踪子 agent 的 map 只在 `background_agent` 启动（`src/tools.ts:359`）和 `bg_message`（`:436`）时写入，profile 启动时没有任何回填。你自己的注释说它是缓存，丢了"只损失节流和定时器"（`src/lifecycle.ts:5-7`），这没错 —— 但因为 `autoReport` 和 idle sweep 都以这个 map 为准（`src/index.ts:262-263`、`src/lifecycle.ts:307`），DSH 重启之后，已有子 agent 的进度流会一直静默，直到有人给它发一条 `bg_message`。既然"跨重启恢复"是主打卖点，用户可能会期待它自己恢复。
- `lib/` 提交进仓库（`cordis.patch.yml:16`）对安装很方便，但也意味着实际运行的东西和读者审阅的东西不是同一份。我只读了 `src/`。

我读的插件是 `main`，harness 侧对照的是 `master @ 47f943859`（0.1.0-rc.5 这一支）—— 你 pin 的是 `HARNESS_COMMIT 8c690c7c` 并声明 rc.6，所以我比你旧；如果上面哪条在 rc.6 上已经不成立，那是我这边的问题。插件写得很好。
