## What the plugin is

- URL: https://github.com/deepseek-ai/deepseek-harness/discussions/2472
- Title: `dsh-permission-rules: declarative permission rules + process-level network policy for DeepSeek Harness`
- Category: **Show Your Plugins!** · Author: `@PerryLink` · Aug 16, 2026 · **0 replies**
- Source: https://github.com/PerryLink/dsh-permission-rules · npm `dsh-permission-rules` · Apache-2.0 · read at `main`, `package.json` version **0.5.0**

Two things in one plugin:

1. **A declarative tool gate.** An ordered `allow` / `deny` / `ask` rule list in `<cwd>/.dsh/rules.yaml`, evaluated on the harness's own `tools/pre-execute` waterfall. Match dimensions: `tools` (globs, incl. `mcp__*`), `agents` (`main` / `subagent` / `preset:<name>`), `params` (key → glob/regex, `!` negation), `paths` (workspace-relative globs), `absent` (keys that must be missing), `when` (`env` + `platform`), and `network` (`domains` / `ips` / `ports` / `schemes`). First match wins. Every decision — hits *and* passthroughs — is appended as a log-only `permissionRules/decision` session event.
2. **A network policy.** A built-in local HTTP/CONNECT proxy plus `HTTP(S)_PROXY` / `ALL_PROXY` injection into the harness process environment, so shell subprocesses route through it. Three modes (`deny-all` / `whitelist` / `allow-all`) plus `auto`, which maps the official sandbox preset onto them.

Supporting surfaces: `/rules` (`list | reload | network | decisions [n] | test [flags] <tool> <json>`), a Web settings section, Chokidar hot reload, `enforce: false` dry-run, and `scripts/repair-session-logs.mjs`.

## What it does well

This is the most carefully-built community plugin I have read against this codebase. Concretely:

1. **It enforces at the harness's own gate, not beside it.** `apply()` registers `ctx.on('tools/pre-execute', …)` (`src/runtime.ts:1149`). That waterfall is not a facade — `docs/subsystems/tools.md:172` places it inside `ctx.tools.execute()`, before guards and before dispatch, and `packages/core/tools/README.md:57` names it "the reorderable allow/deny/ask gate". Every model-issued tool call reaches it, including Code Mode sub-dispatches, which "run through the complete pre-execute → guards → execute → post-execute → result pipeline" (`packages/core/tools/README.md:123`). For tool calls this satisfies `packages/AGENTS.md`'s "enforce a decision in the operation that makes it".
2. **`ask` rides the real approval seam and fails closed.** The plugin returns `{ kind: 'ask' }` and stops (`src/runtime.ts:312-314`); it never answers its own question. `packages/core/tools/README.md:49` and `docs/subsystems/tools.md:381-382` confirm `ask` executes only after an approval service returns `allowed-once` and otherwise denies. `SECURITY.md` states the same scope: "it never runs subagents or models".
3. **It composes with the shipped sandbox instead of shadowing it.** It mounts no filesystem, shell, or terminal provider — `cordis.patch.yml` inserts exactly one root entry. It reads the sandbox policy *optionally* via `this.ctx.get('sandboxPolicy')` (`src/runtime.ts:436`), matching `packages/AGENTS.md`'s "Optional services use `ctx.get(name)`", and degrades to `network.autoFallback` when absent. This is the opposite of the composition defect in [#2422](https://github.com/deepseek-ai/deepseek-harness/discussions/2422) / [#523](https://github.com/deepseek-ai/deepseek-harness/discussions/523), where a preset replaced the enforcing provider.
4. **It is the one layer that currently reaches the `minimal`-preset editor.** `apps/cli/config/agent-presets/minimal/agent.cordis.yml:48-62` isolates only `fs`, and `:18-22` only `terminals`; the tool registry stays the host's, and plain-context pre-execute listeners receive every agent's calls (`docs/subsystems/tools.md:681` — only *agent-scoped* listeners are filtered). So a rule can deny a `str_replace_editor` call that `dsh-fs-sandbox` never sees, because in that preset `ctx.fs.sandboxMode` is `undefined` (`packages/fs/fs/src/index.ts:103`) and the tool's whole policy is gated off (`packages/fs/tool-str-replace-editor/src/index.ts:66-73`). See Finding 1 for the caveat on *how* to write that rule.
5. **The session-log discipline is exactly right, and better than most first-party code would manage from outside.** `src/events.ts:36-88` uses `declare module '@deepseek-ai/dsh-session/types'` declaration merging — the repo's stated mechanism. The event is log-only and never enters model context, while the model-visible deny reason carries the same `callId` (`src/events.ts:1-7`), so "model-visible ⟺ logged" holds. And the `ignorable` handling is precisely correct for this tree: `packages/session/session-persistence/src/coordinator.ts:1063-1064` refuses to interpret a log containing an unknown event type not marked ignorable, and at this commit `Session.append` has **no writer surface for the marker at all** on non-surface events (`packages/core/session/src/index.ts:604-607` — the optional third argument exists only for `SurfaceEventType` and is a `SurfaceIntent`). The plugin detects that (`isUnmarkedHostVersion`, `src/runtime.ts:1184-1188`, plus an envelope probe at `:404-413`), disables session-log audit with a one-time warning, and ships a repair script. On this exact checkout that degrade path is the one that fires. Credit to `@22xuan` for the original report ([#2](https://github.com/PerryLink/dsh-permission-rules/issues/2)).
6. **Every tunable is a validated `Config` field**, defaulted twice — Schemastery (`src/config.ts:157-185`) and a `resolveConfig` pass that re-checks bounds so a plain-JS mount cannot slip past (`:197-287`). Deployment-level file references are validated at mount, not at first use (`src/runtime.ts:913-935`), which matches "misconfiguration fails loud at the earliest resolvable point".
7. **Registrations are effects with disposers.** Watchers, debounce timers, the proxy, and the env injection each go through `ctx.effect()` (`src/runtime.ts:962-970`, `:1050-1058`, `:557-560`, `:565-570`); `ctx.on`, `ctx.provide`, `ctx.plugin`, and `ctx.commands.register` dispose with the fiber. `pruneWatchers`/`evictIfFull` bound long-running hosts.
8. **`allow` and passthrough always delegate via `next()`** (`src/runtime.ts:329`), so it never short-circuits a downstream listener — the waterfall contract most plugins get wrong.
9. **Dry-run (`enforce: false`) records the would-be action alongside the actual downstream outcome** (`src/runtime.ts:306-310`, `src/events.ts:9-17`). That is the right way to roll a policy out, and the audit record stays honest about what actually happened.
10. **The network layer fills a real gap.** `packages/sandbox/sandbox/src/index.ts:24-27` states outright that "Network and process visibility are outside this vocabulary" — the shipped sandbox confines file effects only. So the plugin's own framing ("network interception is entirely this plugin's job", `src/proxy.ts:9-11`) is accurate, and `scrubbedParentEnv()` explicitly preserves proxy variables into every child (`packages/subprocess/subprocess/src/index.ts:46-64`), so the mechanism does reach shipped shell subprocesses.

## Findings

Ordered by how much they would change what a user believes the plugin guarantees. None is an exploit; all are read from source.

### 1. CONFIRMED — `paths` rules cannot address anything outside the workspace, including the shipped baseline's `**/.ssh/**`

`matchPaths` normalizes every candidate through `normalizeWorkspacePath` and then **drops empty results, returning `false` when none survive**:

```ts
// src/rules.ts:537-543
const candidates = extractPathCandidates(args)
  .map(candidate => normalizeWorkspacePath(cwd, candidate, caseInsensitive))
  .filter((candidate): candidate is string => candidate.length > 0)
if (candidates.length === 0) return false
```

and `normalizeWorkspacePath` returns `''` for any absolute path not under the root (`src/rules.ts:1123-1127` → `relFromRoot`, `:1131-1140`). This is documented in the JSDoc (`src/rules.ts:1097-1105`) and in the README's "Security boundaries" section, so it is not hidden — but two consequences deserve stating plainly, because a reader of the *rule file* would not expect them:

- **The shipped 5-rule security baseline is narrower than it reads.** `docs/rules-format.en.md:66-71` recommends `paths: ["**/secrets/**", "**/.env", "**/*.pem", "**/*.key", "**/.ssh/**"]` with no `tools` restriction. For a session whose workspace is a project directory, `~/.ssh/id_rsa`, `~/.aws/credentials`, and `/etc/*` all normalize to `''` and the rule does not fire. Inside the workspace it works as written.
- **It is the wrong dimension for the `minimal`-preset case** (the "does well" item 4 above). `str_replace_editor` "requires absolute paths" (`apps/cli/config/agent-presets/minimal/agent.cordis.yml:47`), and the interesting writes are the out-of-workspace ones ([#523](https://github.com/deepseek-ai/deepseek-harness/discussions/523) reports `C:\Users\Public\Documents\…`). A `paths` rule cannot express that.

**The `params` dimension can.** `matchParams` (`src/rules.ts:502-512`) tests raw argument values through `scalarCandidates`, with no workspace normalization, so `params: { path: ["!/repo/**"] }` or a `patternMode: regex` equivalent does express "not under the workspace". That is a documentation gap more than a code gap — a "deny writes outside the workspace" recipe in `docs/rules-format.*.md` would be high-value, since it is the single most-requested rule in the sandbox threads.

### 2. CONFIRMED — the proxy layer ignores the `agents` dimension, and its own JSDoc says otherwise

`decideNetworkTarget` evaluates `enabled` → `network !== undefined` → `matchToolsProxy` → `when` → `targetMatchesNetwork` (`src/network.ts:109-125`). `rule.agents` is never consulted, and `matchAgents` is not among the imports at `src/network.ts:11`.

The JSDoc directly above says the opposite: *"Agent identity is unknown at the proxy, so agent-scoped network rules fail closed there"* (`src/network.ts:94-97`). The intended behavior is reachable — `options.context` defaults to `{}` (`:108`), and `matchAgents` returns `false` for empty candidates by design (`src/rules.ts:494-499`) — it is simply not called.

Effect on a rule like `{ match: { agents: ["preset:research"], network: { domains: ["*"] } }, action: allow }`: at `tools/pre-execute` it correctly fires only for that preset, but at the proxy it fires for **every** subprocess connection. For a `deny` rule the mismatch over-blocks instead; for an `allow` rule it over-permits. A one-line `if (rule.agents.length > 0) continue` in that loop would make the code match the comment.

### 3. CONFIRMED (mechanism) — "process-level network policy" is proxy-environment steering, which is a control, not a boundary

`injectProxyEnv` sets `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` (plus lowercase) on `process.env` and, by default, blanks `NO_PROXY` (`src/proxy.ts:302-312`). Children inherit them because `scrubbedParentEnv()` deliberately preserves proxy variables (`packages/subprocess/subprocess/src/index.ts:46-64`). Nothing else constrains a subprocess's sockets.

So the policy holds for clients that honor proxy environment variables — curl, wget, git-over-HTTPS, pip, npm, most SDKs — which is genuinely most agent traffic, and the plugin's block message is designed to be read back by the model (`src/network.ts:158-177`). It does not hold for a subprocess that opts out (`curl --noproxy '*'`, `git config http.proxy ''`), for non-HTTP protocols the proxy does not speak (SSH, DNS, raw TCP), or for a program that dials a socket directly. The README's comparison to Codex invites reading it as an OS-level boundary; the module doc at `src/proxy.ts:1-14` is already the honest version. Aligning the README's headline with that paragraph — "a policy proxy for proxy-aware clients", not "process-level" — would prevent the misread. Two supporting notes:

- **`run_code` is entirely outside it.** Code Mode programs run in a worker whose environment is `env: {}` by construction (`packages/code-runtime/code-runtime-worker-thread/README.md`, "Empty environment"), and the same README states the trust posture is "bash-equivalent by design" with full Node built-ins. Tool *bindings* from inside a program do re-enter the pipeline and are covered; the program body's own `node:http` / `node:fs` use is not, by either the rules or the proxy. Worth one line under "Known limitations", since `run_code` is reachable via `DSH_TOOLS_MODE` (`packages/bundle/web-app/cordis.patch.yml:35-39`, `packages/bundle/headless/cordis.patch.yml:17-20`).
- **DNS is re-resolved after the decision.** `decideWithResolution` resolves the host and decides on the returned addresses (`src/proxy.ts:232-243`), then `handleConnect` dials `connect(port, target.host)` by name (`:199`), so the kernel resolves again. `ips` / CIDR rules therefore decide on one answer and connect on another. `domains` rules are unaffected. This is the standard limitation of hostname-based proxy filtering, not a defect unique here, but it belongs next to the `ips` documentation (`src/rules.ts:139-146`).

### 4. CONFIRMED — the env injection is process-wide and permanent while mounted, affecting every harness subprocess

`injectProxyEnv` mutates the harness's own `process.env`, so it applies to *all* children of the harness, not only model-issued shell calls: ripgrep behind `glob`/`grep` (`packages/fs/tool-fs-search`), LSP servers, MCP stdio servers, and any git the harness runs. `noProxy: 'clear'` (the default) additionally blanks a user's corporate `NO_PROXY` process-wide.

For context on how the harness treats those names: `packages/boot/app-boot/src/index.ts:111` lists `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` under "Network reach and trust" as **bootstrap-only** — a discovered `.env` file may not set them; only the inherited process environment may. A plugin overwriting them at mount is not covered by that guard, but the classification shows the harness considers them process-bootstrap state. Documenting the blast radius (and that `network.injectEnv: false` opts out) would set expectations correctly.

### 5. CONFIRMED — `this.envRestore` is nulled synchronously by its own effect, so `onNetworkConfigChanged()`'s restore step is a no-op

```ts
// src/runtime.ts:563-570
this.envRestore = injectProxyEnv(port, cfg.noProxy)
this.ctx.effect(() => {
  const restore = this.envRestore
  this.envRestore = undefined        // runs immediately
  return () => restore?.()
})
```

Cordis executes an effect body synchronously at registration (`vendor/cordis/src/fiber.ts:522`, `task = this._execute(runner)`), so `this.envRestore` is `undefined` the moment `attachNetworkProxy` returns. The rebind path then does `this.envRestore?.()` before re-injecting (`src/runtime.ts:586-589`) and that call never fires, so the second `injectProxyEnv` snapshots a `process.env` that already holds the plugin's own previous proxy address as "previous".

**PLAUSIBLE (not verified):** on final unmount the net result may still be correct if fiber disposal is strictly LIFO across the accumulated effects — I did not trace the fiber's own `_disposables` unload ordering. What is certain is that the field is dead, the guard reads as if it were live, and each rebind adds one more proxy-close effect and one more env-restore effect that are only released at unmount. Holding the restore in a local and disposing the previous `ctx.effect` handle explicitly would make the intent match the behavior. Reachable only through a live settings change to `proxyPort` / `proxyBind` / `injectEnv` / `noProxy` (`src/settings.ts:64-72`).

### 6. CONFIRMED — globs are anchored, so the shipped baseline's command rules match fewer commands than they appear to

`compileGlob` returns `new RegExp('^' + out + '$', …)` (`src/glob.ts:110`). So `command: ["rm -rf*"]` compiles to `^rm -rf.*$` and matches only a command that *starts* with `rm -rf`. In the shipped baseline (`docs/rules-format.en.md:56-64`, `:72-87`), `rm -rf*`, `npm publish*`, and `git push*origin main*` therefore do not fire for `cd build && rm -rf *`, `sudo rm -rf /`, or `pnpm -C pkg npm publish`. Leading-`*` variants work and stay inside `maxGlobStars: 2`. This is worth fixing in the recommended baseline specifically, because that file is what most users will copy verbatim.

More generally, textual command matching is inherently approximate against a model that can rephrase — Claude Code has the same property, the plugin's own README says "Policy, not a kernel", and I am not suggesting otherwise. The anchoring detail is the part a user cannot infer from the YAML.

### 7. PLAUSIBLE — deployment-varying tool names are hardcoded rather than `Config` fields

`packages/AGENTS.md`'s "No hardcoded tunables in plugins" applies to choices that vary by deployment. Three lists qualify:

- `WEB_TOOLS = ['web_fetch', 'web_search']` (`src/runtime.ts:71`) drives the network mode-default gate for tool calls. An MCP fetcher or a custom web tool gets no mode default.
- `isShellTool()` returns true only for `bash` / `pwsh` (`src/rules.ts:839-841`). It controls URL scanning of command text and proxy attribution. `dsh-tool-terminal` ships `terminal_send`, whose command text is in a `text` argument (`docs/tool-catalog.md`, `terminal_send` schema), so terminal commands are not URL-scanned at pre-execute. An explicit `params: { text: … }` rule still works, and the proxy still adjudicates the resulting connection, so this narrows detection rather than opening a hole.
- `PATH_CANDIDATE_KEYS` / `URL_CANDIDATE_KEYS` / `COMMAND_CANDIDATE_KEYS` (`src/rules.ts:29-46`, `:765-780`) are fixed. They do cover the shipped tools I checked — `str_replace_editor` uses `path`, `tool-fs` uses `file_path`, `glob`/`grep` use `path`, `terminal_open` uses `cwd`, `web_fetch` uses `url` — but an MCP server with `target_file` or `destination` contributes nothing to `paths`. The README flags this as heuristic; exposing the lists as config would let a deployment close the gap without a plugin release.

`IN_FLIGHT_TTL_MS` (`src/runtime.ts:74`) and `MAX_ARGUMENT_DEPTH` (`src/rules.ts:52`) are the same class but far lower stakes.

### 8. PLAUSIBLE (theoretical for the shipped stack) — an earlier pre-execute listener could allow past the rules

`tools/pre-execute` is explicitly "reorderable" (`packages/core/tools/README.md:57`). A listener registered ahead of this plugin that returns `{ kind: 'allow' }` without `next()` would short-circuit the rules. I checked the shipped listeners: `packages/hooks/hooks-claude-code/src/index.ts:238-244` and `packages/hooks/hooks-codex/src/index.ts:225` both `return next()` when their hooks do not block, so nothing in the shipped tree does this today. `deny` decisions are unaffected in the other direction — once this plugin returns `deny`, downstream cannot re-allow.

For a *deny* that must survive arbitrary listener ordering, the harness offers `ctx.tools.guard()`: monotonic, evaluated after the whole waterfall, and "no guard can force-allow a call another guard denied" (`docs/subsystems/tools.md:516-525`). Mirroring hard denies onto a guard would make the plugin's `deny` order-independent. `ask` cannot move there (guards have no ask result), so the waterfall remains the right home for `ask`.

### 9. CONFIRMED (minor, documentation) — `SECURITY.md` says the plugin makes no network requests

`SECURITY.md`'s Scope paragraph reads *"it never runs subagents or models, makes no network requests, and never changes OS-level sandbox policy."* The first and third clauses hold. The second no longer does since the network layer landed: `src/proxy.ts:169` forwards plain HTTP upstream via `http(s).request`, `:199` opens TCP tunnels for CONNECT, and `:235` performs DNS lookups. The README's permissions table already declares `network:outbound`, so this is just the one file lagging.

### 10. UNVERIFIED — everything about runtime behavior

I did not install, mount, or run the plugin, and did not read its test suite. No claim above rests on observed behavior; all of it is source reading plus the local harness checkout.

But the mechanism reaching subprocesses is `HTTP(S)_PROXY` / `ALL_PROXY` on `process.env` (`src/proxy.ts:302-312`, inherited because `scrubbedParentEnv()` preserves proxy variables — `packages/subprocess/subprocess/src/index.ts:46-64`). That governs proxy-aware clients, which is most agent traffic, but not `curl --noproxy '*'`, not SSH or raw sockets, and not `run_code` programs — the Code Mode worker gets `env: {}` and a documented bash-equivalent trust posture (`packages/code-runtime/code-runtime-worker-thread/README.md`). Two related notes worth a line each: `ips`/CIDR rules decide on a resolved address (`src/proxy.ts:232-243`) but `connect()` re-resolves by name (`:199`), and the injection is process-wide, so it also routes ripgrep, LSP servers, and MCP stdio servers, with `noProxy: 'clear'` blanking a user's `NO_PROXY` for the whole harness process. Worth knowing that the harness itself classifies those four names as bootstrap-only, settable only from the inherited environment (`packages/boot/app-boot/src/index.ts:111`).

> Three quick ones and I'll stop. `src/runtime.ts:563-570` — the effect body runs synchronously in Cordis (`vendor/cordis/src/fiber.ts:522`), so `this.envRestore` is `undefined` before `onNetworkConfigChanged()` can call it at `:586-589`; the restore-then-rebind step never runs. For hard denies, `ctx.tools.guard()` is monotonic and evaluated after the whole waterfall (`docs/subsystems/tools.md:516-525`), so mirroring `deny` there would make it independent of listener order — nothing in the shipped tree short-circuits `allow` today, so this is belt-and-braces. And `SECURITY.md`'s "makes no network requests" predates the proxy.
