# 2549 — dsh-defend

**Thread:** https://github.com/deepseek-ai/deepseek-harness/discussions/2549 — "dsh-defend: prompt-injection, jailbreak and secret-leak detection + a destructive-delete guard for DeepSeek Harness", by PerryLink, Aug 16 2026, category "Show Your Plugins!", no replies at time of reading.

**What was read:** plugin source at `PerryLink/dsh-defend@7ba3427` (branch `main`, Aug 17 2026); harness source at local HEAD `1836115d3`, which contains `47f943859` (v0.1.0-rc.5).

**Verdict in one line.** This is a careful, honest, well-documented plugin whose author already states the right framing themselves ("Detection, not enforcement", `README.md:116`). It fetches nothing at runtime. Its destructive-delete guard genuinely sits in the tool executor — but its default tool list omits `pwsh`, which is the exact tool that carries the PowerShell `Remove-Item -Recurse` commands the plugin was written in response to. That, and a session-log interaction that can make a session unreadable, are the two findings worth sending.

## What the plugin is

A single cordis plugin, `dsh-defend`, shipped as an npm package with a `dsh.bundle.patch` pointing at its own `cordis.patch.yml` (`package.json:42-46`), i.e. installed as a profile bundle layer via `dsh plugin --profile <name> add dsh-defend`.

It contributes four things:

1. **A destructive-delete guard** on `tools/pre-execute`, reviewing the `command` argument of named shell tools (`src/index.ts:407-416`).
2. **A detection layer** — an Aho-Corasick automaton plus per-rule regexes over three rule families — mounted on three seams: `tools/pre-execute` for tool arguments (`src/index.ts:462`), `tools/post-execute` for tool results (`src/index.ts:486`), `agent/pre-step` for inbound messages (`src/index.ts:510`).
3. **A `defend_report` tool** and a **`/defend` command** reading an in-memory ring buffer (`src/index.ts:536-601`).
4. **A `defend/detection` session audit event** (`src/events.ts:15-48`).

Rule counts, verified by reading the library rather than the post: 25 payload rules with author-written ids `ii-/il-/jb-/pl-/rh-001..005` (`src/detect/rules.ts`, five per prefix), plus 25 Jailbreak-Detector phrases expanded to `jd-001..025` (`src/detect/rules.ts:132-146`, 9 + 9 + 7 = 25), plus 12 secret grammars (`src/detect/secrets.ts:31-56`). The post's "25 / 25 / 12" is accurate.

## What it does well

These are not consolation points; several of them are things the plugin gets right that comparable tools get wrong.

- **It fetches nothing at runtime and does not self-update. CONFIRMED.** A grep across every downloaded file for `fetch(`, `http`/`https` module imports, `undici`, `axios`, `got`, `XMLHttpRequest`, `WebSocket`, `child_process`, `spawn`, `execSync`, `node:fs`, `node:net`, catalog fetching and self-update produced exactly two classes of hit: `RegExp.prototype.exec` calls, and the repository/homepage/bugs URLs in `package.json`. The only Node built-ins imported anywhere in `src/` are `node:os` and `node:path` (`src/index.ts:30-31`). There is no `preinstall`/`postinstall` script (`package.json:129-139`). The workshop manifest declares `"permissions": ["session:append", "network:none"]` (`package.json:64-67`), and the claim holds against the source. This is worth saying plainly, because a plugin recommended in these discussions during the [#2385](https://github.com/deepseek-ai/deepseek-harness/discussions/2385) research did the opposite — it pulled its check catalog from the author's GitHub at runtime and could self-update. dsh-defend is the good case.
- **The author does not overclaim.** `README.md:116` — "Detection, not enforcement. The guard and the detection layer only produce deny/ask/block decisions on official seams; the sandbox and approval systems remain the enforcement authorities." `SECURITY.md` — "Bypasses of this detector are detection gaps (false negatives), not vulnerabilities in the harness itself." That is the correct framing, written by the author, before anyone asked.
- **The delete guard is in the right place.** Putting it at `tools/pre-execute` rather than `post-execute` is the difference between preventing a delete and narrating one. See the guarantee analysis below.
- **Fail-closed is real, not decorative.** `ask()` returns `false` when no `approval` service is present (`src/index.ts:451`), and the delete review denies outright when the session workspace is unavailable (`src/index.ts:307-310`). Both are the strict direction.
- **It rides the real approval seam correctly.** `ctx.get('approval')` matches the service name the harness registers (`packages/interaction/user-approval/src/index.ts:198`), and treating only `'allowed-once'` as a grant (`src/index.ts:458`) matches that service's own contract — "`'allowed-once'` is the only grant" (`packages/interaction/user-approval/src/index.ts:253`).
- **Secret handling is disciplined.** Detailed below; the short version is that no matched text reaches any log, event, report, or model-visible string.
- **Optional services are read the way this repo asks.** `ctx.get('approval')`, `ctx.get('tools')`, `ctx.get('commands')` (`src/index.ts:450`, `:534`, `:587`) rather than the property proxy — exactly what `packages/AGENTS.md` prescribes ("Optional services use `ctx.get(name)`").
- **Registrations dispose.** The four listeners are `ctx.on(...)` (fiber-scoped), and the tool and command registrations go through `ctx.effect(...)` with labels (`src/index.ts:585`, `:589`). This matches the repo convention that every contribution goes through `ctx.effect()` / `ctx.on()`.
- **Configuration is validated, not hardcoded.** Every detection-layer knob is a schemastery field with a default (`src/index.ts:79-104`) and is documented inline in the shipped `cordis.patch.yml`.
- **Provenance is tracked honestly.** Rules carry `source: 'ported' | 'extended'` so the upstream-verbatim rows are distinguishable from the author's additions (`src/detect/rules.ts:22-24` doc, `src/detect/secrets.ts:26`), with `THIRD_PARTY_NOTICES.md` and Apache-2.0 attribution.
- **Bounded by construction.** Scan cap on the head of the input, one match per rule, capped match count, ring-buffered report (`src/detect/scanner.ts:64-78`, `src/index.ts:436-437`).

## What guarantee each feature actually provides

### 1. Destructive-delete guard — **ENFORCING**, for the tools it is told to watch

`tools/pre-execute` is not an observer hook. The `ToolRuntime` runs it itself inside `prepareExecution` (`packages/core/tools/src/index.ts:1475-1478`), and a `deny` decision short-circuits into a materialized error result at `packages/core/tools/src/index.ts:1486-1499` — before `dispatchToolBody` is ever reached (`:1503`, `:1532`). So a denial from this listener genuinely prevents the command from running. This is enforcement in the operation that makes the decision, which is what `packages/AGENTS.md` asks for.

Two qualifications, both about *coverage*, not about the mechanism:

- The guard only inspects executions whose `exec.name` is in `toolNames` (`src/index.ts:408`). Everything outside that set passes untouched. See Findings F3/F4.
- Its position at the head of the waterfall comes from `{ prepend: true }` (`src/index.ts:416`), which orders it first only among listeners registered up to that point. A listener registered later with `prepend` that returns without calling `next()` would pre-empt it. This is precisely the "listener order is not enforcement" case in `packages/AGENTS.md`. There is a stronger seam available — see F7.

### 2. Tool-argument scanning — **ENFORCING** as a decision, **ADVISORY** as detection

Same executor path, so a `block` really does stop the call. What it cannot promise is *coverage of intent*: it is a fixed pattern library over the argument text, so it stops the phrasings in the library and nothing else. The author says this outright (`README.md:122`, "Known limitations — Detection gaps").

### 3. Tool-result scanning — **ENFORCING as egress control toward the model**, not as prevention

`tools/post-execute` runs after the tool body has already executed (`packages/core/tools/src/index.ts:1575` dispatch, `:1611` post-execute). So the file was already read, the request already made. What a `block` decision does guarantee is real and useful: the harness replaces the result content wholesale with the plugin's feedback and marks it an error (`packages/core/tools/src/index.ts:1748-1755`), and the agent loop appends only the final returned result to the session log (`packages/core/agent-loop/src/tool-calls.ts:268-289`). So a blocked secret does not enter model history and does not land in the `tool/result` event. That is the strongest guarantee in the plugin.

### 4. Inbound message scanning — **ENFORCING for the messages it sees**, which is a narrower set than "what reaches the model"

`agent/pre-step` runs in the agent loop before the model request, and a `{kind:'reject'}` decision ends the step with the turn marked `blocked` (`packages/core/agent-loop/src/agent.ts:234-243`, `:266-270`). No model request is made. Genuine.

But the payload is `messages: claimed` — the messages claimed from the inbox this step (`packages/core/agent-loop/src/agent.ts:229`, `:235`). The assembled system prompt is built *before* the waterfall (`:230`) and the rendered context is appended by the **default** handler at `:238`, i.e. after every listener. So content that reaches the model via prompt assembly — AGENTS.md/skill text, MCP resources, memory, compaction output — is never scanned by this plugin. If injection-in-project-files is part of the threat model, `system-prompt/assemble` (`packages/core/system-prompt/src/index.ts:31`) is the seam that sees it. The plugin's own `Surface` union already reserves a `'model-output'` member (`src/detect/types.ts:25`) that no listener currently produces, so assistant output is likewise unscanned.

## Findings

### F1 — No runtime rule fetching, no self-update, no subprocess, no disk writes. CONFIRMED

Established by exhaustive grep over the whole downloaded source set (see "What it does well"). The plugin imports only `node:os` and `node:path`. Stating this plainly, because the question is fair to ask of any security plugin and the answer here is clean.

### F2 — `tools/pre-execute` is a real executor seam, so the delete guard enforces. CONFIRMED

`packages/core/tools/src/index.ts:1475-1478` (waterfall), `:1486-1499` (deny short-circuits to a materialized error), `:1503` (only an allowed call reaches dispatch).

### F3 — The `pwsh` tool is not in the default review set. CONFIRMED. Highest-value finding

- The plugin's default is `DEFAULT_TOOL_NAMES = ['bash', 'persistent-bash', 'terminal-bash']` (`src/index.ts:41`), and the shipped `cordis.patch.yml:12` leaves `toolNames` commented out, so the default applies as installed.
- The harness registers `'bash'` twice — `packages/shell/tool-bash/src/index.ts:243` and `packages/shell/tool-bash-persistent/src/index.ts:375` — so `'bash'` covers both, exactly as the plugin's own comment at `src/index.ts:40` says. `'persistent-bash'` and `'terminal-bash'` match no registered tool.
- The harness also registers `'pwsh'` (`packages/shell/tool-pwsh/src/index.ts:253`), with the same required `command: { type: 'string' }` parameter (`:256`) that `commandOf` already reads (`src/index.ts:387`).
- The base bundle mounts **both** `tool-bash` and `tool-pwsh` (`packages/bundle/base/cordis.patch.yml:210-215`); the web-app bundle references both (`:293`, `:296`).
- The plugin's motivating incidents are PowerShell ones — the module docstring names `Remove-Item`, `~/.claude`, `~/.dsh`, `%TEMP%\dsh-subprocess` (`src/index.ts:4-9`) — and the rule set is built for PowerShell: `/\bRemove-Item\b/i` (`src/index.ts:111`), `/-Recurse\b/i` (`:126`), `-WhatIf`/`-Confirm` (`:137-138`).

So the guard is written for PowerShell, and the PowerShell tool is the one tool outside its default watch list. Adding `'pwsh'` to `DEFAULT_TOOL_NAMES` (or uncommenting and extending `cordis.patch.yml:12`) closes it with no other change, because the argument key already matches.

### F4 — Enumeration of delete-to-disk paths, and which the guard covers. CONFIRMED

| Path | Reaches disk? | Covered by the guard? |
|---|---|---|
| `bash` tool (`tool-bash`, `tool-bash-persistent`, both register `'bash'`) | yes | **yes** — `'bash'` is in the default list |
| `pwsh` tool (`packages/shell/tool-pwsh/src/index.ts:253`) | yes | **no** by default — F3 |
| `terminal_send` (`packages/terminal/tool-terminal/src/index.ts:198`, param `text` at `:203`) | yes, writes to a live shell | **no** — name not listed, and `commandOf` reads only `['command','cmd','input','script','code']` (`src/index.ts:387`), not `text`. Not in the base bundle, so it is an opt-in/web-app surface |
| tools called *from inside* a `run_code` program | yes | **yes** — sub-dispatches go through `registry[TOOL_RUNTIME_SCHEDULER]` (`packages/core/tools/src/code-mode.ts:481`), whose `prepare` is `prepareScheduledExecution` (`packages/core/tools/src/index.ts:797`, `:1459-1460`), i.e. the same `tools/pre-execute` waterfall. This is a genuine strength |
| a `run_code` program touching the filesystem directly | yes | **no** — the program body is compiled with `new AsyncFunction(...)` in a Node worker thread (`packages/code-runtime/code-runtime-worker-thread/src/bootstrap.ts:405-406`) and is not module-restricted; that package's README states "OS processes a program spawns survive termination" (`packages/code-runtime/code-runtime-worker-thread/README.md:49`). Nothing here becomes a tool call, so no command text exists to review |
| the `fs` capability / `tool-fs` | **no delete exists** | n/a — and this is worth stating in the plugin's favour: the `FsProvider` Service Definition has no delete/unlink/rmdir operation at all (`packages/fs/fs/src/index.ts:116-243`); `tool-fs` registers only `read`, `write`, `edit`, `read_image`; `str_replace_editor`'s command enum is `['view','create','str_replace','insert']` (`packages/fs/tool-str-replace-editor/src/index.ts:429`). The fs surface is not a gap |
| the `subprocess` capability | via its consumers only | n/a — `packages/subprocess/*` registers no tool (no `defineTool` in its `src/`); the Service Definition is `resolveExecutable` / `spawn` / `spawnTerminal` (`packages/subprocess/subprocess/src/index.ts:118-139`), reached through the shell providers and terminal, i.e. through the tools above |

The practical summary: with `'pwsh'` added, the guard covers every *shell-command-shaped* delete a model can issue in a base-bundle assembly, including from inside `run_code`. It does not and cannot cover direct filesystem calls made by a `run_code` program — that is the job of `packages/sandbox`, which the base bundle already mounts (`packages/bundle/base/cordis.patch.yml:169`, `:172`), alongside `native/node-addon-landlock-run`. The two layers are complementary; naming the split keeps anyone from mistaking a command-text guard for host containment.

### F5 — On Linux/macOS the guard denies almost everything, and misattributes why. CONFIRMED (partly already known to the author)

The author documents the platform strategy deliberately: `tests/destructive-delete.spec.ts:6-10` states that the guard resolves target tokens by Windows mount semantics and that bare POSIX absolute paths fall into the "POSIX root/UNC cannot be resolved" branch, and the raw-absolute-path suite is `describe.skipIf(process.platform !== 'win32')` (`:119`). Credit where due — this is not an oversight.

What may not be known is the *user-visible consequence* and one diagnostic bug:

- `FLAG_RE = /^(?:--?[A-Za-z]|\/[A-Za-z])/` (`src/index.ts:144`) classifies any token starting with `/` + a letter as a **flag**, and the target filter drops flags before `resolveTarget` is ever called (`src/index.ts:314-319`). So a POSIX absolute path like `/home/u/proj/build` is removed from `targets` as if it were an option, `targets.length === 0`, and the denial produced is the one at `src/index.ts:320-326`: *"no explicit target paths printed — dry-run first"*. The command plainly printed a target. The accurate branch (`:273-275`, "POSIX root/UNC target") is unreachable for these tokens.
- The existing POSIX test asserts only `kind === 'deny'` and never the reason (`tests/destructive-delete.spec.ts:51-54`), which is why this is invisible to CI. The other cases in that file *do* assert on the reason (`:42`, `:48`, `:59`, `:63`).
- Net effect on a Linux/macOS host: relative targets deny (`:276`), POSIX absolute targets deny with the wrong reason, and effectively only `~/...`-form targets inside the workspace pass. Safe, but a Linux user is likely to read it as "this plugin blocks every delete and tells me I didn't specify a path".

Small fix: exclude POSIX-absolute tokens from `FLAG_RE` (require the `/x` form to be short, or check `process.platform`), and add a POSIX resolution branch to `resolveTarget`. Asserting on `verdict.reason` in the POSIX test would have caught it.

### F6 — Dry-run markers are matched against the entire command string. CONFIRMED

`reviewDestructiveDelete` returns `undefined` — full pass — as its very first action if any `DRY_RUN_MARKERS` entry matches anywhere in `command` (`src/index.ts:298`, markers at `:136-141`). `DESTRUCTIVE_VERBS` and `RECURSIVE_FLAGS` are whole-string too, and the module docstring explicitly puts chained commands in scope: "匹配范围是整个命令文本,链式命令(`a && rm -rf x`)同样命中" (`src/index.ts:108`).

Combining those two facts: in a chained command, a dry-run marker belonging to an *earlier* segment suppresses review of a *later* delete. `/(?:^|\s)-n\b/` (`:140`) is the exposed one — `-n` is an ordinary flag on `grep`, `sort`, `head`, `tail`, `uniq`, `docker`, and many others, so this is as likely to fire by accident as by intent.

The materials for the fix are already in the file: `OPERATOR_WORDS` (`src/index.ts:145`) enumerates the separators. Splitting the command on those and running the existing review per segment would scope both the markers and the verb/flag detection correctly. Reported as a scoping improvement; I did not construct or run any bypass.

### F7 — `ToolRuntime.guard()` is a strictly stronger seam for the delete guard. CONFIRMED

The harness has a seam built for exactly this, which the plugin does not currently use:

> "A monotonic execution guard evaluated after every `tools/pre-execute` listener and before the tool body. Returning a reason denies the call; returning `undefined` leaves it unchanged. **Because guards have no allow result, listener ordering cannot turn a denial back into permission.**"
> — `packages/core/tools/src/index.ts:703-711` (the `ToolGuard` type)

Registered via `ctx.tools.guard(guard)` (`packages/core/tools/src/index.ts:1110-1116`) and evaluated at `:1486-1488`, only on the allow path, so no listener can override it.

`reviewDestructiveDelete` already has the `ToolGuard` shape almost exactly — synchronous, pure, `(command, options) => ReviewVerdict | undefined` (`src/index.ts:297`) against `(execution) => string | undefined`. Moving the default `action: 'deny'` path onto `ctx.tools.guard()` would remove the plugin's dependence on `{ prepend: true }` ordering entirely.

One real constraint: guards have **no** `ask` result. So `action: 'ask'` would have to stay on the waterfall listener, and the clean shape is guard-when-`deny`, listener-when-`ask`.

### F8 — Secret detection does not read, log, persist, or echo credential values. CONFIRMED

Traced every path a matched string could take:

- `MatchInfo` carries `ruleId`, `family`, `category`, `severity`, optional `secretType`, and offsets — never text, and the type says so (`src/detect/types.ts:59-76`).
- The scanner constructs matches from offsets only (`src/detect/scanner.ts:84-91`, `:108-116`).
- `DetectionEvent` carries the same facts plus `action`/`approved`/`scannedLength`/`truncated` (`src/events.ts:22-43`, `:51-62`); `detectionEvent()` copies only those (`src/index.ts:666-686`).
- `summarizeRecords` emits ids, families, severities, surfaces, actions (`src/index.ts:689-712`); `defend_report`'s output schema is `additionalProperties: false` throughout (`src/index.ts:541-573`).
- The model-visible deny/block reasons name `family`, `ruleId`, and the scanned length only (`src/index.ts:473`, `:497`, `:526`).
- `safeSnippet` (`src/detect/scanner.ts:162-174`) is the only function that could echo surrounding text. It is exported (`src/detect/index.ts:29`) but **never called** from `src/index.ts` — grep confirms definition and re-export only.

This matches the harness's own posture on credentials, where configuration carries *references* and providers own values, and `CredentialInfo` is documented "safe for configuration UIs — never the value" (`packages/credentials/credentials/src/index.ts:38-46`). The plugin scans text that may transiently contain a credential (unavoidable for any scanner) and never persists, logs, or transmits it.

**One asymmetry worth fixing.** The *delete guard* is less careful than the detection layer: its denial reason embeds `command.slice(0, 160)` (`src/index.ts:323`, `:332`), and that string is both passed to `logger.warn` (`:414`) and returned as the model-visible reason. A shell command with an inline credential (`AWS_SECRET_ACCESS_KEY=… && rm -rf …`, a `curl -H "Authorization: …"` earlier in a chain) would put up to 160 characters of it into the log. Running the existing secret rules over the echoed prefix, or truncating it harder, would restore the symmetry.

### F9 — `defend/detection` events can make a session log unreadable. CONFIRMED from source; highest-severity operational finding

The `README.md:125` note says audit appends use the two-argument `Session.append` form and that on post-rc.6 builds the events are required-on-read, "which is fine while this plugin is installed because it declares the event type." The reasoning does not hold, and the consequence is larger than the note suggests.

- The plugin appends `session.append(DETECTION_EVENT, event)` (`src/index.ts:441`) — two-argument, no envelope.
- The gate is `KNOWN_SESSION_EVENT_TYPES`, a **generated, in-repo-only** `Set<string>` (`packages/core/session/src/known-event-types.ts:1-19`). Its own doc says: *"Downstream (out-of-repo) plugin events are outside this list by construction; a registration surface for them is deferred until such a consumer exists"* (`:15-17`).
- `declare module '@deepseek-ai/dsh-session/types'` (`src/events.ts:15-45`) is a TypeScript declaration merge. It has **no runtime effect** on that generated Set. Installing the plugin therefore does not make the build "know" the type.
- The read path refuses: `assertEventsSupported` throws `SessionFormatUnsupportedError` for any type outside the set unless `ignorable === true` (`packages/session/session-persistence/src/coordinator.ts:1061-1065`), and it runs on every stored-session load path (`:864`, `:884`, `:900`, `:1309`).
- There is currently **no way for an out-of-repo plugin to set `ignorable`.** `Session.append`'s only optional third argument is `SurfaceIntent`, and only for surface event types (`packages/core/session/src/index.ts:604-608`). `ignorable` exists on the envelope type (`packages/core/session/src/types.ts:422`) with no append-time setter.
- The plugin's `try { … } catch {}` around the append (`src/index.ts:440-444`) does not help: the append succeeds; the refusal happens later, at read time.

So a session in which any detection fired can be refused on resume/read. **Framing matters here: this is a harness gap, not a plugin defect.** `known-event-types.ts:15-17` says the registration surface for downstream events was deliberately deferred "until such a consumer exists" — dsh-defend is that consumer. It is worth raising upstream with exactly this citation.

Workaround available today with no code change: set `detection.audit: false` in `cordis.patch.yml` (the field exists, `src/index.ts:73-74`, `cordis.patch.yml:28`). The ring buffer and `/defend` keep working; only the durable audit trail is lost.

**Honest limit:** verified by reading the source at local HEAD. I did not run the harness to observe the refusal. The check to run is: install, trigger one detection, end the session, resume it.

### F10 — Detection defaults will fire on ordinary developer prose, and on some assemblies that blocks the turn. CONFIRMED

- The Jailbreak-Detector needles include `'I need you to'`, `'this is urgent'`, `'you are now'`, `'for educational purposes'`, `'developer mode'`, `'pretend you are'`, `'roleplay as'` (`src/detect/rules.ts:132-146`). These are unremarkable phrases in normal instructions to an agent.
- Defaults are `injectionAction: 'ask'` and `jailbreakAction: 'ask'` (`src/index.ts:86-87`, and the shipped `cordis.patch.yml:20-22`).
- At `agent/pre-step`, `ask` with no approval answerer returns `false` (`src/index.ts:451`) and yields `{kind:'reject'}` (`:529`), which the loop turns into a blocked turn (`packages/core/agent-loop/src/agent.ts:266-270`). Per `README.md:124`, that rejection carries no reason to the model.
- The `approval` plugin lives in the base bundle (`packages/bundle/base/cordis.patch.yml:188`); the headless bundle's own entries are `system-prompt`, `hmr`, `tools`, `code-runtime`, `headless-startup`, `headless-runner` (`packages/bundle/headless/cordis.patch.yml`). Whether a given profile has an approval answerer therefore depends on composition — and where it does not, "I need you to fix the failing test" silently blocks the turn.
- Tool arguments are scanned for *every* tool, because `argumentsText` falls back to `JSON.stringify(argumentsValue)` (`src/index.ts:624-629`). Writing or reading a document that discusses prompt injection trips the injection rules — the plugin's own README would.

Two suggestions, both using machinery already in the file: default `injectionAction`/`jailbreakAction` to `'allow'` (log-only) and let `secretBlockCritical` carry the enforcing weight; and/or gate `ask` on corroboration — `computeConfidence` already returns `1` for secrets, `0.9` for ≥2 matches, `0.5–0.7` for a lone match (`src/detect/scanner.ts:142-150`), and nothing currently consumes it.

### F11 — `inject = ['commands']` makes the delete guard unavailable where `commands` is absent. CONFIRMED (impact PLAUSIBLE)

`export const inject = ['commands']` (`src/index.ts:38`) is a **hard** dependency, so the entire plugin — the destructive-delete guard included — does not apply in an assembly without a `commands` service. The code then also treats it as optional, checking `commands !== undefined` at `:587-588`, so the two are inconsistent. Also `argumentsText` falls back to `JSON.stringify` for every tool (`src/index.ts:624-629`), so any tool call that reads or writes a document discussing prompt injection trips the injection rules — your own README would. Suggestion: default the two prose families to `allow` (log-only) and let `secretBlockCritical` carry the enforcing weight, and/or gate `ask` on corroboration — `computeConfidence` (`src/detect/scanner.ts:142-150`) already produces exactly that signal and nothing consumes it.
> - **`inject = ['commands']` (`src/index.ts:38`) is a hard dependency**, so in an assembly without a commands service **the delete guard doesn't load either** — while the code also treats it as optional at `:587-588`. Since `registerCommand` is already a config flag, dropping `commands` from `inject` and keeping the `ctx.get` check would let the guard run in automation/headless profiles too.
> - **`protectedPrefixes()` (`src/index.ts:185-199`) is a deployment-varying choice that isn't a Config field.** `ReviewOptions.protectedPrefixes` exists (`:290`); `apply()` just never passes it (`:412`). The default list has no `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.config` — a `protectedPrefixes?: string[]` merged with the defaults looks like a cheap win.
> - **The delete guard's denial reason echoes the first 160 characters of the raw command** (`src/index.ts:323`, `:332`) into both `logger.warn` (`:414`) and the model-visible reason. The detection layer is scrupulous about this; worth aligning, since inline credentials in shell commands do happen.
>
> **Two boundary clarifications, not problems**
>
> - `fs` isn't a gap: `FsProvider` has no delete operation at all (`packages/fs/fs/src/index.ts:116-243`), `tool-fs` registers only `read`/`write`/`edit`/`read_image`, and `str_replace_editor`'s command enum is `['view','create','str_replace','insert']` (`packages/fs/tool-str-replace-editor/src/index.ts:429`). `subprocess` registers no tool and is reachable only through shell/terminal.
> - A `run_code` **program body** touching the filesystem directly is invisible to the guard: the body is compiled with `new AsyncFunction(...)` in a worker thread (`packages/code-runtime/code-runtime-worker-thread/src/bootstrap.ts:405-406`), not a module sandbox, and that package's README notes programs' spawned processes survive termination (`README.md:49`). That was never a command-text guard's job — the base bundle already mounts `sandbox` and `sandbox-policy` (`packages/bundle/base/cordis.patch.yml:169`, `:172`). The layers are complementary; I mention it only so nobody mistakes the guard for host containment.
