## What the plugin is

A DSH plugin giving agent file mutations an undo key. It snapshots the pre-operation content of every `write` / `edit` tool call and restores it on demand.

| Command | Effect |
|---|---|
| `/undo` | Undo the most recent file write/edit |
| `/undo list` | List recorded operations (index + time + tool + path) |
| `/undo <n>` | Undo a specific operation by index |
| `/undo prune [days]` | Drop snapshots older than N days (default 7) |

Storage is an append-only JSONL file at `~/.dsh/file-undo/snapshots.jsonl`. Snapshots are global, not per-session. MIT licensed.

The author's stated open problems, verbatim from the OP: (1) `ctx.fs` has no `delete`/`unlink`, so undoing a *creation* is impossible through supported surfaces, and they explicitly refuse to reach for `node:fs` on workspace files; (2) "the official tool results / session log do not retain the pre-op content: `write`/`edit` outcomes return only a success string"; (3) shell-side deletions (`rm`, `Remove-Item`) are invisible to the tool waterfall.

## What it does well

**CONFIRMED (from the OP and the source read).**

- **It solves a problem people actually have.** The single reply on 2467 (zengzheng138) reports repeated, unrecoverable agent damage. That is the strongest possible signal for a plugin like this.
- **The `next()` discipline is right.** The `tools/pre-execute` listener returns `next()` rather than short-circuiting, which is exactly what the harness requires of a waterfall listener — `packages/core/tools/src/index.ts:150` documents `tools/pre-execute` as `@mode waterfall`, and the repo convention is that a waterfall listener that returns without `next()` short-circuits the chain. A snapshotting observer must not do that, and this one does not.
- **Command registration goes through `ctx.effect()`.** Registering inside a `ctx.effect` generator and yielding `ctx.commands.register(...)` is the sanctioned disposer pattern (`AGENTS.md`: "every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer"). The plugin does not need to hold the disposer itself — `ctx.effect` owns it — so this is correct, and it means HMR/unload cleanup works.
- **Carrying the caller session's sandbox policy into the restore is the non-obvious correct thing.** `FileSystem.writeText`'s fifth parameter is exactly that (`packages/fs/fs/src/index.ts:222-228`, with the `sandboxPolicy` parameter documented at `:217-219`). Plenty of plugin authors would have written from a global context and shipped a `file access denied` bug. They found it and wrote it up.
- **It refuses to bypass `ctx.fs` for workspace files.** Reaching for `node:fs` on the *agent's* files would defeat the sandbox seam entirely. Holding that line, and saying so publicly rather than quietly shipping the shortcut, is the right instinct. (Note the plugin *does* use `node:fs/promises` for its own sidecar snapshot store under `~/.dsh` — that is a different thing and is defensible, though see the `ctx.storage` finding below.)
- **The "pitfalls" section is a genuine contribution to other plugin authors** — particularly pitfall 1 (an `inject` omission type-checks but explodes at runtime in the Guard) and pitfall 3 (argument-bearing commands need `input` declared or they silently degrade to plain messages). Those are the kind of findings that are expensive to rediscover.

## The deletion-rollback question (their actual ask — answer it here, with citations)

Their three questions, answered against `47f943859`. Two of the three premises hold. **One does not, and correcting it materially improves the plugin.**

### Q1 — "Is there an official `delete`/`unlink` on `ctx.fs` I've missed?"

**CONFIRMED: no, and their reading is exactly right.** The `FileSystem` abstract service (`packages/fs/fs/src/index.ts:86-250`) declares precisely twelve abstract members: `resolve` (`:116`), `processPath` (`:126`), `fileUrl` (`:135`), `contains` (`:144`), `stat` (`:152`), `lstat` (`:168`), `readText` (`:176`), `streamText` (`:187`), `readBytes` (`:199`), `listDir` (`:208`), `writeText` (`:222`), `editText` (`:243`), plus the non-abstract `sandboxMode` getter (`:103`). There is no create-directory, no rename, no remove. Grepping `packages/fs/*/src/*.ts` for `unlink|rmdir|\.rm\(` at this commit returns exactly one hit, and it is a comment about a concurrent external unlink in the local backend's version derivation (`packages/fs/fs-local/src/index.ts:258`) — not an API.

So: **undo-of-creation cannot be completed through `ctx.fs`.** That half of their diagnosis is correct and I could not find a way around it.

**But there is a sanctioned deletion route they did not mention: the shell capability.** `ctx.shell` is a first-party Service Definition (`packages/shell/shell/src/index.ts:41-43` declares `shell: ShellExecutor`), with `resolve(request): ShellExecSpec` (`:85`) and `run(spec): Promise<ShellRunResult>` (`:93`). Critically, `ShellExecSpec` carries `sandboxPolicy: SandboxExecutionPolicy | undefined` (`packages/shell/shell/src/types.ts:109`) — the *same* policy type `writeText` takes. So a plugin can delete a file through a declared capability, under the caller session's sandbox policy, without importing `node:fs` and without inventing an API:

```
inject = ['commands', 'tools', 'fs', 'shell', 'sandboxPolicy']
// resolve the policy exactly as the restore path already does, then:
const spec = ctx.shell.resolve({ command: `rm -- ${quoted}`, sandboxPolicy: policy })
await ctx.shell.run(spec)
```

**Label this PLAUSIBLE, not CONFIRMED.** The types and the sandbox plumbing line up and I verified each cited line, but I did not execute this, and it carries real caveats worth stating in the same breath: it is platform-specific (`rm` vs the `pwsh` executor at `packages/shell/tool-pwsh/src/index.ts:253`), it depends on the deployment actually mounting a shell provider, and quoting a hostile path correctly is on the plugin. It is a workaround, not a primitive. Their instinct that **the right fix is an upstream fs delete primitive** is, in my reading, well-founded — but that is a maintainer call, not mine to make, and I would not present it as anything other than their proposal.

### Q2 — "Do the tool results / session log retain the pre-op content?"

**This is the premise that does not hold, and it is good news.** The OP says: "`write`/`edit` outcomes return only a success string; the pre-op content is discarded by the tool result." The *rendered, model-facing* text is a success string — but the **canonical tool value is not**, and it carries the full before-state.

**CONFIRMED — the fs service returns the before-content.** `FsWriteOutcome.before: string | null` (`packages/fs/fs/src/types.ts:141`, documented `:133-140` — LF-normalized prior content, `null` only for a create or a declined basis) and `FsEditOutcome.before: string` (`:165`, documented `:160-164`).

**CONFIRMED — the `write` and `edit` tools pass that straight through into their canonical output value.** The `write` tool declares `before` and `after` in its output schema (`packages/fs/tool-fs/src/write.ts:84-91`) and returns `{ path, operation, before, after }` (`:123-128`). The `edit` tool declares the same (`packages/fs/tool-fs/src/edit.ts:99-100`) and returns `{ path, before, after }` (`:142-146`). The success string they saw is only `render` (`write.ts:94`, calling `formatWriteOutput`) — the *projection*, not the value.

**CONFIRMED — that value reaches a plugin at `tools/post-execute` and `tools/result`.** `ToolExecutionSuccess.value: JsonValue` (`packages/core/tools/src/index.ts:559`), and both events carry the result: `'tools/post-execute'(exec, result, next)` (`:175`, `@mode waterfall`) and `'tools/result'(exec, result)` (`:197`, `@mode emit`, deep-frozen final snapshot).

**CONFIRMED — and this is why their session-log search came up empty.** `value` is documented at `packages/core/tools/src/index.ts:558` as "Execution-local canonical value; **deliberately omitted from durable events**." So the before-state is available in-process but is deliberately not in the session log. Their session-log conclusion was right; the reason is this line, and it is a design decision rather than an oversight.

**Why this matters practically — moving the capture from `tools/pre-execute` to `tools/post-execute` is a straight upgrade:**

1. **No TOCTOU gap.** Today the plugin does its own `fs.readText` at pre-execute, and the tool then does `ctx.fs.writeText` (`write.ts:114`) some time later. `outcome.before` instead comes from inside the backend's atomic mutation, so it is the content that was actually replaced.
2. **No phantom entries.** `tools/pre-execute` is the allow/deny gate (`packages/core/tools/src/index.ts:143-152`) — it fires for calls that are subsequently denied, and for writes that then throw (`write.ts:115-120` maps sandbox/stale failures into throws). Those currently land in `/undo list` as operations that never happened. At post-execute you record only mutations that actually occurred.
3. **It answers the creation half directly.** `write`'s value carries `operation: 'create' | 'update'` (`write.ts:125`, schema `:83`). That is an authoritative "this call created the file" signal — no stat-probing, no guessing. So *detecting* a creation is solved cleanly; only *acting* on it (the delete) remains blocked by Q1.
4. **One fewer read per mutation**, and the plugin's `inject` could arguably drop `fs` for the capture path (it still needs it for restore).

There is also `'tools/execute'` (`packages/core/tools/src/index.ts:163`), an around-dispatch waterfall, if a wrapping shape is ever wanted. I would not use it here: its contract (`:154-158`) says wrappers "may change only `exec.signal`, while call identity remains immutable", so it buys nothing over post-execute for this purpose.

**One scope caveat regardless of seam.** The plugin matches only `write` and `edit`. A deployment mounting `str_replace_editor` instead (`packages/fs/tool-str-replace-editor/src/index.ts:423`) gets no coverage at all — and that tool's `create` / `str_replace` / `insert` subcommands mutate files through the same `ctx.fs` (it emits `fs/observed` present at `:270`, `:321`, `:363`). The author already hit this from the other direction (pitfall 2 — they *started* on `str_replace_editor` and switched). Both tools exist upstream; which is mounted is a profile choice, so covering both, or resolving the name from the tool catalog, would make the plugin portable across profiles.

### Q3 — "Is there a sanctioned hook to observe shell-side deletions (`rm`)?"

**CONFIRMED: no. Their conclusion is correct, and the scope boundary is sharper than the OP states.**

- **`ShellExecutor` emits no events at all.** `packages/shell/shell/src/index.ts:40-45` declares only `interface Context { shell: ShellExecutor }` inside its `declare module` block. There is no `interface Events`.
- **`SubprocessRuntime` emits no events either.** `packages/subprocess/subprocess/src/index.ts:68-73` — same: `Context` only, no `Events`.

So the only visibility into a shell deletion is at the **tool** layer, on the `bash` tool (`packages/shell/tool-bash/src/index.ts:243`, or the persistent variant at `packages/shell/tool-bash-persistent/src/index.ts:375`) or `pwsh` (`packages/shell/tool-pwsh/src/index.ts:253`). At that layer a plugin sees **the command string, not its filesystem effects**. You would have to parse shell — and `rm` reached via a script, a `Makefile`, a `git clean`, a test runner's temp cleanup, or anything spawned through `ctx.subprocess` produces no tool call at all. That is not a gap to be closed by a cleverer hook; it is a genuine capability boundary.

**The honest scope answer, which is probably the crux of their difficulty:**

| Path | Visible to a plugin? | Before-content available? |
|---|---|---|
| `write` / `edit` tools | Yes — `tools/pre-execute` / `tools/execute` / `tools/post-execute` / `tools/result` | **Yes**, `result.value.before` |
| `str_replace_editor` tool | Yes, same seams — but only if you match its name | Yes (same `ctx.fs` outcomes) |
| Any direct `ctx.fs.writeText` / `editText` by another plugin | No tool event; only `fs/write-intent` / `fs/edit-intent` (pre-only, target but no content) | No |
| `bash` / `pwsh` tool | Command string only | No |
| Anything via `ctx.subprocess`, or spawned by a shell command | **No** | No |
| Deletion, by any route | **No event exists** | — |

**And there is no deletion event to build on.** `fs/observed` (`packages/fs/fs/src/index.ts:76`) looks like a candidate but is not one: `FsObservation` is `{kind:'present', version}` or `{kind:'absent'}` (`packages/fs/fs/src/types.ts:52-54`), and the only emitters of `absent` are *read* paths reporting "I looked and it wasn't there" (`packages/fs/tool-fs/src/read-target.ts:27`, `packages/fs/tool-str-replace-editor/src/index.ts:108`). It is an observation-policy signal for the read-before-write rule, not a mutation record. Nothing in the harness emits "a file was deleted", because nothing in the harness deletes files.

### Is there first-party checkpoint/snapshot machinery to build on?

**CONFIRMED: no — not for file content.** I checked the packages the name suggests:

- **`packages/session/session-checkpoint-policy`** is not file checkpointing. Its module doc reads "Semantic durability checkpoints for model requests, top-level tool dispatch, and completed agent steps" (`src/index.ts:1-5`); the mechanism is `await ctx.sessions.flush(session)` (`:35`) — flushing the **session event log** to durable storage. Nothing to do with file contents. The same is true of the "snapshot"/"checkpoint" vocabulary throughout `packages/session/*/README.md`: it means event-log snapshots and projection-state checkpoints.
- **`packages/workspace`** is workspace *entities* — "user directories with titles and ordered session membership" (`packages/workspace/README.md:5`) — not file versioning.
- `agent/pre-step` (`packages/core/agent/src/runtime-types.ts:231` @ `47f943859`, `@mode waterfall`) is a real per-step seam and would be the natural place to hang a *coarse* "checkpoint the workspace between agent steps" design, if they ever wanted git-style step-level rollback instead of operation-level undo. It gives no file information by itself.

So hand-rolling the snapshot store was the correct call — there is nothing first-party to build on for file content. **UNVERIFIED:** whether upstream has anything of this kind in flight; I only read `47f943859` and did not search issues/PRs, and roadmap questions are for the maintainers anyway.

## Other findings (each labelled, each cited)

1. **Disposers — correct. CONFIRMED (harness side).** Commands registered inside `ctx.effect` (plugin `src/index.ts` ~L129–132) and the listener via `ctx.on` both get automatic disposal. This matches `AGENTS.md`'s "Registrations are effects" rule. No leak.

2. **No credential or network behavior. CONFIRMED (source read).** `src/index.ts` makes no network calls; it touches only `node:fs/promises`, `node:path`, `node:os` for its own store, and `ctx.fs` / `ctx.commands` / `ctx.sandboxPolicy` for harness work. No environment variables, no telemetry, no `dsh` credential surfaces. `package.json` has no `postinstall` or lifecycle script (only `build` and `typecheck`). For a plugin whose whole job is reading your file contents, that is the right posture and worth saying out loud.

3. **Hardcoded tunables with no `Config`. CONFIRMED (source read), PLAUSIBLE as a concern.** `DEFAULT_PRUNE_DAYS = 7`, the store path under `homedir()`, and `'utf8'` are constants; there is no exported `Config`. For a third-party plugin this is a style note rather than a defect, but it is exactly what the in-repo convention pushes against: *"No hardcoded tunables in plugins: deployment-varying choices are validated `Config` fields changeable from cordis.yml; a `DEFAULT_*` constant or test hook is not configurability"* (`AGENTS.md`, Conventions). Retention days and the store location are plainly deployment-varying. Adding `export interface Config { pruneDays?: number; storePath?: string }` would make it configurable from `cordis.patch.yml` and would cost very little.

4. **`ctx.storage` exists and may be a better home than hand-rolled JSONL. CONFIRMED (harness side), PLAUSIBLE as advice.** `packages/storage/storage/src/index.ts:31-33` declares `storage: Storage`, with `storage-json` and `storage-sqlite` backends and a validated domain-record layer `ctx.storageDomain` (`packages/storage/README.md:5-12`) — "persists application data other than session event logs through named backends and typed data forms". The plugin's own store is the one place it does use `node:fs` directly, and this is the sanctioned alternative. I am flagging it as an option rather than a correction: an append-only JSONL file is a defensible choice for exactly the reason the author gives (no read-modify-write race), and I have not read enough of the storage seam to promise it preserves that property.

5. **Unbounded snapshot growth. PLAUSIBLE (source read).** No size cap on captured content and no locking were found in `src/index.ts`. Every `write` of a large file appends that file's entire prior content to a single JSONL file; `/undo prune` is manual and time-based, not size-based. On a repo with big generated files this could grow fast. Contrast the harness's own rule for bounded surfaces (`packages/AGENTS.md`: "Apply bounds to the complete result"). A `maxSnapshotBytes` skip-and-record-a-tombstone would keep `/undo list` honest about what it can restore.

6. **Snapshots are global, not per-session. CONFIRMED (author states this as a deliberate boundary).** Worth noting only because `/undo` with concurrent sessions against different workspaces will interleave in one index space, and `/undo 1` addresses a global index. The restore path already resolves the *caller* session's sandbox policy (~L154), so a cross-workspace restore would presumably be denied rather than silently misapplied — **UNVERIFIED**, I did not trace `sandboxPolicy.resolve` for that case.

7. **Committed `lib/` in the repo.** Observed in the tree listing. Not a defect for a link-installed plugin — the install instructions in the OP require `pnpm build` anyway — just an observation.

为了回答你关于删除回滚的问题，我去读了 harness 源码（`47f943859`，即 `feat/npm-public` 的合并提交）。简短结论：你的三个判断里有两个成立，一个不成立——而不成立的那个对你是好消息。

**Q2 —— 修改前的内容并没有丢失。这是最值得改的一点。**

你看到的成功字符串只是工具的 `render` 投影。工具的规范返回值（canonical value）其实完整携带了修改前的内容：

- `FsWriteOutcome.before: string | null` —— `packages/fs/fs/src/types.ts:141`；`FsEditOutcome.before: string` —— `:165`。
- `write` 工具在输出 schema 中声明了 `before`/`after`（`packages/fs/tool-fs/src/write.ts:84-91`），并返回 `{ path, operation, before, after }`（`:123-128`）。`edit` 同理（`packages/fs/tool-fs/src/edit.ts:99-100`、`:142-146`）。
- 这个值会作为 `result.value` 在 `tools/post-execute`（`packages/core/tools/src/index.ts:175`）或 `tools/result`（`:197`）交到你手里，类型见 `ToolExecutionSuccess.value`（`:559`）。

至于你在 session log 里没找到的原因：`packages/core/tools/src/index.ts:558` 对 `value` 的注释是 *"Execution-local canonical value; deliberately omitted from durable events."*（仅限本次执行的规范值；有意不写入持久化事件。）所以它在进程内可用，但被刻意排除在日志之外。你对 session log 的判断是对的，这一行就是原因。

把捕获点从 `tools/pre-execute` 换到 `tools/post-execute`，看起来是纯粹的改进：

1. **没有 TOCTOU 窗口。** `outcome.before` 来自后端原子写入的临界区内部，而不是你在工具真正 `writeText`（`write.ts:114`）之前若干时间自己读的那一次。
2. **不会产生幽灵记录。** `tools/pre-execute` 是允许/拒绝闸门（`:143-152`）——被后续拒绝的调用、以及随后抛错的写入（`write.ts:115-120`）都会触发它。这些操作实际没发生，但今天会进入 `/undo list`。
3. **它直接给出「新建」信号。** `write` 的返回值里有 `operation: 'create' | 'update'`（`write.ts:125`），这是权威的「本次调用创建了该文件」，不需要再 stat 探测。

无论用哪个 seam，都有一个覆盖面问题：你匹配的是 `write`/`edit`，但上游还存在 `str_replace_editor`（`packages/fs/tool-str-replace-editor/src/index.ts:423`），它同样通过 `ctx.fs` 改文件（`:270`、`:321`、`:363`）。挂载哪一个取决于 profile——你在「踩坑 2」里是从相反方向撞上这件事的。两个都覆盖，或者从工具目录里解析名字，可以让插件在不同 profile 之间通用。

**Q1 —— 你是对的，`ctx.fs` 确实没有删除方法。**

`FileSystem` 一共声明了十二个抽象成员（`packages/fs/fs/src/index.ts:86-250`）：`resolve`、`processPath`、`fileUrl`、`contains`、`stat`、`lstat`、`readText`、`streamText`、`readBytes`、`listDir`、`writeText`、`editText`。没有删除、重命名或建目录。`packages/fs` 里唯一的 `unlink` 是本地后端关于外部并发 unlink 的一句注释（`fs-local/src/index.ts:258`）。

有一条你没提到的路径，仅作为选项提出，不是建议：`ctx.shell` 是已声明的一方能力（`packages/shell/shell/src/index.ts:41-43`，`resolve()` 在 `:85`，`run()` 在 `:93`），而 `ShellExecSpec` 带有 `sandboxPolicy: SandboxExecutionPolicy | undefined`（`packages/shell/shell/src/types.ts:109`）——和 `writeText` 接受的是同一个策略类型。所以 `rm` 可以在调用方 session 的沙箱策略下执行，无需 `import node:fs`。我没有实际运行验证，而且代价是真实的：平台相关（`rm` 对 `pwsh`，见 `tool-pwsh/src/index.ts:253`）、依赖部署确实挂载了 shell provider、路径转义要你自己负责。这是权宜之计，不是原语。

**Q3 —— 判断正确，而且边界比 OP 里写的更硬。**

这两个服务根本不发事件：`packages/shell/shell/src/index.ts:40-45` 和 `packages/subprocess/subprocess/src/index.ts:68-73` 的 `declare module` 块里都只有 `Context`，没有 `interface Events`。所以唯一的可见性在 `bash`/`pwsh` 工具层（`tool-bash/src/index.ts:243`、`tool-bash-persistent/src/index.ts:375`、`tool-pwsh/src/index.ts:253`）——你拿到的是命令**字符串**，不是它的文件系统效果。而且通过脚本、Makefile、`git clean`，或任何经由 `ctx.subprocess` 派生的进程执行的 `rm`，根本不产生工具调用。这是能力边界，不是缺一个钩子。

另外有一个看起来像候选、但需要明确排除的：`fs/observed` 不是删除信号。`FsObservation` 只有 `present | absent` 两态（`packages/fs/fs/src/types.ts:52-54`），而 `absent` 只由**读取**路径发出，含义是「我去看了，它不在」（`tool-fs/src/read-target.ts:27`、`tool-str-replace-editor/src/index.ts:108`）。

**关于「有没有现成机制可以复用」：** 我查了，文件内容层面没有任何一方机制，所以你自己实现快照存储是正确的选择。`session-checkpoint-policy` 说的是 **session 日志**的持久化，与文件无关——它的模块文档写的是 "Semantic durability checkpoints for model requests, top-level tool dispatch, and completed agent steps"，实现就是 `ctx.sessions.flush(session)`（`src/index.ts:1-5`、`:35`）。`packages/workspace` 是工作区实体，即带标题和 session 归属的目录（`README.md:5`）。如果你以后想要粗粒度的「按 step 回滚」而不是「按操作撤销」，`agent/pre-step`（`packages/core/agent/src/runtime-types.ts:231`）是那个 seam，不过它本身不提供任何文件信息。

顺便两个小点：`ctx.storage` 是存在的（`packages/storage/storage/src/index.ts:31-33`，有 json 和 sqlite 后端），如果你不想自己维护那个 JSONL 文件的话——当然你选择 append-only 的理由是充分的，可听可不听。另外 `DEFAULT_PRUNE_DAYS` 和存储路径是常量而非 `Config` 字段，这大概是上游 reviewer 唯一会提的一点；加一个小的 `Config` 就能让它们从 `cordis.patch.yml` 配置。

感谢你写的「踩坑」部分，尤其是 `inject` 漏声明能通过 `tsc` 但运行时才炸的那条——这种坑重新踩一遍代价很高。
