# 2470 — [BUG] dsh subagent 在 GUI 冷恢复后默认切回 dsv4p 模型导致扣费路由错误

## Verdict

**CONFIRMED — real bug, real money bug, and a duplicate of at least four open discussions.**

The core claim is exactly right and reproduces in source at `master @ 47f943859`: `resolveChildAgentOptions()` reads the parent's creation-time `AgentOptions` and never consults the parent's live/logged route, while the Web GUI's model selection deliberately overrides routing only through the `agent/request` waterfall and never writes back to `agent.options`. Because a provider route id is also the stem of the credential reference that authenticates the call, a child inheriting the stale `provider` authenticates and bills against a different account than the parent. The parent is correct; every descendant is wrong; the wrong route is then frozen into the child's durable descriptor and re-applied on each cold resume, which is how one wrong parent turn becomes 61 wrong sessions.

Sub-claim status:
- Child options read static creation-time options: **CONFIRMED**
- GUI model selection never updates `agent.options`: **CONFIRMED**
- Cold recovery seeds `agentOptions` from deployment defaults while routing comes from the persisted header: **CONFIRMED (mechanism); trigger is conditional** — see Root cause, Case B
- Divergence changes the billed provider account, not just the model: **CONFIRMED**
- "No Agent Note has decided this": **CONFIRMED** — but the repo has already decided the *identical question* for presets and for delegation policy, in the opposite direction from what the code does here.
- Zero replies / novel report: **REFUTED** — [#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581), [#1472](https://github.com/deepseek-ai/deepseek-harness/discussions/1472), [#2006](https://github.com/deepseek-ai/deepseek-harness/discussions/2006), [#2053](https://github.com/deepseek-ai/deepseek-harness/discussions/2053) report the same defect; [#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581) already carries a tested patch.

## Research findings (each with a path:line or URL citation)

### The named function exists in source, under that exact name

**CONFIRMED.** The built path in the report maps to `packages/subagent/subagent/src/child-agent.ts`:

- `packages/subagent/subagent/src/child-agent.ts:68-83` — `resolveChildAgentOptions(parent, requested, childDepth)`.
- `packages/subagent/subagent/src/child-agent.ts:73-75` — the three reads that are the whole defect:
  ```ts
  const parentProvider = parent.options.provider
  const parentModel = parent.options.model
  const parentMaxTokens = parent.options.maxTokens
  ```
- Its JSDoc at `packages/subagent/subagent/src/child-agent.ts:59-62` already states the *intended* contract in words the code does not honor: "the parent's provider/model/maxTokens **route** unless the request overrides it".

Two call sites, i.e. both in-process delegation paths:
- `packages/subagent/subagent-in-process-driver/src/index.ts:136` — one-shot children.
- `packages/subagent/subagent/src/continuation.ts:444` — continuable/background children.

### `Agent.options` is a creation snapshot; the live route is elsewhere

**CONFIRMED.**

- `packages/core/agent/src/runtime-types.ts:24-31` — `AgentOptions { provider?, model?, maxTokens? }`.
- `packages/core/agent/src/runtime-types.ts:67-68` — `Agent.options` is documented as "The provider route and model this agent's requests use". **That JSDoc is now false** for any deployment that installs a request-level selection, which is every Web/GUI deployment. This is itself a citable documentation defect and is very likely why the subagent code was written this way.
- `packages/core/agent-loop/src/agent.ts:419-436` — the loop builds its seed config from `this.options` **only for the first request of a loop instance**; later steps seed from the persisted `request/header`.
- `packages/core/agent-loop/src/agent.ts:437-440` — the seed then passes through the `agent/request` waterfall, and the waterfall result (not `this.options`) is what is dispatched.
- `packages/core/agent-loop/src/agent.ts:463-472` — the *resolved* config is what gets appended as `request/header` (`reason: 'initial' | 'resume' | 'change'`). So the durable log records the route actually used.
- `packages/core/session/src/index.ts:670-680` — `session.requestHeader()` is the incrementally folded, O(new events) read of that header. **This is the authoritative live-route accessor the fix needs, and it already exists.**

### GUI model selection overrides the request, never the options

**CONFIRMED.**

- `packages/core/agent/src/model-selection.ts:39-75` — `installModelSelection()` registers exactly two agent-scoped waterfall listeners: `system-prompt/assemble` (to keep prompt variables in step) and `agent/request` (`packages/core/agent/src/model-selection.ts:54-70`), where it replaces `provider`, `model`, and `reasoningEffort` on the resolved config. It never touches `agent.options`. By design — see the Agent Note citations below.
- `packages/host/apiproxy/src/api-proxy.ts:1154-1180` — `selectionFor(agent)` resolves its tiers **on every read**: process-local pick → `agent.session.requestHeader()?.config` → `defaults.defaultModelSelection()`.
- `packages/host/apiproxy/src/api-proxy.ts:2314` — `session.selectModel` writes only `selectionFor(found.agent).current = selected`.
- `packages/host/apiproxy/src/api-proxy.ts:2316` — it additionally persists the choice as the shared deployment default via `saveDefaultModelSelection?.(selected)`, and `packages/host/apiproxy/src/api-proxy.ts:2317-2321` swallows a save failure with a `logger.warn` ("the model switch applies to this session but was not saved as the default").

So after a GUI pick: the parent's requests route to B/b, the log records B/b, and `parent.options` still holds whatever the deployment default was when the agent was created.

### Cold recovery seeds options from the deployment default

**CONFIRMED (mechanism).**

- `packages/host/apiproxy/src/api-proxy.ts:1111-1115` — `agentOptions()` is defined as *"The seed model each create/resume declares; re-read so it never goes stale"* and returns `{ provider, model }` from `defaults.defaultModelSelection()`.
- `packages/host/apiproxy/src/index.ts:99` — that closure is `ctx.agentDefaultModel.currentSelection()`.
- Call sites: `packages/host/apiproxy/src/api-proxy.ts:1659` (cold resume), `:1672` (fresh create), `:2434` (fork).
- The asymmetry is visible in the code as written: at `packages/host/apiproxy/src/api-proxy.ts:1649-1656` the resume path deliberately resolves the **preset** from the session's own LOG rather than a default, immediately above the line that seeds the **model** from the deployment default.

### The wrong route is then made durable and re-applied

**CONFIRMED.** This is the amplifier the report's "61 sessions" points at, and it is not in the report.

- `packages/subagent/subagent/src/continuation.ts:413-414` — the continuable descriptor's `agentProvider`/`agentModel` are snapshotted from `request.agentOptions?.… ?? parent.options.…`, i.e. the same stale values.
- `packages/subagent/subagent/src/continuation.ts:918-923` — a **cold resume of a continuable child** rebuilds `agentOptions` from that persisted descriptor, so the wrong route survives restarts independently of the parent.
- `packages/subagent/subagent/src/continuation.ts:1009-1023` (`materializeTracked`) — children are created/resumed through `this.ownerCtx.agents.{create,resume}` with `agentOptions` only. No model selection is installed on a child, so unlike the parent a child has **no** tier that could recover the correct route from its own log.
- Grandchildren: a child's `agent.options` now *is* the wrong route, so `resolveChildAgentOptions(child, …)` propagates it downward faithfully. One wrong parent turn contaminates the whole subtree.

### Existing tests pin the current (defective) behavior only negatively

Asserts that nothing is fabricated; asserts nothing about *which* route is inherited when the parent has a live one.
- `packages/subagent/subagent/tests/continuation.spec.ts:2265-2276` — pins that an explicit per-request `agentOptions.model` wins. That precedence is unchanged by any fix here.
- No test anywhere asserts inheritance from a parent whose live route differs from its creation options. **That gap is the bug's habitat.**

## Root cause

`resolveChildAgentOptions()` inherits from the wrong authority.

The harness has two distinct representations of "which model this agent uses":

1. **`Agent.options`** — the `AgentOptions` frozen at `agents.create()` / `agents.resume()`. Under the Web host these are always `defaults.defaultModelSelection()` at that moment (`packages/host/apiproxy/src/api-proxy.ts:1111-1115`, `:1659`, `:1672`), never the session's own route.
2. **The live route** — the `agent/request` waterfall result, which is what actually dispatches and what gets appended to the log as `request/header` (`packages/core/agent-loop/src/agent.ts:437-472`), readable at any time via `session.requestHeader()?.config` (`packages/core/session/src/index.ts:670`).

Everything that decides routing at runtime — the GUI picker, `session.selectModel`, cold-resume restoration — operates on (2) by deliberate design (`packages/core/agent/src/model-selection.ts:54-70`; `packages/host/apiproxy/src/api-proxy.ts:1154-1180`). `resolveChildAgentOptions()` reads (1). The two are equal only for the first request of a freshly created agent under an unchanged deployment default; every other state diverges.

**Case A (GUI switch, no restart)** — CONFIRMED end to end. Create seeds `options = A/a`; the pick sets the process-local selection to B/b; the parent's requests and log say B/b; delegation copies `options` and the child runs A/a.

**Case B (cold recovery)** — mechanism CONFIRMED, trigger conditional. Resume re-seeds `options` from the *current shared deployment default* while the parent's route is restored from its own log. These agree only when the default still equals that session's logged route. Because `session.selectModel` also writes the shared default (`packages/host/apiproxy/src/api-proxy.ts:2316`), the common single-session case self-heals after a restart; the divergence persists when the default has since moved (another session picked a different model, the Models page changed it) **or when that save failed silently** — a launchd-run `dsh web` with a non-writable `$DSH_HOME/settings.yaml` gets exactly one `logger.warn` at `packages/host/apiproxy/src/api-proxy.ts:2317-2321` and then behaves like Case B forever. I could not determine which of these applies to the reporter; see Open questions.

**Why it is a money bug and not a cosmetic one.** The layer that decides the *model* and the layer that decides the *credential* are the same string, resolved at different times by different code:

- `provider` is a registered adapter route: `packages/llm/llm-deepseek/src/index.ts:256` (`ctx.llm.registerAdapter([PROVIDER], adapter)`), `packages/llm/llm-pi-ai/src/index.ts:270` (`registerAdapter(routes, adapter)`).
- Each route resolves its **own** credential reference and endpoint: `packages/llm/llm-deepseek/src/index.ts:184` (`apiKeyEnv: credentialRef(...)`), `:225-245` (`resolveApiKey`), `:284` (`authorization: Bearer …`); pi-ai resolves per-profile at `packages/llm/llm-pi-ai/src/config.ts:355` and `packages/llm/llm-pi-ai/src/index.ts:175-197`.
- The repo names this consequence itself, in a comment about *not* falling back to ambient keys: "**billing another tenant for a request the deployment meant to authenticate differently**" — `packages/llm/llm-pi-ai/src/index.ts:180-184`.
- And again in an Agent Note: the provider id "is the stem of the derived credential reference" (`<ROUTE>_API_KEY`) — `.agents/notes/implemented/architecture/2026-08-04-declaring-a-provider-from-the-models-page.md:27`.

So `agent.options.provider` is not a display preference. It selects the API key, the base URL, and therefore the account charged. A stale `provider` on a child is a silent cross-tenant charge with no error, no warning, and no UI signal — the parent's own header looks correct in the GUI the whole time. In a single-provider deployment the same divergence is merely a wrong model (still a cost difference between e.g. a pro and a flash tier); in the reporter's multi-provider setup it is a wrong invoice.

### What the correct inheritance rule should be, per this repo's own conventions

The repo has already answered this question twice, for sibling facts, and both times chose the parent's **live** state over its creation snapshot:

- **Preset composition.** `.agents/notes/implemented/bug-fix/2026-08-10-child-agents-join-their-parent-preset.md:21`: `childSessionMeta()` records the joined preset id "read from the **parent's live scope chain rather than from its header**, because a parent that switched preset while blank runs on the newer composition while its header still names the older one." The code comment repeats it at `packages/subagent/subagent/src/child-agent.ts:92-96`, and the README at `packages/subagent/subagent/README.md:45`. **This is the same bug shape, in the same file, decided the other way — nine lines above the defective function.**
- **Delegation policy.** `packages/subagent/subagent/README.md:61` and `.agents/notes/implemented/feature/2026-07-25-subagent-policy-inheritance.md`: `captureDelegatedPolicyOverrides()` (`packages/subagent/subagent/src/child-agent.ts:199-204`) reads the parent session's *explicit live override* via `sandboxPolicy.overrideOf(parent.session)` and pointedly never copies the deployment default.
- **The model layer's own rule.** `.agents/notes/implemented/feature/2026-08-07-default-model-follows-the-picker.md:23` and `.agents/notes/implemented/feature/2026-07-24-web-session-model-selector.md:13` both state the tiering explicitly: process-local selection → the session's own latest logged `request/header` → the deployment default. A subagent inheriting "the parent's route" must consume that same ladder, not a fourth thing.

Against the repo-wide conventions in `CLAUDE.md`:

- **Model-visible ⟺ logged** is *satisfied* in the narrow sense (the child logs the wrong route it actually used, so its history is reconstructable) but violated in spirit: the parent's live model-visible route is not the value the delegation reads, so the delegation decision is not derivable from the authoritative log. `.agents/notes/implemented/bug-fix/2026-08-10-child-agents-join-their-parent-preset.md:13` invokes exactly this rule for the preset half of the same problem.
- **"Explicit > implicit at package boundaries"** — "defaulting is an explicit `resolve(request): Spec` step in the owning implementation". `resolveChildAgentOptions()` *is* that resolve step; it currently resolves against the wrong input. The fix belongs there, not in a `?? default` at a call site.
- **"Prefer symmetry for parallel values; unexplained asymmetry usually signals a missed extraction."** Within one function, preset and policy read live state and the model route reads the snapshot, with no explanation. That is the tell.
- **Capability-seam roles.** `resolveChildAgentOptions()` lives in the Service Definition package `dsh-subagent`, shared by both in-process drivers — correct home for the rule; a Consumer-side or apiproxy-side patch would leave the other driver wrong and is the wrong role per `.agents/notes/implemented/architecture/2026-06-13-capability-seams.md`.

**No Agent Note has decided subagent model inheritance.** I searched `.agents/notes/**` for the function name, for model/route inheritance, and read every subagent note in `implemented/{feature,architecture,bug-fix}`. `2026-07-12-subagent-persona-tool-filter-and-depth.md` covers persona/toolFilter/maxDepth; `2026-07-25` and `2026-08-10` cover policy; `2026-08-10-child-agents-join-their-parent-preset.md` covers composition. The model route is the one inherited fact with no note and no stated rule — consistent with it having been written from the (now inaccurate) `Agent.options` JSDoc at `packages/core/agent/src/runtime-types.ts:67-68`.

The rule the fix should state: **a child inherits the route its parent's most recent model request actually used** — `parent.session.requestHeader()?.config` for `provider`/`model` — falling back to `parent.options` only when the parent has never made a request, and always yielding to an explicit per-request `agentOptions` override.

## Recommended next steps (concrete and ordered)

1. **Redirect, don't duplicate.** [#2470](https://github.com/deepseek-ai/deepseek-harness/discussions/2470) is the fourth report of the same defect and the only one with an incident-scale account. 2. **Fix the resolver — `packages/subagent/subagent/src/child-agent.ts:68-83`.** Prefer the parent's logged route over its creation options:
   - read `parent.session.requestHeader()?.config` and take `provider` / `model` from it when present;
   - fall back to `parent.options.provider` / `parent.options.model` when the parent has never issued a request (preserves the routeless-parent behavior pinned at `packages/subagent/subagent-in-process-driver/tests/subagent-in-process-driver.spec.ts:300-312`);
   - keep `requested` (per-call `agentOptions`) as the outermost override — unchanged precedence;
   - **do not** promote header `maxTokens` into the child's explicit options when the header marks it adapter-owned. `EpochHeader.adapterDefaults` already carries that flag (`packages/core/agent-loop/src/agent.ts:462-465`, `packages/llm/llm/src/call-config.ts:36-39`), and the loop's own restore logic at `packages/core/agent-loop/src/agent.ts:419-425` reads it. Promoting it would pin a child to one adapter's default forever. (This is the refinement [#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581)'s patch author already identified.)
   - update the JSDoc at `packages/subagent/subagent/src/child-agent.ts:59-66` to name the log as the authority, matching the preset paragraph at `:92-96`.

3. **Fix the durable descriptor — `packages/subagent/subagent/src/continuation.ts:413-414.**` It must snapshot the same resolved route, or a continuable child cold-resumes onto the stale one forever (`packages/subagent/subagent/src/continuation.ts:918-923`). Deriving both from the single resolver output is the symmetric form.

4. **Correct the misleading contract — `packages/core/agent/src/runtime-types.ts:67-68.`** `Agent.options` must be documented as the creation-time seed, with a pointer to `session.requestHeader()` as the authority for the route in force. This JSDoc is the most likely proximate cause of the defect and will re-create it in the next consumer otherwise.

5. **Decide the cold-resume seed — `packages/host/apiproxy/src/api-proxy.ts:1111-1115`, `:1659`.** With step 2 landed, delegation no longer depends on it, but `agent.options` still misreports a resumed session. Two coherent options: (a) leave it and rely on the log-first rule everywhere (minimal, matches how `selectionFor` already works), or (b) seed resume from `resolveSessionPreset`'s sibling — the session's own logged header — which would make `agent.options` honest again and match the preset resolution three lines above at `:1649-1656`. (a) is smaller; (b) removes the whole class. Either way this needs a stated decision, not silence.

6. **Consider surfacing the route in the delegation UI.** The reporter's real loss was that nothing was observable for 61 sessions. The child's `request/header` already records the truth; a subagent row showing its provider/model would have made this a five-minute discovery. Out of scope for the fix, worth its own discussion.

> ### 已确认：这是一个真实缺陷，且已有三个先前报告（含一份候选补丁）
>
> 感谢这份报告 —— 特别是 61 个会话和 ~7.7M token 的实测数据，这是目前把该问题的**扣费**后果讲清楚最完整的一份。你的定位是对的，我在 master 源码上逐行核对了三条论断，全部成立。
>
> **先说止血办法（无需等待修复）**
>
> 按优先级：
>
> 1. **把 `agent-default-model` 设成你真正想计费的那条路由。** 子 agent 的路由来自父 agent 创建/恢复时刻的部署默认值（`packages/host/apiproxy/src/api-proxy.ts:1111-1115`, `:1659`, `:1672`）。只要默认值与你实际使用的路由一致，分歧就消失。这是当前唯一能同时覆盖 Case A 和 Case B 的办法。
> 2. **在 GUI 里切换模型之后，先重开（或重启后恢复）该会话，再派发子 agent。** `session.selectModel` 会把选择同时写回共享默认值（`packages/host/apiproxy/src/api-proxy.ts:2316`），所以下一次 create/resume 才会带上新路由；当前这个进程内的父 agent 的 `options` 不会被更新。
> 3. **在部署里显式钉住子 agent 的路由。** `dsh-tool-subagent` 的 `agentOptions`（`provider` / `model`）会覆盖继承值（见 `packages/subagent/tool-subagent/README.md`）。它是静态的、不跟随选择器，但它把计费边界变成显式的 —— 在多供应商部署里这本身就值得。
> 4. **事后核账**：每个子会话自己的 `request/header` 事件记录了真正发出的 `provider`/`model`。这是判断某个子会话计到哪个账上的权威依据，不要看父会话的 GUI 显示。
>
> **关于 Case B，能否补充一点信息？**
>
> 冷恢复确实用部署默认值重新播种 `agentOptions`，而路由则从会话自己的日志恢复 —— 机制与你描述的一致。但因为 `selectModel` 也会把选择保存为默认值，单会话场景在重启后通常会自愈。你的复现稳定成立，说明保存那一步没有生效。两种可能：(a) 期间有别的会话/Models 页把默认值改回了 A/a；(b) 默认值**保存失败**了 —— launchd 跑的 `dsh web` 如果对 `$DSH_HOME/settings.yaml` 没有写权限，只会打一行 warn 就继续（`packages/host/apiproxy/src/api-proxy.ts:2317-2321`）。
>
> 麻烦贴一下：`settings.yaml` 里的 `agent-default-model:` 段，以及日志里是否出现过 `api-proxy: the model switch applies to this session but was not saved as the default`。如果是 (b)，那你其实同时踩中了第二个（可独立修复的）问题。
>
> **根因**
>
> 仓库里存在两个"当前模型"的表示：
>
> - `Agent.options` —— `agents.create()` / `resume()` 时冻结的快照。Web host 下它**永远**是那一刻的部署默认值。
> - 真正的路由 —— `agent/request` waterfall 的结果，也是写进日志 `request/header` 的值（`packages/core/agent-loop/src/agent.ts:437-472`），随时可通过 `session.requestHeader()` 读取。
>
> GUI 选择器、`session.selectModel`、冷恢复还原，全部作用于后者（`packages/core/agent/src/model-selection.ts:54-70`；`packages/host/apiproxy/src/api-proxy.ts:1154-1180`）。而 `resolveChildAgentOptions()`（源码在 `packages/subagent/subagent/src/child-agent.ts:68-83`，即你说的 `lib/index.js` 501-512）读的是前者。二者仅在"刚创建、默认值未变、第一次请求"时相等。
>
> 还有一条你没提到、但能解释 61 这个数字的放大路径：可续（continuable）子 agent 会把这条错误路由**固化进持久化 descriptor**（`packages/subagent/subagent/src/continuation.ts:413-414`），并在每次冷恢复时重新套用（`:918-923`）；而孙子 agent 从子 agent 的 `options` 继承，于是整棵子树都被污染。父会话自己始终是对的 —— 这正是它无声的原因。
>
> **为什么这是扣费问题而不是显示问题**
>
> `provider` 这个字符串同时决定模型**和凭据**：每条路由自带 `apiKeyEnv` 与 base URL（`packages/llm/llm-deepseek/src/index.ts:184`, `:225-245`, `:256`；pi-ai 见 `packages/llm/llm-pi-ai/src/index.ts:175-197`）。仓库自己在一处注释里就写过这个后果：*"billing another tenant for a request the deployment meant to authenticate differently"*（`packages/llm/llm-pi-ai/src/index.ts:180-184`）。所以陈旧的 `provider` = 用另一把 key、发往另一个端点、记到另一个账户上，且全程无报错。
>
> **正确的继承规则（仓库自己已经定过两次）**
>
> 同一个文件里，往上九行：子 agent 的 preset 是"从父 agent 的**活动 scope 链**读取，而不是从它的 header 读取"（`packages/subagent/subagent/src/child-agent.ts:92-96`，决策见 `.agents/notes/implemented/bug-fix/2026-08-10-child-agents-join-their-parent-preset.md:21`）。沙箱/审批策略同样读父会话的**活动**覆盖值（`captureDelegatedPolicyOverrides()`，`packages/subagent/subagent/src/child-agent.ts:199-204`）。唯独模型路由读的是创建快照，且没有任何 Agent Note 记录过这个选择 —— 我认为这只是照着 `Agent.options` 那句已经过时的 JSDoc（`packages/core/agent/src/runtime-types.ts:67-68`，写着"this agent's requests use"）写出来的。
>
> 正确规则应为：**子 agent 继承父 agent 最近一次模型请求实际使用的路由**（`parent.session.requestHeader()?.config`），父 agent 从未发过请求时才回退到 `parent.options`，显式的每次调用 `agentOptions` 始终优先。有一个细节需要注意：不要把 header 里由 adapter 提供的 `maxTokens` 默认值提升为子 agent 的显式选项（`adapterDefaults` 标记了它），否则会把子 agent 永久钉死在某个 adapter 的默认值上。

> ### Confirmed — real bug, and a duplicate of three earlier reports (one already has a candidate patch)
>
> Thanks for this — the 61 sessions and ~7.7M tokens make it the most complete account of the **billing** consequence so far. Your diagnosis is correct; I verified all three claims against master.
>
> **Immediate workarounds, in priority order:**
>
> 1. **Set `agent-default-model` to the route you actually want billed.** A child's route comes from the deployment default as of the parent's create/resume (`packages/host/apiproxy/src/api-proxy.ts:1111-1115`, `:1659`, `:1672`). Aligning the default removes the divergence, and it is the only workaround that covers both Case A and Case B.
> 2. **After switching model in the GUI, reopen (or restart-and-resume) the session before delegating.** `session.selectModel` also saves the choice as the shared default (`:2316`), so the *next* create/resume picks it up; the live parent's `options` are never updated.
> 3. **Pin the child's route explicitly** via `dsh-tool-subagent`'s `agentOptions` (`provider`/`model`) — an explicit override of inherited options (see `packages/subagent/tool-subagent/README.md`). Static, but it makes the billing boundary explicit.
> 4. **Audit by log, not by UI:** each child session's own `request/header` records the provider/model actually used. That is the authority for which account was charged.
>
> **On Case B — one question.** Cold resume does re-seed `agentOptions` from the deployment default while routing is restored from the session log, exactly as you describe. But since `selectModel` also writes that default, a single-session setup usually self-heals across a restart. Your reproduction being stable suggests the save is not landing. Either (a) another session or the Models page moved the default back to A/a, or (b) the save **failed silently** — a launchd-run `dsh web` without write access to `$DSH_HOME/settings.yaml` logs one warn and continues (`:2317-2321`). Could you post your `agent-default-model:` section and check the logs for `api-proxy: the model switch applies to this session but was not saved as the default`? If it is (b), you have hit a second, independently fixable problem.
>
> **Root cause.** There are two representations of "the current model": `Agent.options`, frozen at create/resume (always the deployment default under the Web host), and the live route — the `agent/request` waterfall result, logged as `request/header` (`packages/core/agent-loop/src/agent.ts:437-472`) and readable via `session.requestHeader()`. The GUI picker, `session.selectModel`, and cold-resume restoration all act on the second (`packages/core/agent/src/model-selection.ts:54-70`; `packages/host/apiproxy/src/api-proxy.ts:1154-1180`). `resolveChildAgentOptions()` (source: `packages/subagent/subagent/src/child-agent.ts:68-83` — your `lib/index.js` 501-512) reads the first.
>
> One amplifier you did not mention explains the 61: a continuable child freezes the wrong route into its **durable descriptor** (`packages/subagent/subagent/src/continuation.ts:413-414`) and re-applies it on every cold resume (`:918-923`), while grandchildren inherit from the child's now-wrong `options`. The parent stays correct throughout — which is why it is silent.
>
> **Why it is money and not cosmetics.** The `provider` string selects the model *and* the credential: each route carries its own `apiKeyEnv` and base URL (`packages/llm/llm-deepseek/src/index.ts:184`, `:225-245`, `:256`). The repo names the consequence in its own comment — *"billing another tenant for a request the deployment meant to authenticate differently"* (`packages/llm/llm-pi-ai/src/index.ts:180-184`).
>
> **The rule this should follow** is already settled twice in the same file: a child's preset is read "from the parent's live scope chain rather than from its header" (`packages/subagent/subagent/src/child-agent.ts:92-96`; `.agents/notes/implemented/bug-fix/2026-08-10-child-agents-join-their-parent-preset.md:21`), and delegated sandbox policy reads the parent session's live override (`:199-204`). Only the model route reads the creation snapshot, and no Agent Note ever decided that — most likely it was written from the now-inaccurate `Agent.options` JSDoc at `packages/core/agent/src/runtime-types.ts:67-68`. The fix: **inherit the route the parent's most recent request actually used** (`parent.session.requestHeader()?.config`), fall back to `parent.options` only for a parent that has never requested, keep explicit per-call `agentOptions` outermost — and do not promote adapter-owned `maxTokens` defaults into the child's explicit options.
>
> **Prior reports:** [#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581) (same root cause, 6 replies, candidate patch), [#1472](https://github.com/deepseek-ai/deepseek-harness/discussions/1472) (same billing symptom), [#2006](https://github.com/deepseek-ai/deepseek-harness/discussions/2006), [#2053](https://github.com/deepseek-ai/deepseek-harness/discussions/2053). Please add your data — especially the cold-recovery path and the cross-provider billing consequence, which none of the earlier reports have — to **[#1581](https://github.com/deepseek-ai/deepseek-harness/discussions/1581)**. There is still no upstream issue or PR, so the fix is unowned.
