## Research findings

### 1. The ordering defect the OP names is real

`packages/client/ui-settings-models/src/client/ProviderEditor.tsx:270-284` — the settings write gates the credential write:

```ts
if (ops.length > 0) {
  const response = await api.settings.mutate({ ns, ops, expectedRevision })
  if (!response.result.ok) {
    return response.result.error.code === 'settings-conflict'
      ? t('conflict')
      : response.result.error.message
  }
  ...
}
if (keyValue.length > 0) {
  const stored = await api.credentials.set({ ref: keyRef, value: keyValue })
  if (!stored.result.ok) return stored.result.error.message
}
```

A failed `settings.mutate` returns at `:272-276`, so `api.credentials.set` at `:282` never executes and `.credentials.yaml` stays unchanged. **[CONFIRMED]**

The most reachable trigger is a stale optimistic revision: `expectedRevision` is captured once at card mount (`ProviderEditor.tsx:157`) from `namespace.revision`. Any settings change from another tab, another card, or the file watcher between mount and save yields `settings-conflict`. **[PLAUSIBLE]**

The same ordering, with the same early return, exists in the create path at `packages/client/ui-settings-models/src/client/CustomProviderCard.tsx:145-166` — though that one deliberately latches `setCommitted(true)` (`:158`) so a retry resumes at the credential write. `ProviderEditor` has an analogous baseline advance at `:277-279`. So both cards are designed for a *reported* partial failure plus retry, not for a silent drop.

### 2. The "silent / no UI feedback" characterization does not hold

- `applyOnce`'s return value is a failure message; `apply` stores it via `setFailure(failure)` at `ProviderEditor.tsx:293-296`.
- It renders as an error paragraph at `ProviderEditor.tsx:485`.
- The `settings-conflict` branch uses `t('conflict')`, and that copy key exists in **both** locales — `packages/client/ui-settings-models/src/client/locales.ts:30` (en) and `:130` (zh: 「这张卡片打开期间，这些设置已被其他地方改动。请关闭后重新打开，在当前值上编辑。」). It is not an empty/missing string. **[CONFIRMED]**
- Host-side credential rejections are mapped to a `credential-rejected` envelope carrying the provider's message — `packages/host/apiproxy/src/api-proxy.ts:3336-3348` — so they reach the card as text too.
- A test asserts the shadowed-write message is displayed: `packages/client/ui-settings-models/tests/components.client.spec.tsx:1053-1062` ("surfaces a shadowed credential write on the card").

So the file-not-updated half is real; the no-feedback half is **REFUTED**.

### 3. No code path writes the credentials file during a model switch

Repo-wide, `credentials.set` / `credentials.unset` have exactly three product call sites:

- `packages/client/ui-settings-plugins/src/client/web-search-card-controller.ts:174` (web-search key)
- `packages/client/ui-settings-models/src/client/CustomProviderCard.tsx:163` (create provider)
- `packages/client/ui-settings-models/src/client/ProviderEditor.tsx:282` (edit provider)
- plus `packages/client/ui-settings-models/src/client/ModelsSection.tsx:102` (`unset`, on provider removal)

The model-selection UI (`packages/client/ui-model-selection/src/client/`: `index.ts`, `directory.ts`, `service.ts`, `ModelSelect.tsx`, `slots.ts`) contains **no** credential call whatsoever. `DeepSeekOnboardingDialog.tsx` likewise contains no `credentials.set`.

The file is therefore user-owned and written **only** from the Models/plugins settings surfaces, never from switching a model. The briefing's stated mechanism is **REFUTED**.

### 4. How a provider's key slot is selected

`packages/client/ui-settings-models/src/client/ProviderEditor.tsx:132-138`:

```ts
function refFor(namespace: SettingsNamespaceView, path: readonly string[], provider: string): string {
  const profile = getPath(namespace.value, path)
  const named = ... (profile as { apiKeyEnv?: unknown }).apiKeyEnv ...
  return typeof named === 'string' && named.length > 0 ? named : deriveKeyRef(provider)
}
```

`packages/client/ui-settings-models/src/client/store.ts:69-71`:

```ts
export function deriveKeyRef(provider: string): string {
  return `${provider.toUpperCase().replace(/[^A-Z0-9]+/g, '_')}_API_KEY`
}
```

So the slot is the profile's own `apiKeyEnv` when present, else derived from the provider route id.

**Can provider A's key land in provider B's slot?**

- From harness-derived refs: **REFUTED**. Custom route ids are constrained to `/^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$/` (`CustomProviderCard.tsx:47`) — lowercase alphanumerics with single internal hyphens, no dots, no doubled separators. Under that alphabet `deriveKeyRef` is injective (hyphen→underscore, one-for-one), so two distinct valid routes cannot derive the same ref.
- From a **hand-written `apiKeyEnv`**: **CONFIRMED as possible**. Nothing prevents a user from setting two profiles' `apiKeyEnv` to the same name (e.g. both to `DEEPSEEK_API_KEY`). The store is keyed by ref, so saving one provider's key then overwrites the other's. This is the only real cross-provider clobber path, and it is user-authored configuration, not harness behavior.
- Deletion is guarded against this: `ModelsSection.tsx:135-139` only passes a `credentialRef` to `unset` when `row.apiKeyEnv === deriveKeyRef(row.entry.provider)` and the credential is configured and writable — so removing a provider never unsets a hand-shared slot.

`OPENCODE_GO_API_KEY` specifically is exactly `deriveKeyRef('opencode-go')`. **[CONFIRMED]** as the derivation; its appearance in the briefing traces to the OpenCode Go thread, not to 2363.

### 5. The credentials file schema is a flat ref→string map, not keyed by provider

`packages/credentials/credentials-local/src/index.ts:29-34` (module doc, verbatim):

> The document holds nothing but credentials, which is why it is a strict `CredentialRef`-to-string mapping rather than a dotenv file: a store the Harness owns and never materializes into the environment cannot also serve as the user's environment layer; a store that doubled as the environment layer would shadow non-secret entries behind its precedence, making them silently unreachable.

Path: `$DSH_HOME/.credentials.yaml` (`:52`, `CREDENTIALS_FILENAME`), created and replaced at mode `0600`, and refused outright if group/other bits are set (`assertOwnerOnly`, `:~90-120`). A `CredentialRef` is a POSIX shell identifier matching `/^[A-Za-z_][A-Za-z0-9_]*$/` (`packages/credentials/credentials/src/index.ts:17,22-28`).

I did **not** find any provider-id-keyed structure. Any schema shaped like `deepseek: {apiKey: ...}` would be an invention.

### 6. Credential precedence — the strongest explanation for "file unchanged + still 401"

`packages/credentials/credentials-local/src/index.ts:2-18` (module doc, verbatim):

```text
inherited process environment      (read-only, wins)
> $DSH_HOME/.credentials.yaml      (provider-managed, writable)
> <invocation cwd>/.env            (read-only fallback)
> $DSH_HOME/.env                   (read-only fallback)
```

Implementation: `resolve` at `:309-317` returns `{source:'env'}` first; `describe` at `:319-327` returns `{configured:true, source:'env', writable:false}` when the launch environment supplies the ref.

Consequences on the settings card, when the provider's `apiKeyEnv` names a variable that is also exported in the shell that launched `dsh`:

- `keyLocked = keyState?.writable === false` (`ProviderEditor.tsx:315`)
- the key input is rendered **disabled** (`:374`) with placeholder `keyEnvLocked` = 「由启动环境提供（只读）」 (`locales.ts:136`)
- so `keyDraft` stays empty → `keyValue.length === 0` (`:212`) → the `credentials.set` at `:282` is skipped → **the file is never written**
- and requests keep using the stale environment value → **`401` persists**
- if nothing else on the card changed, `ops.length === 0`, `applyOnce` returns `undefined`, and `apply` calls `props.onClose(true)` (`:298`) — the card closes as a success with no message.

That last combination is the one genuinely feedback-free path I found, and it reproduces all three of the OP's observations at once. Asserted by test `packages/client/ui-settings-models/tests/components.client.spec.tsx:1064-1075` ("locks the key input when the launch environment provides the credential").

If instead the field is enabled (e.g. `describe` failed, which the card deliberately tolerates — `ProviderEditor.tsx:176-189`, test at `components.client.spec.tsx:1077-1087`), the write is attempted and the provider rejects it explicitly: `assertUnshadowed` at `credentials-local/src/index.ts:410-416` throws `"…is supplied read-only by the launching environment, so set would be shadowed; unset it in the shell you start dsh from instead"`, called from `write()` at `:374,381`. Unit-covered at `packages/credentials/credentials-local/tests/local.spec.ts:329-339`.

I initially suspected the documented shadow rejection on `set`/`unset` (`packages/credentials/credentials/src/index.ts:85-98`) was undocumented-but-unimplemented, since `set` at `credentials-local/src/index.ts:333-338` has no visible check. It is implemented one level down in `write()`. That hypothesis is **REFUTED**.

## Root cause

Two distinct defects sit behind the report; the OP identified one of them and mis-characterised its symptom.

**Primary (best fit for all three observations): launch-environment shadowing.** For a provider whose `apiKeyEnv` names a variable exported in the shell that started `dsh`, the inherited process environment outranks the managed store (`credentials-local/src/index.ts:2-18,309-317`). The card correctly locks the key input (`ProviderEditor.tsx:315,374`), so no key is ever submitted, nothing is written to `.credentials.yaml` — matching "文件不会更新" — and the stale environment value keeps producing `401`. When no other field changed, the card closes reporting success with no message, matching "UI 也无任何提示". The user's "correct key" never left the browser.

**Secondary (real, and what the OP actually traced): the settings-then-credentials ordering.** `ProviderEditor.applyOnce` aborts before the credential write whenever `settings.mutate` fails (`ProviderEditor.tsx:270-284`), most reachably via a stale `expectedRevision` producing `settings-conflict`. This genuinely leaves the correct key unwritten. It is **not** silent — `t('conflict')` is defined in both locales and renders at `:485` — but it does discard the typed key, and the fix is worth making regardless.

The briefing's model-switch-rewrites-the-file mechanism is **REFUTED**: no credential writer exists anywhere on the model-switch path.
