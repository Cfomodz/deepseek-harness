## What they do well

These are not courtesies — each one is a thing most third-party harness plugins get wrong, checked against this checkout.

1. **The gap they identified is real.** `packages/jobs/jobs-local/src/index.ts` contains no persistence of any kind — a search for `persist`, `sqlite`, `writeFile`, or `fs.` returns nothing. The first-party job registry is purely process-local, exactly as `dsh-witness`'s README claims. This is not a solved problem being re-solved.

2. **Registrations are effects, correctly, in all four plugins I read.** `ctx.effect()` for teardown at `WitnessJobRegistry.ts:67`, `dsh-schedule/src/plugin.ts:32`, `dsh-anchor/src/plugin.ts:133`. This is the repo's central plugin rule and it is honored without being told.

3. **The waterfall contract is honored.** `dsh-anchor/src/plugin.ts:76-94` and `:97-121` both `await next()` **first**, then do their own work, then return the downstream decision. That matches `docs/cordis-primer.md#cordis-waterfall-semantics` and the `AGENTS.md` rule that a listener returning without `next()` short-circuits the chain. The comment at `:77` ("先放行——拦截权归官方 guard") shows the intent was deliberate, not accidental.

4. **Optional services use `ctx.get()`.** `job-host.ts:62, 66` and `schedule-tools.ts:11-12` use `ctx.get('agents')` / `ctx.get('jobs')` / `ctx.get('tools')` rather than the topology-sensitive property proxy — the exact rule in `packages/AGENTS.md`.

5. **Function-plugin export form is correct.** `schedule-tools.ts:7-10` exports `name` / `inject` / `apply` with no default export, avoiding the namespace-drop failure documented in `docs/postmortem/0001-acp-default-export-drops-inject.md`.

6. **`exec.arguments` was researched, not guessed.** `dsh-anchor/src/plugin.ts:37-41` reads `exec.arguments` with an `exec.args` fallback and cites its source. It is right: `ToolExecutionInput.arguments` at `packages/core/tools/src/index.ts:317`.

7. **The honest-boundaries sections are genuinely honest.** `dsh-witness` README lines 117-122 disclose that arbitrary native code can self-rescue past the ACL layer; `schedule-core` README lines 59-66 disclose at-least-once, no backlog replay, no cron, single-machine only. Both state "数天级断网长跑未实测，不声称" — declining to claim something untested. The mid-thread correction admitting CI was red at posting time is the same instinct.

8. **They read the first-party package before writing theirs.** `schedule-core`'s `every_seconds ≥ 300` is annotated "对齐官方下限", and the first-party floor is indeed five minutes (`packages/schedule/schedule/README.md`, `every_seconds` intervals "of at least five minutes"). Their at-least-once disclosure mirrors first-party's documented "Narrow crash duplicate window". That alignment is deliberate and worth crediting.

9. **The Linux bwrap profile is well-constructed.** `detach-runner-linux.cjs:79` orders `--ro-bind / /` → `--tmpfs /tmp` → `--ro-bind jobDir jobDir`, with `--unshare-all --share-net`. The comment at `:76` explains `--share-net` as a concession to unprivileged CI where netns setup returns EPERM. That is a real constraint, correctly diagnosed.

10. **Shell quoting is done properly in the runner** — `q()` at `detach-runner-linux.cjs:17` implements correct POSIX single-quote escaping.

## Findings

### F1 — CONFIRMED: `schedule_create` with the default `action: 'remind'` can never deliver

The highest-value finding, and a small fix.

`schedule-tools.ts:51` constructs the input with `createdBy` hardcoded:

```ts
let input: ScheduleInput = { prompt: String(a.prompt ?? ''), rule: 'after', action, createdBy: undefined }
```

Lines 54, 57, 61 and 66 each rebuild `input` by spreading `...input`, and none of them ever sets `createdBy`. The core persists what it is given — `input.createdBy ?? null` at `schedule-core/src/ScheduleRegistry.ts:108`, read back as `createdBy: r.created_by ?? undefined` at `:142`. Delivery then gates on exactly that field, `dsh-schedule/src/job-host.ts:128-129`:

```ts
const owner = rec.createdBy !== undefined ? agents()?.get(rec.createdBy) : undefined
if (owner === undefined) return 'retry'   // 会话不 live：保持 overdue（下次周期重试）
```

So for every schedule created through the tool, `rec.createdBy` is `undefined`, `owner` is `undefined`, and `deliverReminder` returns `'retry'` unconditionally — forever. The record stays `overdue` and is re-attempted each dispatch cycle. `action: 'job'` is unaffected, because `executeJob` never reads `createdBy`. Since `remind` is the default (`schedule-tools.ts:50`, `(a.action ?? 'remind')`), the default path is the broken one.

The fix is available in-tree: tool `execute` receives a second argument, `execute(args: unknown, exec: ToolRunContext)` (`packages/core/tools/src/index.ts:235`), and `ToolRunContext extends ToolExecution` (`:404`) which carries `readonly agent?: Agent` (`:329`). First-party precedent for using it: `packages/jobs/tool-jobs/src/index.ts:334`, `ctx.jobs.wait(id, timeout, exec.agent, exec.signal)`. The registry lookup keys on a session id — `get(id: SessionId): Agent | undefined` at `packages/core/agent/src/index.ts:583`.

*Confidence:* the code path is CONFIRMED by reading. That it manifests as a never-firing reminder at runtime is PLAUSIBLE — I did not execute it.

### F2 — CONFIRMED: witness jobs are invisible to the harness's job tools

`WitnessJobRegistry` publishes itself on a private key, `ctx.provide('witness-jobs', reg)` (`WitnessJobRegistry.ts:391`). It does not extend the first-party seam and does not register `ctx.jobs`.

The first-party seam is an abstract service on `ctx.jobs` (`packages/jobs/jobs/src/index.ts:29-33`, class at `:62-71`), and the model-facing tools bind to it exclusively: `tool-jobs` declares `inject = ['tools', 'jobs', 'systemPrompt']` (`packages/jobs/tool-jobs/src/index.ts:22`) and reads only `ctx.jobs` (`:189`, `:260`, `:334`, `:356`). Consequence: `job_output`, `job_list` and `job_kill` never see a witness job.

Two related mismatches. The seam fences every read on the calling agent — `list(caller?: Agent)`, `get(id, caller?)`, `read(id, caller?)`, `kill(id, caller?, reason?)` (`packages/jobs/jobs/src/index.ts:90-120`), documented at `:47-49` as "Owned-job access is fenced by the owner's session id". Witness's equivalents take no caller at all (`:185`, `:267`, `:336`, `:365`), so there is no owner isolation. And the return type is reached by casting rather than construction — `{ id: id as never, kind: kind as never, ... } as JobSnapshot` at `:299`.

Worth noting the suite is internally inconsistent here, in the good direction: `dsh-schedule`'s job host *does* file its work into the first-party registry via `ctx.get('jobs')` and `jobs.start({...})` (`job-host.ts:66, 91`). The pattern already used in `dsh-schedule` is the one `dsh-witness` would need.

### F3 — CONFIRMED: the "rebuildable cache" holds state that cannot be rebuilt

The README's strongest durability argument is the two-source split — directory is truth, SQLite is a disposable index (README line 21: "SQLite=可重建的只读索引缓存…缓存坏了永远不挡恢复——从目录重建即可").

Two pieces of state live only in that "cache" and are not derivable from the directory tree:

- **Job id allocation.** `nextId()` (`WitnessJobRegistry.ts:210-213`) increments the `job_seq` table and returns `${kind}-${count}`. Nothing consults existing directories.
- **Output cursor.** `out_cursor` (`:60`, written `:202-204`) is the sole record of how far `read()` has consumed.

Losing or rebuilding the db therefore resets the counter to 1 while `jobs/pwsh-1/` still exists on disk. `start()` then does `fs.mkdirSync(path.join(d, 'state'), { recursive: true })` (`:306`) — recursive mkdir succeeds silently on an existing directory — and proceeds to overwrite `spec.json` (`:309`) and write a fresh `state/running` marker (`:311-313`) inside the earlier job's directory. Cursor loss separately re-reads output from byte 0, which is the exact "不重不漏" property claim A-03 rests on.

*Confidence:* the code paths are CONFIRMED. The resulting directory collision is PLAUSIBLE — not executed.

### F4 — CONFIRMED: the third adoption evidence is Windows-only in the witness core

The headline adoption claim is three evidences — lock contents, process liveness, and process start-time comparison to defeat PID reuse (README line 50). The third one is `procStartSec()` (`WitnessJobRegistry.ts:251-257`), which unconditionally shells out to PowerShell:

```ts
const r = spawnSync('powershell', ['-NoProfile', '-Command', `[int](Get-Date -Date (Get-Process -Id ${pid}).StartTime.ToUniversalTime() -UFormat %s)`], ...)
```

On Linux or macOS that throws, is caught, and returns `undefined`. The caller then skips the check entirely — `lockAlive()` at `:246`:

```ts
if (cur !== undefined && cur !== Number(m[2])) return false   // PID 复用
```

With `cur === undefined`, liveness rests on `process.kill(pid, 0)` alone, so the defense silently degrades from three evidences to two off Windows.

This is a wiring gap, not a knowledge gap: the suite already contains all three platform formulas. `dsh-schedule/src/job-host.ts:35-58` implements win32 PowerShell, Linux `/proc/<pid>/stat` + `btime`, and macOS `ps -o lstart`; `detach-runner-linux.cjs:21-28` has the same `/proc` formula. Only `WitnessJobRegistry.procStartSec` was left Windows-shaped.

### F5 — CONFIRMED: witness's own spawn path never reaches the cross-platform runners

`WitnessJobRegistry.start()` resolves the runner with no platform switch and passes no mode argument (`:317-321`):

```ts
const runnerPath = path.join(path.dirname(fileURLToPath(import.meta.url)), '..', 'detach-runner.cjs')
...
spawn(process.execPath, [runnerPath, d, outFile, exitFile, cmdB64], { detached: true, stdio: 'ignore', windowsHide: true })
```

Four arguments, and `detach-runner.cjs` hardcoded — which is the Windows runner, and the only runner `dsh-witness` ships (`package.json` `files` and `exports['./runner']`). Compare `dsh-schedule/src/job-host.ts:29-32`, which does switch (`detach-runner.cjs` / `detach-runner-macos.cjs` / `detach-runner-linux.cjs`) and appends the mode at `:78` (`if (process.platform === 'linux') runnerArgs.push('bwrap')`).

This matters because the Linux runner's sandbox choice is driven by that fifth argument, `detach-runner-linux.cjs:18`:

```js
const useBwrap = (mode === 'bwrap') && sh('which bwrap').length > 0
```

Absent it, `useBwrap` is false, `hardenImmutables` becomes true (`:47`), and the runner attempts `chattr +i` — which needs `CAP_LINUX_IMMUTABLE`, as the comment at `:45` itself notes, and fails closed to `EXIT:-998` for an unprivileged user (`:72`, `:65-71`). So the platform backends appear reachable only through `dsh-schedule`, not through `dsh-witness` directly.

*Confidence:* the wiring facts are CONFIRMED from code. The runtime consequence of running the Windows `.cjs` on Linux is PLAUSIBLE — I did not read `detach-runner.cjs`.

### F6 — CONFIRMED: the sandboxes are an evidence fence, not the harness's sandbox seam, and their polarity differs per platform

This is the finding I would most want the author to see, because the word "sandbox" is doing two different jobs.

What these backends protect is the job's **own bookkeeping** — `lock`, `exit.txt`, `out.log` — so a task cannot forge its own completion record. That is a coherent and unusual goal, and on that axis the three platforms genuinely are comparable.

What they do *not* do is constrain what the task may touch elsewhere, and here the two Unix platforms are near-opposites:

- **Linux, bwrap mode** (`detach-runner-linux.cjs:79`): `--ro-bind / /` plus `--tmpfs /tmp` — the entire filesystem is read-only and only `/tmp` is writable. Strictly *tighter* than the harness's own `workspace-write`.
- **macOS** (`macos-backend.mjs:69`): `(version 1) (allow default) (deny file-write* (subpath "${real}"))` — allow-by-default, denying writes only inside the job directory. The task may write anywhere else in the user's account.

So residual write authority ranges from "nothing outside /tmp" to "the whole home directory" depending on platform. The README's "三平台同级 / 能力对等" is defensible for evidence integrity and not for confinement; saying which axis the parity claim covers would close the gap.

Separately, this layer is orthogonal to the harness's own sandbox seam. That seam derives its allow-list from one function — `writableRoots()` at `packages/sandbox/sandbox/src/roots.ts:52-55`, empty exactly under `read-only` — and selects a per-platform runner chain in `packages/sandbox/sandbox-local/src/index.ts` (bwrap → landlock on Linux, seatbelt on darwin, windows-acl on win32; `:141` for the runner union, bwrap probe at `:67-69`). Neither witness nor the scheduler consults the session's `sandbox/mode`: a job command goes to `bash -c cmd` (`detach-runner-linux.cjs:80-81`) with no reference to the session policy. A composition that mounts these alongside the shipped sandbox gets a second, independent confinement that does not report through the harness's permission surface. That is the same shape as the composition defect in [#2422](2422.md) — not the same bug, but the same trap: the enforcing layer and the advertised layer are different objects. Documenting "this is a per-job evidence fence, and it neither reads nor replaces `sandbox/mode`" would prevent the whole misunderstanding.

### F7 — CONFIRMED: the three scheduler tool names collide with the first-party ones

`dsh-schedule` registers `schedule_create`, `schedule_list`, `schedule_delete` (`schedule-tools.ts:15, 74, 87`). The first-party `@deepseek-ai/dsh-schedule` registers exactly the same three names (`packages/schedule/schedule/src/tools.ts:318, 400, 420`). `ToolRegistry.register` documents that "duplicates within one layer and the reserved `run_code` name fail" (`packages/core/tools/src/index.ts:1030-1036`), so mounting both in one layer throws rather than silently shadowing.

The tool description at `schedule-tools.ts:1` says the names are deliberate — "协议对齐官方名字" — which is a reasonable drop-in-replacement stance. It is worth stating explicitly in the README that it *replaces* rather than *accompanies* the first-party plugin.

### F8 — CONFIRMED: the suite does not write the session log from another process

Checked specifically because it is the failure mode behind the `seq gap in committed region` reports ([#2359](2359.md)): JSONL appends use a bare append + fsync (`packages/session/session-persistence-jsonl/src/index.ts:651-677`) positioned by an **in-memory** cursor (`packages/session/session-persistence/src/coordinator.ts:1354-1359`) with no cross-process lock, so a second writer corrupts the log (`format.ts:364-373`).

Neither plugin goes near it. `dsh-witness` writes only its own job directories and its own SQLite. `dsh-schedule` keeps schedule state in SQLite and delivers through `owner.followup?.(...)` on a **live, in-process** agent, returning `'retry'` when the agent is not live (`job-host.ts:127-140`) — the same mechanism the first-party plugin uses (`packages/schedule/schedule/src/runtime.ts:275`). Cross-process coordination happens in SQLite via lease-claim, never in the session log. That is the right call and it should be said out loud in the README, because "cross-restart persistence" is precisely the feature that usually gets this wrong.

The trade-off worth naming: because the state lives outside the session log, it is not reconstructable from it. The repo convention is "Model-visible ⟺ logged — anything that reaches a model request must be reconstructable from the session log; a new model-visible input requires a session event" (`AGENTS.md`, Conventions). A dispatched reminder does reach the model. That is a design difference, not a defect, and it is exactly why the first-party plugin chose `schedule/change` events and accepted session-local delivery as the cost.

### F9 — CONFIRMED: `edit` is branched on but never actually reconciled

`dsh-anchor/src/plugin.ts:48-58` reconciles `write`, `edit` and `create_file`, but the branch body requires `args.content`:

```ts
const content = typeof args?.content === 'string' ? args.content : undefined
if (p0 !== undefined && content !== undefined) { ... envChecked: true }
```

In this checkout `write` takes `file_path` + `content` (`packages/fs/tool-fs/src/write.ts:70`; arguments visible at `packages/fs/tool-fs/tests/tools.spec.ts:163`), but `edit` takes `file_path` + `old_string` + `new_string` (`packages/fs/tool-fs/src/edit.ts:84`; `tests/tools.spec.ts:165`) and has no `content`. So `edit` always falls through to the generic `{ expect: 'ok', observed: 'ok', envChecked: false }` at `:60`, meaning environment reconciliation covers `write` only. A repo-wide search for `name: 'create_file'` under `packages/` returns nothing, so that third name matches no tool at this commit.

Reconciling `edit` is still possible — read the file after the call and confirm `new_string` is present and `old_string` is gone — it just needs a different predicate than `content`.

### F10 — PLAUSIBLE: anchor's cross-check state is module-global

`activeAnchors` (`dsh-anchor/src/plugin.ts:30`) and `let prevTarget` (`:32`) are declared at module scope, outside `apply()`. The WeakMap is keyed by the `exec` object so it stays correct, but `prevTarget` is a single shared slot. Two mounted anchor instances (two agents, or an HMR reload) would interleave writes at `:115-116` and read each other's target at `:107-113`, which could attribute a `DIVERGED` verdict to the wrong anchor tree. Moving both inside `apply()` makes each instance independent. Consequence not reproduced.

### F11 — CONFIRMED (low severity): shell quoting is right in the runner and missing in the backends

`detach-runner-linux.cjs:17` defines proper escaping and uses it throughout (`:51-52`, `:60`, `:66`, `:88`, `:93`). The two backends interpolate raw paths into a `sh -c` string instead: `sh(\`chattr +i '${t}'\`)` at `linux-backend.mjs:31`, also `:42` and `:49` (`chmod 555`); and `chmod 444` / `chflags uchg` at `macos-backend.mjs:28-29`, `:38`, with `ls -lO` at `:46` and `chflags nouchg` at `:56`. Both route through `execFileSync('sh', ['-c', cmd])` (`linux-backend.mjs:17`, `macos-backend.mjs:12`).

Job directory paths derive from `jobsRoot` plus an id of `${kind}-${count}` (`WitnessJobRegistry.ts:212`), where `kind` comes from the job spec, and `jobsRoot` is user-configured. A single quote anywhere in that path breaks the command or injects into it. The fix already exists in the same suite — reuse `q()`.

### Not a finding — checked and cleared

I initially suspected the three `tools.register(...)` calls at `schedule-tools.ts:14, 73, 86` leaked, because the returned disposer is discarded while the first-party plugin collects them (`packages/schedule/schedule/src/tools.ts:317, 399, 419`). **That is wrong.** `ToolRegistry.register` is internally effect-scoped — it returns `this.layers.effect(this.ctx, layer => layer.tools.insert(name, definition), { label: 'tools.register()' })` (`packages/core/tools/src/index.ts:1057-1061`) — so disposing the registering fiber removes the tool regardless. Likewise `ctx.provide(name, value)` is effect-scoped in vendored cordis (`vendor/cordis/src/reflect.ts:46, 277, 304`), so discarding its return in `WitnessJobRegistry.ts:391`, `dsh-schedule/src/plugin.ts:31` and `dsh-anchor/src/plugin.ts:132` is also correct. Recorded so this does not get re-raised as a defect.

## Overlap with first-party packages

Stated plainly, because "does this duplicate something that already ships" is the least obvious thing from outside the repo.

**`packages/jobs/` — the seam exists; the durability does not.** Three packages ship: `@deepseek-ai/dsh-jobs` (the abstract `ctx.jobs` registry, `packages/jobs/jobs/src/index.ts:62`), `dsh-jobs-local` (process-local implementation), `dsh-tool-jobs` (model-facing tools). Searching `packages/jobs/jobs-local/src/index.ts` for `persist`, `sqlite`, `writeFile` or `fs.` returns nothing — **there is no crash-surviving job store in-tree**. `dsh-witness` is filling a real hole. What it duplicates is not the durability but the *seam*: it re-declares a registry rather than subclassing `JobRegistry`, which is why F2 happens. Subclassing would inherit `ctx.jobs`, the model tools, owner fencing, `onJobDone`/`onJobsChanged` and controller attachment for free.

**`packages/schedule/` — the package exists, with the same three tool names, and a deliberately different scope.** `@deepseek-ai/dsh-schedule` (`packages/schedule/schedule`, version `0.1.0-rc.5`) implements `after` / `at` / `every_seconds` reminders with the same five-minute floor. Its store is the **session event log** — a strict version-1 `schedule/change` create/delete/dispatch union folded on replay — not a database. Its README's Known Limitations are explicit that this is the boundary: *"Session-local delivery only — a reminder runs on time only while its original Session is live; a cold Session receives no external notification and processes an overdue record only after resume."*

That single sentence is the entire justification for `dsh-schedule` existing, and it is a good one: cross-restart, cross-session dispatch is documented first-party non-goal territory, and `schedule-core` covers it with SQLite plus lease-claim. The duplication is confined to the three tool names (F7) and to re-deriving clock discipline (RFC3339, IANA zones, DST) that `packages/schedule/schedule/src/domain.ts` already implements in 807 lines.

**`packages/sandbox/` + `packages/fs/` + `native/` — different layer entirely, as covered in F6.** The first-party seam owns mode vocabulary (`read-only` / `workspace-write` / `danger-full-access`), a single allow-list function (`roots.ts:52-55`), an OS-runner chain per platform (`sandbox-local/src/index.ts`, with the landlock rung imported from `@deepseek-ai/node-addon-landlock-run` at `:31-33`), and a separate tool-layer policy check in `packages/fs/fs-sandbox`. The suite's backends do not implement, extend, or consult any of it. They are a per-job evidence fence. Both can coexist; neither substitutes for the other; the README should say so.

**`packages/session/` — untouched, correctly (F8).**

**Naming.** The repo convention is that every npm package is `@deepseek-ai/dsh-<name>` (`AGENTS.md`, Conventions). The suite publishes unscoped `dsh-witness` and `dsh-schedule`, and `schedule-core` under `@wang--lin--chang/`. An unscoped `dsh-schedule` on npm sitting beside the first-party `@deepseek-ai/dsh-schedule` — same three tool names, different store, different delivery guarantees — is a confusion worth pre-empting in the README. (Same class of ambiguity as `dsh-shelf` in [#2359](2359.md).) Package naming and any question of official association are maintainers' calls, not ours.

> - **Witness jobs are invisible to the built-in job tools.** `ctx.provide('witness-jobs', reg)` (`WitnessJobRegistry.ts:391`) doesn't register `ctx.jobs`, and `tool-jobs` injects `['tools','jobs','systemPrompt']` and reads only `ctx.jobs` (`packages/jobs/tool-jobs/src/index.ts:22,189,334`) — so `job_output` / `job_list` never see them.
