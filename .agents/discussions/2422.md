## Research findings (each with a path:line or URL citation)

### The named modes and what `read-only` forbids by design

- `packages/sandbox/sandbox/src/index.ts:29` — the closed vocabulary is exactly three: `'read-only' | 'workspace-write' | 'danger-full-access'`. Re-exported for validation/advertisement at `packages/sandbox/sandbox-policy/src/session-mode.ts:42`.
- `packages/sandbox/sandbox/src/roots.ts:52-55` — `writableRoots()` is the one home for the mode's meaning: **`read-only` returns an empty allow-list** (`if (policy.mode !== 'workspace-write') return []`); `workspace-write` grants the session workspace root plus `/tmp` and `os.tmpdir()`, canonicalized.
- `packages/sandbox/sandbox/src/index.ts:24-27` — doc contract: `read-only` permits only required sinks such as `/dev/null`; `danger-full-access` bypasses confinement entirely. Network and process visibility are explicitly **outside** this vocabulary.
- `packages/sandbox/sandbox-policy/src/index.ts:135-142` — `resolve()` precedence: an approved per-call escalation mode **>** the session's last `sandbox/mode` event **>** the deployment default. The session's `header.cwd` is the workspace boundary; the configured root is only the fallback for agentless calls.
- `packages/sandbox/sandbox-policy/src/index.ts:94` — schema default is `read-only` (fail-safe), but the shipped bundle overrides it (below).
- `packages/bundle/base/cordis.patch.yml:172-176` — shipped default is **`workspace-write`**, not read-only: `mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'`.
- `packages/bundle/base/cordis.patch.yml:194-206` — the shipped preset table offering all three user-facing presets, each bundling a sandbox mode with an approval policy: `read-only`→`{sandbox: read-only, approval: ask}`, `workspace-write`→`{workspace-write, ask}`, `danger-full-access`→`{danger-full-access, never}`.

### Enforcement is at two independent layers, and they are composed separately

**OS layer (untrusted code — the `bash` / PTY path).** `packages/sandbox/sandbox-local/src/index.ts:159-166` selects the runner chain by platform: Linux `['bwrap','landlock']` (probed in order), darwin `['seatbelt']`, win32 `['windows-acl']`. A platform with no chain **fails closed** (`chainVerdict()` → `'unavailable'` → `SandboxUnavailableError`, `packages/sandbox/sandbox-local/src/index.ts:492-510`). Enforcement completeness per rung at `:177-187` — bwrap/landlock/seatbelt claim `full`; **windows-acl is `partial` by construction** (WRITE_RESTRICTED must retain Everyone in its restricting list, and NTFS hard links alias one file object across paths). `packages/sandbox/sandbox/src/index.ts:131-144` — a missing backend throws `SANDBOX_UNAVAILABLE` rather than silently running unconfined.

**Tool layer (trusted code, model-controlled path — the `write`/`edit`/`str_replace_editor` path).** `packages/fs/fs-sandbox/src/index.ts:126-148` — `checkedTarget()`: `danger-full-access` delegates unfenced; `read-only` throws `FS_SANDBOX_DENIED` unconditionally (`:130-132`); `workspace-write` re-canonicalizes immediately before the syscall and requires containment under a `writableRoots()` root (`:136-147`). The module doc at `packages/fs/fs-sandbox/src/index.ts:14-18` is explicit that this is **"a policy check in TRUSTED code over a MODEL-CONTROLLED path, NOT a kernel boundary"**, with a documented, accepted residual TOCTOU.

Crucially, the two layers derive the same allow-list from one function so bash and fs cannot drift (`packages/sandbox/sandbox/src/roots.ts:5-11`).

### The bypass: `sandboxMode === undefined` disables the tool-layer fence entirely

- `packages/fs/fs/src/index.ts:103-105` — the base `FileSystem` seam returns `sandboxMode: undefined`, documented at `:91-100` as *"`undefined` when it does not confine at all"*. `LocalFileSystem` (`dsh-fs-local`) does **not** override it; only `SandboxedFileSystem` does (`packages/fs/fs-sandbox/src/index.ts:69-71`).
- `packages/fs/tool-str-replace-editor/src/index.ts:66-73` — `MutationPolicy` reads `ctx.fs.sandboxMode`; when it is `undefined`, `this.policy` stays `undefined`, `resolve()` returns `undefined`, and every mutation is delegated to a provider with no fence. Same gating in the sibling tool at `packages/fs/tool-fs/src/sandbox.ts:44-50` (`escalationModes` becomes `[]`).
- **`apps/cli/config/agent-presets/minimal/agent.cordis.yml:46-62`** — the shipped `minimal` preset does exactly that:
  ```yaml
  # The bare local filesystem shadows the host's sandboxed provider only for this
  # preset. The editor shares that realm and requires absolute paths.
  - id: filesystem
    name: cordis:group
    isolate:
      fs: true
    config:
      - id: fs-local
        name: '@deepseek-ai/dsh-fs-local'
      - id: str-replace-editor
        name: '@deepseek-ai/dsh-tool-str-replace-editor'
  ```
- This is **documented and deliberate**, not an accident: `.agents/notes/implemented/feature/2026-08-11-minimal-profiles-bare-two-tool-runtime.md:39` — *"The editor can address any absolute path visible to the runtime process, independently of the persistent shell's sandbox policy."* The alternative of keeping `fs-sandbox` was explicitly **rejected** at `:31` — *"Rejected because the sandboxed provider still makes confinement and escalation part of the editor capability. The target runtime requires the bare local provider, whose lack of `sandboxMode` is composition truth."* See also `.agents/notes/implemented/bug-fix/2026-08-10-minimal-preset-owns-rl-composition.md:19` — *"shadows the host filesystem provider only for that agent."*
- What is **not** documented anywhere in those notes: that the UI continues to advertise and display a permission preset that does not govern this tool. `packages/interaction/permission-presets/src/index.ts` registers the `permissions` projection on the **host** plane, so the composer chip renders `Read Only` for a `minimal` session whose editor is entirely unconfined.
- The `standard` / `code` / `cordis` presets are **not** affected: they mount `tool-fs` (`apps/cli/config/agent-presets/standard/agent.cordis.yml:56-60`) over the host's `dsh-fs-sandbox` (`packages/bundle/base/cordis.patch.yml:443-444`), so `read-only` correctly denies.

### Claim (b): mode is mutable per session by design — but a PTY fence blocks it

- **Mutable, explicitly.** `packages/sandbox/sandbox-policy/src/session-mode.ts:1-19` — the session log *is* the store; `effective = fold(events) ?? deployment default`. `setSandboxMode()` at `:69-71` appends one `sandbox/mode` event and *"Takes effect on the session's next confined call (bash or fs)."* So mode is **not** fixed at session start.
- The user-facing write path is the `/permission <preset>` command, `packages/interaction/permission-presets/src/index.ts` (command registration, `handler` calling `this.apply(...)`).
- **The web UI has two different controls, and they are not interchangeable** — this alone can produce claim (b):
  - `packages/client/ui-permission-presets/src/client/PermissionRow.tsx:1-5` — Settings row header comment: *"the default preset for **subsequently created sessions**. Current-session switches remain on the composer `/permission` control."* Its `select()` writes only `settings.mutate({ns:'permission', path:['defaultPreset']})` (`packages/client/ui-permission-presets/src/client/settings-store.ts:143-147`). Changing it does **nothing** to the running session.
  - `packages/client/ui-conversation/src/client/skeleton/PermissionSelect.tsx:98-103` — the composer chip is the real in-session switch; it submits `/permission <id>`.
  - The composer chip is **not** locked merely because a turn is running: `packages/client/ui-conversation/src/client/skeleton/InputBar.tsx:129-134` — *"Running input stays free"*; `locked = removed || inert || !live || blocked !== undefined || parentOffline`.
- **The real blocker.** `packages/terminal/terminal-bash/src/index.ts:34-53` — `ensureSandboxModeFence()` registers a global `internal/dispatch` listener on `session/event` that **throws** on any `sandbox/mode` event changing the effective mode while `state.pty.hasOwnerActivity(owner)`:
  ```
  cannot change sandbox mode from "<from>" to "<to>" while persistent terminal
  sessions are open or being created; wait for creation to settle and close them first
  ```
  `hasOwnerActivity` is true while any PTY record or pending spawn exists for that agent (`packages/terminal/terminal/src/index.ts:231-234`).
- The fence is **by design** and documented: `.agents/notes/implemented/feature/2026-07-16-persistent-pty-sessions.md:44` — the mode and workspace root *"remain the process boundary for the PTY lifetime. A write that would change the effective `sandbox/mode` is rejected before commit while the owner has any open PTY or unpublished spawn."* The confinement is baked into the PTY's argv at spawn (`packages/terminal/terminal-bash/src/index.ts:71-80`), so it genuinely cannot be changed retroactively.
- **But the fence is undirectional and the escape hatch is missing.** It blocks *widening* (read-only → workspace-write → full access) as hard as it blocks *tightening*, even though widening a live shell is not the risk the fence exists to prevent. And `tool-bash-persistent` registers exactly one tool named `bash` with a single `command` parameter (`packages/shell/tool-bash-persistent/src/index.ts:374-398`) — there is **no** `terminal_close` / restart. The shell is closed only on plugin dispose, initialization failure, send failure, timeout, abort, or shell exit (`packages/shell/tool-bash-persistent/src/index.ts:207-230, 257, 300, 314, 323, 332`). The `minimal` preset does not mount `dsh-tool-terminal`. **Net effect: in 极简模式, after the first successful `bash` call, the session's sandbox mode is permanently frozen.**
- Failure is also non-atomic: `packages/interaction/permission-presets/src/index.ts` `apply()` appends `permission/preset` **before** calling `setSandboxMode()`, so when the fence throws, the preset event is already committed and `derive()` returns `CUSTOM_PRESET` — the UI drops to `Custom`, matching neither the old nor the new preset. This is precisely what #2226 reports.

- Profile / patch-layer bootstrap under the Harness home `~/.dsh` — `packages/boot/app-boot/src/profile.ts:153, 162-167, 226, 285`.
- Agent-preset authoring metadata — `packages/preset/agent-presets/src/authoring.ts:161`.

**These do not explain the OP's report** if the file was created by a model-visible tool call. #523 documents the same symptom with the writing tool named explicitly (`str_replace_editor`) and the created paths listed, which rules the sanctioned-writer explanation out for that case.

### There is also a legitimate, approval-gated way for a write to happen under read-only

`packages/sandbox/sandbox/src/escalation.ts:28-31, 157-189` — a tool may carry `sandbox_permissions` + `justification` to request a **strictly wider** mode for exactly one call. `approveEscalation()` checks strict widening against the call's effective mode, then routes to `ctx.approval.request(...)`; every non-approval outcome throws and nothing executes. If the OP clicked **Allow** on such a prompt, a file legitimately appears under a nominally read-only session. This is an alternative benign explanation the screenshots might show — worth asking, but it is *not* the leading hypothesis.

## Root cause

**Claim (a) — a composition defect, not a confinement failure.** DSH's sandbox is a *capability seam*: the fence lives in the mounted `ctx.fs` provider, and `ctx.fs.sandboxMode === undefined` is the seam's honest signal for "this backend never confines" (`packages/fs/fs/src/index.ts:91-105`). The `minimal` / 极简模式 preset deliberately mounts bare `dsh-fs-local` inside an `isolate: {fs: true}` realm to reproduce a bare RL training runtime (`apps/cli/config/agent-presets/minimal/agent.cordis.yml:46-62`; rationale at `.agents/notes/implemented/feature/2026-08-11-minimal-profiles-bare-two-tool-runtime.md:15, 31, 39`). Every downstream consumer then correctly concludes there is nothing to enforce and nothing to escalate.

The bug is the **mismatch between that composition truth and the product surface**. `permission-presets` and its `permissions` projection live on the host plane and keep advertising and displaying `Read Only` / `Workspace Write` for a session whose only editor obeys none of it. Two host-plane guards that exist elsewhere are missing here: `PermissionPresetService` refuses to compose over an unconfined **shell** (`packages/interaction/permission-presets/src/index.ts`, constructor: *"the mounted bash executor does not confine (no sandboxMode) … composing this plugin over an unconfined executor is a misconfiguration"*), and both fs tools throw if a confining backend lacks `sandboxPolicy` (`packages/fs/tool-fs/src/sandbox.ts:47-49`, `packages/fs/tool-str-replace-editor/src/index.ts:70-72`). Nothing performs the symmetric check for an **unconfined filesystem under an advertised permission preset**. Compounding it, the minimal persona sets `complete: true` and `includeRuntimeContext: false`, so the `sandbox:policy` prompt section (`packages/sandbox/sandbox-policy/src/index.ts:112-123`) is discarded — the model is never even told a policy exists, so it has no reason to hesitate.

**Claim (b) — a correct invariant with a missing escape hatch.** The PTY fence is sound in principle: confinement is baked into the shell's argv at spawn (`packages/terminal/terminal-bash/src/index.ts:71-80`), so a running PTY's boundary genuinely cannot be re-negotiated. But three things turn a correct invariant into a dead end: (1) the fence is **undirectional**, rejecting widening as hard as tightening; (2) `tool-bash-persistent` exposes **no** way to close or restart the shell (`packages/shell/tool-bash-persistent/src/index.ts:374-398`), and `minimal` does not mount `dsh-tool-terminal`, so "close them first" is un-actionable; (3) the preset-application order commits `permission/preset` before `sandbox/mode`, so the failed switch leaves the UI stuck at `Custom`.

**Why one post reports both.** These are not two coincidences. The 极简模式 preset is the single composition that simultaneously mounts the unfenced `fs-local`+`str_replace_editor` pair *and* makes persistent PTY bash the only shell. A user in that preset sees files created despite `Read Only`, tries to switch mode to make sense of it, and finds the switch permanently rejected. The OP's title bundling both symptoms is strong circumstantial evidence they were in 极简模式 — which is exactly the fact their post omits.

## Recommended next steps

1. **Do not treat this as a novel report — consolidate.** Reply on #2422 pointing to #523 (claim a) and #2226 (claim b), and ask for the four missing facts (draft below). #523 is still **unanswered** and is the better-evidenced security thread; it should carry `kind/bug` + `area/sandbox` + `area/preset` and get a maintainer response.
2. **Confirm the preset from the screenshots.** The single highest-value missing fact is whether the OP was in 极简模式. If yes, both claims are already-known duplicates and no new investigation is needed. Ask them to paste the preset name and the `permission/preset` + `sandbox/mode` events from their session log.
3. **Fail closed on the composition mismatch (fixes the class, not the instance).** Add the symmetric guard that `permission-presets` already applies to the shell: when a permission preset is advertised for a session whose effective `ctx.fs.sandboxMode` is `undefined`, either refuse to compose or suppress the permission chip for that session. Enforcement must be in the operation that makes the decision, per `packages/AGENTS.md` — a UI-only change would leave direct callers bypassing it.
4. **Decide the `minimal` preset's real contract.** Either (i) mount `fs-sandbox` there and accept that the editor gains confinement/escalation semantics (explicitly rejected in the note at `:31` — so this needs a *new* Agent Note reversing that decision, not an edit to the existing one), or (ii) keep the bare provider and make the preset advertise no permission control at all. Option (ii) preserves the RL-runtime intent; option (i) preserves the product promise. This is a product call, not a mechanical fix.
5. **Make the PTY fence directional and give it an exit.** Adopt #2226's proposal: permit *widening* by killing the owner's shells (the next `bash` call respawns under the new mode — `packages/shell/tool-bash-persistent/src/index.ts:225-230` already has `reset()`), keep tightening guarded, and make `apply()` atomic so a rejected `sandbox/mode` rolls back the already-appended `permission/preset` instead of stranding the UI at `Custom`.
6. **Add the missing coverage.** Per repo testing policy this is model-/user-visible behavior, so it needs a keyless snapshot through a real runnable example — an assembled `minimal`-preset transcript asserting that a `str_replace_editor` write outside the workspace under `read-only` is denied (or that no permission control is advertised), plus a `/permission` switch attempt with an open PTY.

**If it had to be treated as an unproven escape, a repro harness would need:** the exact `dsh` version and platform; the assembled composition (`dsh --dump-config`, or the preset name plus `agent.cordis.yml`); the session log's `permission/preset`, `sandbox/mode`, `approval/asked`, `approval/resolved` and `tool/call` + `tool/result` events for the offending turn; the absolute path written; and the resolved `ctx.fs` provider identity. The last one is decisive — `ctx.fs.sandboxMode === undefined` immediately distinguishes "fence absent" (this bug) from "fence defeated" (a genuine escape, which would be far more serious).

>
> **先说结论：这两个现象很可能都来自同一个原因——你当时用的是「极简模式」这个 Agent 预设。**
>
> **关于「read only 仍然创建了文件」**
>
> 这不是内核沙箱（bwrap / Landlock / Seatbelt / Windows ACL）被绕过，而是**该预设根本没有挂载带沙箱的文件系统后端**。极简模式在 `apps/cli/config/agent-presets/minimal/agent.cordis.yml:46-62` 里用一个隔离域挂载了裸的 `@deepseek-ai/dsh-fs-local`，把宿主的 `dsh-fs-sandbox` 遮蔽掉了。裸后端的 `sandboxMode` 是 `undefined`（`packages/fs/fs/src/index.ts:103`），于是 `str_replace_editor` 的沙箱校验整段不生效（`packages/fs/tool-str-replace-editor/src/index.ts:66-73`）——无论会话处于 read-only 还是 workspace-write。此时界面上的权限标签仍然照常显示，这是我们的问题：**UI 承诺了一个该工具并不遵守的边界。**
>
> 已有完全相同的报告并附带完整复现：**#523**。
>
> 另外请注意，read-only 下出现文件也有两种**正常**情况：一是模型发起了 `sandbox_permissions` + `justification` 的一次性提权申请、而你在弹窗里点了「允许」（`packages/sandbox/sandbox/src/escalation.ts:157`）；二是harness 自身的状态写入（会话日志、`~/.dsh` 下的身份与凭据文件等），这些不受 `sandbox/mode` 管辖。所以我们需要知道**具体是哪个工具、写到了哪个路径**。
>
> **关于「中途无法切换到 workspace write / full access」**
>
> 权限模式**本身是支持会话中途切换的**，并非启动后固定：切换会写入一条 `sandbox/mode` 事件，下一次受限调用即生效（`packages/sandbox/sandbox-policy/src/session-mode.ts:69`）。
>
> 你遇到的是持久 bash 的护栏：只要该 Agent 还有打开的 PTY，任何改变沙箱模式的写入都会被拒绝（`packages/terminal/terminal-bash/src/index.ts:34-53`），错误信息是 `cannot change sandbox mode from "…" to "…" while persistent terminal sessions are open or being created`。原因是沙箱边界在 PTY 启动时就固化进了进程 argv，无法事后更改。问题在于极简模式**只提供 `bash` 一个 shell 工具，没有任何关闭终端的工具**，所以一旦模型跑过一次 bash，这个会话就再也切不动了。这与 **#2226** 是同一个问题（该帖已有回复和一个社区绕行插件）。
>

The permission chip keeps rendering regardless, and that is our bug: **the UI promises a boundary this tool does not honor.**

> An identical report with full repro steps: **#523**.

That is why we need **which tool wrote which path**.
>
> **On "cannot switch to workspace-write / full access mid-session"**
>
> Permission mode **is** switchable mid-session by design — it is not fixed at session start. A switch appends a `sandbox/mode` event that takes effect on the next confined call (`packages/sandbox/sandbox-policy/src/session-mode.ts:69`).
>
> What you hit is the persistent-bash guard: while the agent has any open PTY, every mode-changing write is rejected (`packages/terminal/terminal-bash/src/index.ts:34-53`) with `cannot change sandbox mode from "…" to "…" while persistent terminal sessions are open or being created`. The boundary is baked into the PTY's argv at spawn, so it genuinely cannot be changed afterward. The real defect is that `minimal` ships **only** the `bash` tool and no way to close the terminal — so after the first bash call the session is permanently frozen. Same issue as **#2226** (which has a reply and a community workaround plugin).
>
> One more thing that often confuses this: **the Permission dropdown in Settings only changes the default for newly created sessions, not the current one** (`packages/client/ui-permission-presets/src/client/PermissionRow.tsx:1-5`). For the current session use the permission button in the composer, or type `/permission <preset>`.
