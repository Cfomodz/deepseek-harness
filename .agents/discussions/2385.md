## Verdict

**Answerable now, with a correction to the existing reply.** The error is a real, well-understood on-disk misconfiguration: the composed profile entry list contains two rows whose `id` is `mcp-argo`. It persists across restarts because it lives in files (`package.json` `dsh.profile.bundles` + `cordis.patch.yml`), not in runtime state.

The existing reply by @moonquake2004 is **directionally correct but materially wrong in two places**:

1. **REFUTED — there is no first-party `dsh-doctor`.** No `doctor` command exists anywhere in this codebase. `npx @moonquake2004/dsh-doctor` is the reply author's **own third-party npm package**, first published **one day before** the discussion, and it fetches its check catalog from the author's GitHub at runtime. It should be labelled as third-party, not presented as the diagnosis step.
2. **REFUTED — `dsh plugin ls` as written does not run.** `--profile` is a `requiredOption` on the `plugin` subcommand; the working form is `dsh plugin --profile <name> ls`.

The reply also **understates a known upstream defect**: [#1404](https://github.com/deepseek-ai/deepseek-harness/discussions/1404) (which the reply cites) describes the exact mechanism, and that defect is **still present unfixed** at this checkout. The most likely cause is not "manual edits" or "double install" — it is `dsh plugin add` auto-promoting a bundle-declaring dependency the user was already loading via a `cordis.patch.yml` insert.

### F1 — Where the error is raised — CONFIRMED
`vendor/loader/src/config/group.ts:64`, inside `EntryGroup.update()` (`vendor/loader/src/config/group.ts:59-66`):

```ts
const seen = new Set<string>()
for (const options of config) {
  const id = this.tree.ensureId(options)
  if (seen.has(id)) throw new TypeError(`duplicate loader entry id: ${id}`)
  seen.add(id)
}
```

This is a pre-flight scan over **one entry list** before any entry mounts. It is the only site in the repo producing this string (repo-wide grep returned exactly this one match).

### F2 — What an "entry id" is — CONFIRMED
`vendor/loader/src/config/tree.ts:66-73` (`EntryTree.ensureId`): the id is the row's own `id` field as written in config; only when absent does the loader mint a random 8-hex-char id. So **every collision is between two rows that both carry an author-written `id`** — a random id can never collide (`tree.ts:68-70` loops until unused).

### F3 — Which entry failed: the root include — CONFIRMED
The OP's message names `include (cordis:include)`. That is the root `Include` row mounting the profile's `cordis.yml`. Its apply path is `vendor/include/src/index.ts:315-317` (`_apply` → `applyPatches` → `this.root.update(data)`), which lands in F1's `EntryGroup.update`. So the duplicate is in the **composed profile entry list**, not in a nested group.

### F4 — `insert` patches do not de-duplicate by id — CONFIRMED
`vendor/include/src/index.ts:92` and `:94` — `applyEntryPatches` appends insert rows with a bare push:

```ts
target.config.push(...insert)   // :92 (into a group)
data.push(...insert)            // :94 (top level)
```

There is no id check here. Two layers each inserting `id: mcp-argo` produce two rows, and the failure surfaces only later at F1. This is why the error names the id but nothing about where either row came from.

### F6 — What legitimately produces a collision — CONFIRMED (mechanisms) / PLAUSIBLE (which one hit the OP)
Because all layers flatten into one list (F5) and inserts never dedupe (F4):

- **(a) `dsh plugin add` promotion — the [#1404](https://github.com/deepseek-ai/deepseek-harness/discussions/1404) defect.** `apps/cli/src/plugin.ts:65-70`:
  ```ts
  for (const packageName of dependencies) {
    const isBundle = exportsPatch(packageName, profileDir)
    if (isBundle && !plugins.includes(packageName)) {
      plugins.push(packageName)      // unconditional promotion
  ```
  This appends **every** dependency declaring `dsh.bundle` to `dsh.profile.bundles` on **every** invocation. A package the user was previously loading only through a `cordis.patch.yml` insert gets promoted to a bundle layer; its bundle patch then inserts the same id the user's patch already inserts. **This guard is absent at HEAD `47f943859` (v0.1.0-rc.5)** — grep for `userIds` / `readInsertIds` / any user-patch cross-check in `apps/cli/src/plugin.ts` returns nothing.
- **(b) Same id inserted by two different patch files** — e.g. profile `cordis.patch.yml` and home-level `$DSH_HOME/cordis.patch.yml`, or two bundles both shipping an `mcp-argo` row.
- **(c) Same bundle listed twice in `dsh.profile.bundles`** (hand-edited `package.json`; the CLI's own `plugins.includes` check prevents the CLI from doing it).
- **(d) Stale rows baked into the profile root `cordis.yml`.** `apps/cli/src/profile-boot.ts:85-93` documents exactly this: the vendored loader's tree write-back "can bake composed rows into this file — which would duplicate every bundle insert on the next boot." The current launcher **always rewrites** the root to an empty list (`:59-64`, `:101`), so this is fixed at rc.5+ but would explain the same error on an older install whose root file was polluted.

## Root cause

The profile's composed entry list contains **two rows with `id: mcp-argo`**, because `applyEntryPatches` appends `insert` rows without any id de-duplication (`vendor/include/src/index.ts:94`) while every layer — bundle patches, profile `cordis.patch.yml`, home `cordis.patch.yml`, `--patch` overlays — is flattened into one list (`apps/cli/src/profile-boot.ts:122-129`, `:151`). `EntryGroup.update` then rejects the list wholesale before any entry mounts (`vendor/loader/src/config/group.ts:64`).

The most probable specific trigger, given the OP said this started while installing a plugin, is the **unfixed [#1404](https://github.com/deepseek-ai/deepseek-harness/discussions/1404) defect**: `reconcilePlugins` unconditionally promotes any dependency declaring `dsh.bundle` into `dsh.profile.bundles` (`apps/cli/src/plugin.ts:65-70`), so a package the user was already loading via a hand-written `cordis.patch.yml` insert now *also* contributes its own bundle-layer insert of the same id. **PLAUSIBLE** rather than CONFIRMED — confirming it requires the OP's `package.json` and `cordis.patch.yml`.

It survives restarts because both contributions are files on disk; nothing about the failure is runtime state.

## Recommended next steps

**For the OP (ordered, all first-party):**

1. `dsh --profile <name> --dump-config` — succeeds despite the crash (F7) and prints **both** `mcp-argo` rows with `# ==` comments naming their source layers. This is the actual answer to "which file do I edit".
2. `dsh --profile <name> --dump-default-config` — bundle layers only, user layer never parsed. If `mcp-argo` appears here, a **bundle** contributes it; if it appears only in the full dump, a **user patch file** does.
3. Remove exactly one contribution — the `- insert:` block from `~/.dsh/profiles/<name>/cordis.patch.yml` (or `~/.dsh/cordis.patch.yml`), **or** drop the package with `dsh plugin --profile <name> remove <package>`, which also de-lists it from `dsh.profile.bundles` (`apps/cli/src/plugin.ts:78-87`).

**For the maintainers — two legitimate findings:**

1. **Land the [#1404](https://github.com/deepseek-ai/deepseek-harness/discussions/1404) guard.** `apps/cli/src/plugin.ts:65-70` should not promote a bundle-declaring dependency whose insert ids already exist in the user patch layer. A branch reportedly exists (F10) and no PR has landed (F10). Without it, `dsh plugin add` remains a foot-gun that bricks the next boot.
2. **The error message should name the two colliding sources — yes, this is a real diagnosability gap.** `vendor/loader/src/config/group.ts:64` emits `duplicate loader entry id: mcp-argo` and nothing else: not the two rows, not their `name`s, not the files. The launcher **already computes per-layer row attribution** for `--dump-config` (`renderConfigDump`'s prefix-snapshot diffing in `packages/boot/app-boot/src/index.ts`), so the information exists. Two options, in preference order:
   - **Preferred: pre-validate in the launcher.** Add a uniqueness check to `composeProfile` (`apps/cli/src/profile-boot.ts:142-171`), which knows the layer labels, and fail with e.g. `dsh: duplicate loader entry id "mcp-argo" — inserted by both @scope/pkg (bundle layer) and ~/.dsh/profiles/web/cordis.patch.yml; remove one insert`. This keeps `vendor/` unmodified, which the vendoring policy prefers, and fails before boot.
   - Alternatively, have `--dump-config` flag duplicate ids as a warning, so the recommended diagnostic actively points at the problem rather than requiring the user to eyeball two identical ids.

   `packages/mcp/mcp-client/src/index.ts:155-157` is the in-repo template for what a good message looks like here.

**Positioning of the third-party tool:** `@moonquake2004/dsh-doctor` is real and its `P2` check is genuinely on-target (F9), but it must be described as a community tool, not as `dsh doctor`. Mentioning that it fetches remote checks by default and can self-update is fair disclosure, not an accusation.
