## Research findings (each with a path:line or URL citation)

1. **The screen is the web boot gate, not a runtime error.** `packages/client/web/src/AppRoot.tsx:52` renders `Failed to load plugins`, and it only renders while boot has not settled (`AppRoot.tsx:36` returns the app once `settled`). The listed lines are loader entries whose projected fiber state is `failed`, keyed by entry name (`packages/client/web/src/loader-status.ts:43`). CONFIRMED: this is a **boot-time** failure, so the app genuinely never opens — consistent with 打不开了.

2. **`details` is a `single`, session-scoped slot declared by ui-layout.** `packages/client/ui-layout/src/client/index.ts:72` (type declaration) and `:125` (runtime declaration `{ kind: 'single', scope: 'session' }`); it is rendered as the right column at `packages/client/ui-layout/src/client/AppFrame.tsx:191`. CONFIRMED.

3. **Error site.** `packages/client/ui-slots/src/index.ts:801-802`:
   ```ts
   const occupant = rec.entries.find(e => (e.options.priority ?? 0) === priority)
   if (occupant) throw new Error(`single slot "${options.name}" already has a registration ${occupantHint(occupant)}`)
   ```
   CONFIRMED.

4. **What `priority` means, and the exact registration rule.** `packages/client/ui-slots/src/index.ts:796-798` computes `const priority = options.priority ?? 0` and builds the hint; the contract is documented at `:718-724`:
   > "entries sharing one cell … coexist at distinct priorities, sorted ascending with ties keeping registration order; the cell's lowest live entry renders. A second registration at an occupied cell's exact priority (default 0) throws naming the occupant, so priority-less composition keeps the historical one-occupant-per-cell fail-loud."

   So: a `single` slot is **not** exclusive by design — it is exclusive *per priority level*. Two plugins coexist on one `single` slot only if they register at **different** priorities; the numerically lowest live entry is the one that renders (sort at `:866-868`, winner selection documented at `:926`). Field doc: `:487`. CONFIRMED — **a non-zero priority does resolve this**.

5. **REFUTED: ui-conversation and ui-cordis do NOT both register `details` in-tree.** The only in-tree registration of `details` is `packages/client/ui-conversation/src/client/apply.ts:445` (`slots.register({ name: 'details', locale: NS, children: { 'conversation.details.tool': … }, store: chatStore, … }, DetailsPanel)`) — with **no `priority`**, i.e. priority 0. `@deepseek-ai/dsh-client-ui-cordis` (= `packages/extensions/ui-cordis`, name confirmed in its `package.json:2`) registers only into `sidebar.footer.action` (`packages/extensions/ui-cordis/src/client/index.ts:84`) and four keys of `tool.call.toolview` (`:115`, `:122`, `:136-143`). It never touches `details`. **This is not a shipped conflict; the default `web` roster is not reproducible-broken.**

6. **Why ui-cordis appears in the failed list anyway (PLAUSIBLE, cascade).** `tool.call.toolview` is declared by an entry ui-tool mounts inside `conversation.chat.node` — see the generated catalog, `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts:1659`: `declaredBy: "an entry in 'conversation.chat.node' (client-ui-tool), so it exists while that entry is mounted"`. `conversation.chat.node` only exists while ui-conversation's entry is mounted. ui-conversation's `details` register is the **last** statement of its `apply` (`apply.ts:445-455`), so the throw unwinds the whole fiber and every conversation-owned slot declaration disappears; ui-cordis's `ctx.slots.inject('tool.call.toolview', …)` then never resolves. ui-cordis is collateral, not a cause. (Both entries are ordinary rows in the shipped roster: `packages/bundle/web-app/cordis.patch.yml`, `id: ui-conversation` and `id: ui-cordis`.)

7. **CONFIRMED: a dynamic Cordis package (`cordis_define`, the self-modification / `demo:cordis` path) can never be the priority-0 occupant.** The browser-half guard rewrites the priority on every non-chain registration: `packages/extensions/cordis-client-runner/src/client/guard.ts:120-127`
   ```ts
   let priority = options.priority
   if (spec === undefined || spec.kind !== 'chain') {
     priority = env.allocatePriority()
     options.priority = priority
   }
   ```
   and the allocator is `allocatePriority: () => --this.nextPriority` over `private nextPriority = 0` (`packages/extensions/cordis-client-runner/src/client/runtime.ts:424` and `:183`) — i.e. the first dynamic registration is **-1**, never 0. The escape hatch is closed too: `ctx.get('slots')` returns the same guarded proxy (`guard.ts:206-208`, reached from `guard.ts:214`). So the likely first hypothesis — "the agent defined a plugin that grabbed the details column and now the page is bricked" — is **REFUTED by construction**. A dynamic package on `details` shadows ui-conversation silently; it does not crash boot.

8. **The occupant is therefore an ordinary loader-entry plugin.** `registrant` is `options.registrant ?? ctx.fiber.name` (`packages/client/runtime/src/client/slots.ts:361`), and a dynamic package's fiber is named `dyn/<pluginId>` (`packages/extensions/cordis-client-runner/src/client/runtime.ts:156-158`, `:430`/`:435`), not a bare `x6`. REFUTED that `x6` is a minified bundle symbol: the client bundles are **not** JS-minified — the only `minify: true` in `packages/client/tsdown.client.ts:243` is the lightningcss CSS transform, and `sourcemap: true` is set at `:184`. So `x6` is a real, literal plugin name — a plugin the reporter's composition adds.

9. **The likely authoring trap (PLAUSIBLE, and it is a real documentation defect).** The model-facing slot catalog tells a plugin author to register into `details` with *no* priority — `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts:1049` gives the example verbatim as `ctx.slots.register({ name: 'details' }, …)`, marks `replaceRisk: 'shadows-shipped-ui'` (`:1048`), and the shared preamble at `:71` says *"Do NOT pass `priority`: the browser-half facade assigns one automatically"*. That advice is **only true inside the dynamic-package facade** (finding 7). Copied into a hand-written client plugin mounted as a roster row, the same call lands at priority 0 and collides with ui-conversation — exactly this crash. PLAUSIBLE as the reporter's path if `x6` is a plugin they (or an agent) wrote.

10. **Second candidate cause (PLAUSIBLE): a duplicated roster row.** The web kernel creates one loader entry per manifest row with `loader.create({ name })` (`packages/client/web/src/boot.tsx:198`), and `parseBootManifest` (`packages/client/modules/src/client/manifest.ts:108-140`) validates types but does **not** reject duplicate ids. A composition listing the same client package twice would apply ui-conversation twice and throw here. This does not fit `registered by x6` (the occupant would be named after ui-conversation's own fiber), so it ranks below finding 9 — but it cannot be excluded without the reporter's config.

11. **Repo registration rules (CLAUDE.md) hold here and explain the loudness.** "Registrations are effects; a registry's `register()` returns the disposer" — `SlotCore.register` returns `() => void` (`packages/client/ui-slots/src/index.ts:757`, `:785`) and the client `SlotRegistry` layer hangs that disposer on the *caller's* fiber via `ctx.effect` (`packages/client/runtime/src/client/slots.ts:355-372`; described at `packages/extensions/cordis-client-runner/src/client/api-catalog.ts:220`). Because the registration is a fiber-owned effect, a stale entry cannot leak across a clean unload — which is why "occupied at priority 0" means a genuinely **live second registrant**, not residue. It also matches "Misconfiguration fails loud at load."

12. **No Agent Note covers slot priority/shadowing.** The two slot notes are `.agents/notes/implemented/architecture/2026-07-22-slot-type-chain-implementation.md` (one incidental `priority` mention, about chain election) and `.agents/notes/implemented/architecture/2026-08-05-slot-declaration-injection.md` (zero mentions). The shadowing rule's only authority is the JSDoc at `packages/client/ui-slots/src/index.ts:718-724` plus the generated catalog. CONFIRMED.

## Root cause (or precisely why it cannot be determined)

The mechanism is certain; the trigger is not.

**Mechanism (CONFIRMED).** `details` is a `single` slot whose cells are keyed by priority. The shipped `ui-conversation` occupies it at the default priority 0 (`apply.ts:445`, no `priority` field). A second plugin — named `x6` in the reporter's build — registered into `details` at priority 0 first, so when the loader applied `ui-conversation`'s entry (`f90db188`) the guard at `ui-slots/src/index.ts:801-802` threw. Because that register call is the tail of ui-conversation's `apply`, its fiber failed, every conversation-owned child slot declaration collapsed, and `ui-cordis` — which registers into `tool.call.toolview`, a slot declared only inside the conversation subtree — never became active either. Boot never settled, so the gate screen stayed up and the app "won't open."

**Why the trigger cannot be determined (INSUFFICIENT-DATA).** `x6` does not exist in this repository, in any bundle roster, or as any dynamic-package fiber name, and dynamic Cordis packages are structurally incapable of taking priority 0. So `x6` is a plugin present only in the reporter's composition, and nothing in the post identifies it, its origin, or the version of the harness. One post-ready fix exists for the plugin's author (finding 4 / draft below); which of the two remaining routes produced it (hand-written client plugin copying the catalog's priority-less example, vs. a duplicated roster row) needs the reporter's config.
