## Research findings

### The error site and what it means

1. **CONFIRMED — exact error site.** `packages/session/session-persistence-jsonl/src/format.ts:364-373`:
   ```ts
   if (event.seq !== this.events.length) {
     const expected = this.events.length
     this.events.length = rowStart
     this.issue = new Error(
       `corrupt session log: seq gap in committed region at line ${this.eventLine} `
       + `(expected ${expected}, got ${event.seq})`,
     )
   ```
   `expected` is the count of events accumulated so far; `got` is the offending row's `seq`. The sibling SQLite backend raises the same wording at `packages/session/session-persistence-sqlite/src/schema.ts:261`, but the OP's message carries `at line N`, which only the JSONL scanner emits — so the OP is on `@deepseek-ai/dsh-session-persistence-jsonl`, the backend the shipped base bundle mounts (`packages/bundle/base/cordis.patch.yml:98-101`).

2. **CONFIRMED — the invariant `seq` carries.** `seq` is a **dense 0-based positional index** into the session's event array: a row is valid only when `event.seq === this.events.length` (`format.ts:364`). Packed chunk rows (`text-chunks` / `reasoning-chunks` / `tool-call-chunks`) carry a `seq0` envelope and expand to a contiguous run (`packages/core/session/src/chunk-rows.ts:161-179`, `packages/core/session/src/chunk-rows.ts:339-346`), so one JSONL line can expand to many events — which is why 5,121 good event lines can hold 91,237 events (~17.8 events/line).

3. **CONFIRMED — "committed region" = the prefix up to and including the last `turn/end`.** The scanner records the first anomaly but only *throws* if a `turn/end` is seen at or after it (`format.ts:357-360`, `format.ts:371`); anything after the last `turn/end` is a tolerated crash tail that is silently dropped. The three behaviours are pinned by tests at `packages/session/session-persistence-jsonl/tests/jsonl.spec.ts:951` (gap after the last `turn/end` → tail bounded, prefix preserved), `:963` (gap before a later `turn/end` → throws — *"Truncating it would silently drop committed data → unloadable"*), `:1003` (gap in the uncommitted tail → tail dropped). So the OP's log has **committed data after the damage**, which is why it hard-fails instead of self-trimming.

4. **CONFIRMED — the reported "line 5122" is an EVENT line, not a file line.** `this.eventLine` starts at 0 and is incremented only in `consumeEventLine` (`format.ts:279`, `format.ts:348`); the header record is consumed separately by the constructor/`parseHeaderRecord` (`format.ts:287-291`, `format.ts:388-393`). The header is physical line 1, so **event line N = file line N+1**: the bad row is file line **5123**, and file lines 1..5122 are the header plus the 5,121 good event lines. This detail is load-bearing for any hand repair and is easy to get wrong.

### What recovery exists today

5. **CONFIRMED — there is no repair, doctor, salvage, or truncate command anywhere in this repo.** No `dsh` subcommand, script, or plugin performs operator-driven session-log repair. The only automatic repair is internal and *narrow*: `commitRepair()` truncates a **torn tail** to `committedBytes` and re-appends synthetic closers (`packages/session/session-persistence-jsonl/src/index.ts:436-444`, truncate at `:692-698`; driven from `packages/session/session-persistence/src/coordinator.ts:944-948` and `:1314`). It is invoked **only** when the backend returned a `tornMarker`, which the plaintext path sets only for a physically incomplete final record (`index.ts:327-329`) and the zstd path only for a structurally incomplete final frame (`index.ts:385-411`). A seq **rewind inside the committed region produces no `tornMarker` at all** — `scanLog` throws before any marker is computed. So no code path in the product will ever fix this file.

6. **CONFIRMED — a read-only salvage path DOES exist and does bypass the failing validator.** `readRaw()` reads the artifact bytes and decodes the physical encoding **without ever calling `scanLog`** — it only parses the header line (`packages/session/session-persistence-jsonl/src/index.ts:252-282`, header parse at `:275-278`). It is surfaced as an HTTP ZIP download at `packages/host/apiproxy/src/api-proxy.ts:3639-3693` (`downloads.sessionLog`), and driven from the browser by the `/export` command and a Session-header download button (`packages/session-query/session-log-export/src/index.ts:18-26`, `packages/session-query/session-log-export/src/client/index.ts:37-50`). It is mounted in the **web-app** bundle (`packages/bundle/web-app/cordis.patch.yml:70-71`) — the surface the OP is on.
   - **INSUFFICIENT-DATA:** whether `/export` is actually *reachable* for a session whose `history` call fails. The command must be typed inside the session and the header button rendered in its header; I could not verify that the Web conversation view mounts its header/command bar when `history` returns `internal`. This is the single most important thing to have the user try first, and the reason the draft answer does not depend on it alone.

7. **CONFIRMED — where the file lives.** Root is `dshHomePath('sessions')` (`packages/bundle/base/cordis.patch.yml:100-101`), i.e. `$DSH_HOME/sessions` else `~/.dsh/sessions` (`packages/util/home-paths/src/index.ts:60-62`, `:87-91`, `:98-100`). Layout: `<root>/--<slugified-cwd>--/<encoded-session-id>/session<suffix>` (`packages/session/session-persistence-jsonl/src/format.ts:147-208`). For `session-1d66c860-84f1-4963-975f-88a747ff08f7` every character is in `[A-Za-z0-9._-]`, so `encodeSegment` is the identity (`format.ts:121-136`) and the directory name is literally the session id.

8. **CONFIRMED — the file is Zstandard-compressed by default.** `DEFAULT_COMPRESSION = 'zstd'` (`packages/session/session-persistence-jsonl/src/index.ts:38`, schema at `:54-57`), suffix `.jsonl.zstd` (`format.ts:24-26`). The container is **concatenated standard zstd frames** (magic `0xFD2FB528`, `packages/session/session-persistence-jsonl/src/zstd.ts:15`, `scanZstdFrames` at `:48-60`), which the stock `zstd` CLI reads and writes.

9. **CONFIRMED — you cannot leave both encodings side by side.** If a `session.jsonl` and a `session.jsonl.zstd` exist in the same session directory, every read throws an encoding-mismatch error (`packages/session/session-persistence-jsonl/src/index.ts:783-785`, same check at `:485`). Any hand repair must end with exactly one artifact whose suffix matches the configured `compression`.

10. **CONFIRMED — a hand-repaired file must keep `"version":0`.** `SESSION_FORMAT_VERSION = 0` (`packages/core/session/src/types.ts:56`); a header whose `version` differs is refused up front with an "upgrade the harness" error, before any structural check (`packages/session/session-persistence-jsonl/src/format.ts:240-247`). `CLAUDE.md` states `dsh-session` keeps `SESSION_FORMAT_VERSION` at `0` with **no compatibility promise**, so there is no format-migration angle here — this is damage, not a version problem.

## Root cause

**The validator is behaving correctly; the log genuinely contains two overlapping branches of the same conversation.**

- **CONFIRMED (arithmetic):** `got (89909) < expected (91237)`. This is **not a hole** — nothing is missing. It means that at file line 5123, a row appears whose writer believed the log ended at event 89908, while the bytes before it already contain events 0..91236. 1,328 events are written twice, at the same seq positions, by two different writers (or by one writer with two cursors). Wording nit worth knowing: the message says "gap", but this instance is an **overlap/rewind**.
- **CONFIRMED (no cross-process protection):** appends are a bare `open(path, 'a')` + write + `fsync` (`packages/session/session-persistence-jsonl/src/index.ts:651-677`), the append position is an **in-memory** `cursor` (`packages/session/session-persistence/src/coordinator.ts:1354-1359`), and there is **no file lock anywhere** in `session-persistence*` (no `flock`, no lockfile, no `O_EXCL`). Two harness processes pointed at the same `~/.dsh/sessions` therefore interleave appends with independent cursors. There is a further hazard in the same file: `rollbackAppend` truncates the log back to the size it observed **before its own write** (`index.ts:680-690`) — under a second writer that discards the other process's committed bytes.
- **Most likely mechanism (PLAUSIBLE, best fit):** a second reader/writer of the same session (second `dsh` instance, second port/tab, a CLI alongside the Web app, or a stale cached prepared source) opened the log while its last committed event was 89908, took `cursor = 89909`, the first writer meanwhile appended events 89909..91236, and then the second writer appended its own batch at 89909 — landing after the first writer's bytes. That reproduces the observed numbers exactly with no filesystem misbehaviour required, and matches discussions #2257, #1433, #420, #2254.
- **zoahdev's "power-loss edge case" (PLAUSIBLE but weaker, and as stated misleading):** a crash-truncate that failed to become durable could leave stale tail bytes ahead of resumed writes, producing the same backwards signature. But `repair()` fsyncs after truncating (`index.ts:692-698`), so this requires the crash to land in a very narrow window or the filesystem to reorder a synced metadata update. Power loss **by itself cannot manufacture a valid older row**; something must have written at a stale cursor. Calling this "a power-loss edge case" understates a concurrency hazard the user can actually avoid.
- **REFUTED — that the strictness is the bug.** It is a deliberate, documented choice: truncating a gap that sits before a committed `turn/end` would silently delete committed conversation, so the loader refuses (`packages/session/session-persistence-jsonl/tests/jsonl.spec.ts:963-972` and its comment). Relaxing the check is the wrong fix; not producing overlapping logs is the fix.

### Is it recoverable in principle?

**CONFIRMED — yes, and cleanly, with a known loss.** The bytes are all still there; they are just two branches spliced into one file. Cutting the file after file line 5122 (= event line 5121) leaves a contiguous 0..91236 prefix, which `scanLog` accepts; if its last turn is left open, `interruptedTurnClosers` synthesizes the missing `step/end`/`turn/end` on load (`packages/session/session-persistence/src/coordinator.ts:902-904`). **What is lost:** everything written after the fork — i.e. the newer branch that starts at line 5123. The alternative (keeping the newer branch by deleting the older branch's 89909..91236 rows from the middle) preserves the newest turns instead but requires locating an exact line range, and is only worth attempting if the newest turns are the valuable ones. Either way the discarded branch remains fully readable in the backup as plain JSONL.

## Recommended next steps

### What the user does now

1. **Back up the whole session directory before touching anything.** Everything below is reversible only because of this.
2. **Try the built-in read-only export first** (Web `/export`, or the download button in the Session header). It goes through `readRaw()` and never runs the failing validator, so it is the lowest-risk way to get the conversation out. If the session will not open far enough to run it, fall through to 3.
3. **Read the conversation straight out of the backup**: decompress `session.jsonl.zstd` with the stock `zstd` CLI and read the JSONL. Everything is there — the file is damaged, not lost.
4. **If they want the session to load again**, cut the decompressed copy after file line **5122** (note: the error's "line 5122" counts event lines; the header is file line 1), recompress, and put back exactly one artifact with the original suffix.
5. **Prevent a recurrence**: do not run two harness instances against the same `~/.dsh/sessions` at the same time (two ports, two tabs against different servers, CLI + Web) — that is the mechanism that best fits these numbers.
6. **Post the details on #2257 / open an issue** — there is currently no upstream issue for this at all (finding 15), which is why nothing is being fixed.

### What the repo should change

1. **Ship a first-party recovery command.** This is the real gap: `readRaw()` already proves salvage is trivial, the discussions board has ~25 threads on it, and the vacuum is being filled by unaudited third-party tools recommending `npx` commands that do not resolve. A read-only `verify` + an explicit, backup-taking `repair --truncate-at-last-good-seq` belongs in the product.
2. **Make the diagnostic self-service.** The message should name the artifact path, say whether the anomaly is a *hole* or an *overlap* (`got < expected` is knowable at throw time), and state the file line rather than the event line — or label it `event line` so nobody `head`s off one line too many.
3. **Guard the log across processes.** An advisory lock or a durable writer identity/epoch in the header would turn a silent corruption into a loud refusal. Alternatively, verify the on-disk tail against the in-memory cursor before appending (cheap: the coordinator already has `readStoredRevision`).
4. **Reconsider `rollbackAppend` under concurrency** (`packages/session/session-persistence-jsonl/src/index.ts:680-690`): truncating back to a previously observed size can destroy another writer's committed bytes.
5. **Consolidate the ~25 duplicate discussions into one tracking issue.**
