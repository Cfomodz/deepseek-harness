# 2532 — dsh-session-sync

Peer feedback on a community plugin shared in "Show Your Plugins!". We are not maintainers; nothing here is a verdict, and nothing is posted without the owner asking.

## What the plugin is

Source: https://github.com/deepseek-ai/deepseek-harness/discussions/2532 — "dsh-session-sync: cross-device session sync with keep-both conflict resolution", opened by `PerryLink` on 2026-08-16, **no replies** at the time of reading (2026-08-17).

`dsh-session-sync` (Apache-2.0, npm `dsh-session-sync`, v0.1.1) mirrors the DSH session store into a **dedicated git worktree** and syncs that worktree to a user-supplied git remote. It ships a `/sync status|pull|push|diff|log|help` command, `sync_status` / `sync_pull` / `sync_push` model tools, three auto modes (`autoPullOnStart`, `autoPushOnTurnEnd`, `pullIntervalMinutes`), and an "append-only keep-both" three-way merge that, on divergence, keeps the local file at its path and preserves the remote side as a `*.remote-fork-<UTC14>-<device8>` file.

The single most important structural fact, which the discussion post does not state outright: **the mirror is one-directional.** Bytes flow `$DSH_HOME/sessions → <repoDir>/sessions → remote`. Nothing in the plugin writes into the session store.

## What it does well

This is careful work, and several of the choices are exactly the ones this failure class rewards.

1. **It never writes into the session store.** A repo-wide grep for filesystem writes finds exactly three: `fs.writeFile` into the mirror worktree (`lib/mirror.mjs:47`), `fs.writeFile` of a fork file inside the worktree (`lib/engine.mjs:268`), and `fs.unlink` inside the mirror root (`lib/mirror.mjs:101`). `sessionRoot` is only ever *read* (`lib/mirror.mjs:58`). That single decision is what keeps this plugin out of the `[#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359)` / `[#2257](https://github.com/deepseek-ai/deepseek-harness/discussions/2257)` / `[#1497](https://github.com/deepseek-ai/deepseek-harness/discussions/1497)` / `[#2473](https://github.com/deepseek-ai/deepseek-harness/discussions/2473)` seq-overlap family — see Finding 1.
2. **The merge is whole-file, never byte-splicing.** `classifyPath` (`lib/merge.mjs:39-63`) compares `base`/`ours`/`theirs` as whole `Buffer`s and picks one of them; the append-both verdict keeps ours intact and writes theirs to a *separate* file. There is no code path that concatenates or interleaves two logs, which is precisely the operation that manufactures a `seq` overlap.
3. **The byte-prefix test matches the harness's physical format.** `isPrefix` (`lib/merge.mjs:25-29`) asks whether the merge base is a byte prefix of each side. That is the right question: the JSONL backend appends whole encoded batches to the end of the file (`packages/session/session-persistence-jsonl/src/index.ts:650-677`), and the zstd form is concatenated standard frames, so a genuine append *is* a byte-prefix extension. Anything that isn't — a `repair()` truncation (`index.ts:691-698`), a `rollbackAppend` (`index.ts:680-690`) — falls to `diverged`, which is loud and keeps both sides. Failing safe in the right direction.
4. **The session-event gate is the correct instinct, and rarer than it should be.** `makeEventGate` (`lib/gate.mjs:125-131`) refuses to append `sync/*` unless the host knows the type. That is exactly right: `assertEventsSupported` (`packages/session/session-persistence/src/coordinator.ts:1060-1064`) *refuses to load the whole session* on an unknown, non-ignorable event type, and the reasoning is documented at `packages/core/session/src/types.ts:412-422`. A plugin that logged its own event types naively would brick sessions — and in a cross-device product it would brick them on the *other* device, which is worse. (See Finding 6 for why the gate's second arm can't currently open.)
5. **Registration hygiene matches this repo's conventions.** Auto-pull and the periodic pull are `ctx.effect` (`index.mjs:716-721`, `index.mjs:745-752`), turn-end push is `ctx.on` (`index.mjs:726`), tools go through `ctx.inject(['tools'], …)` (`index.mjs:706-710`), and the storage domain is closed from an effect (`index.mjs:483-486`). Not capturing the return of `ctx.commands.register` / `tools.register` is correct here, not sloppy: both already route through `layers.effect(this.ctx, …)` (`packages/interaction/commands/src/index.ts:245-251`, `packages/core/tools/src/index.ts:1037`).
6. **The git layer is genuinely hardened.** A verb whitelist with runtime assertions, explicit refusal of `-f`/`--force`/`--force-with-lease`/`--mirror`/`+refspec`, `checkout` allowed only with `--ours`/`--theirs`, `merge` only with `--no-commit`/`--abort`, no `commit --amend` (`lib/git.mjs:19-61`); `GIT_TERMINAL_PROMPT=0` and bounded output/deadline (`index.mjs:215-229`); `core.autocrlf false` set on the mirror repo so checkout cannot rewrite session bytes (`lib/git.mjs:160-164`); every git operation serialized per repo (`lib/git.mjs:103-107`).
7. **Honest limitations section.** The README says plainly that session bytes sit unencrypted in your remote and that a private repo is the baseline (`README.md:152`), that the `approval` channel cannot work between turns (`README.md:155`), and that `sync/*` events are skipped on rc.6 (`README.md:154`). Stating the sharp edges up front is the thing most plugin READMEs skip.
8. **A real two-device end-to-end test.** `test/engine.test.mjs:84-168` drives two engines against a real bare git remote through first push, first pull, append-both fork, diverged fork, and a rejected-push reconcile-and-retry. That is a lot more than most plugins ship.

## Findings

### Finding 1 — It cannot produce the `seq`-overlap corruption by itself (CONFIRMED)

The failure documented in [`.agents/discussions/2359.md`](2359.md) needs a second writer appending to a live session log at a stale cursor: appends are a bare `open(path, 'a')` + write + `fsync` with no lock (`packages/session/session-persistence-jsonl/src/index.ts:650-677`), the append position is in-memory per process (`packages/session/session-persistence/src/coordinator.ts:1353-1358`), and the loader refuses a log whose `seq` moves backwards inside the committed region (`packages/session/session-persistence-jsonl/src/format.ts:363-372`).

This plugin is not that second writer. It never opens a file under `sessionRoot` for writing (see "What it does well" #1), and its merge never splices two logs into one file (`lib/merge.mjs:39-63`). Running it alongside a live harness cannot, on its own, produce `corrupt session log: seq gap in committed region`. That is the headline, and it should be said first.

### Finding 2 — There is no path back into the session store, so the last mile is manual — and the manual step is the dangerous one (CONFIRMED for the code; the consequence is a reasoned inference)

Pulled bytes land in `<repoDir>/sessions/…` and stop there. A session that exists only on device B never becomes a loadable session on device A: `SessionStore`/the JSONL backend discover sessions by scanning `$DSH_HOME/sessions` (`packages/session/session-persistence-jsonl/src/index.ts:851-872`), which the plugin does not write to. `ARCHITECTURE.md:33` draws the flow with one arrow direction, and no README (EN or ZH) documents a restore step — I grepped all five for restore/恢复/还原 and found only cross-links to other plugins.

So a user who wants their session *on the other device* has to copy files from the mirror into `$DSH_HOME/sessions` by hand. That copy is exactly the act that produces the `[#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359)` failure if the target session id is live in a running harness, or if a `*.remote-fork-*` file is renamed back over a session that has since been appended to. Nothing warns them.

This is not a criticism of the design — mirroring without restoring is a defensible, deliberately conservative scope. It is a documentation gap with a sharp edge behind it: the plugin's careful "never overwrite" guarantee ends precisely where the user's `cp` begins.

### Finding 3 — The mirror's delete pass removes the *other* device's sessions from the tip, and keep-both never sees it (CONFIRMED for the code; PLAUSIBLE for the end-to-end effect, not executed)

`mirrorSessionRoot` builds `targets` from the local session root, then walks the mirror root and unlinks every regular file that is not in `targets` and does not match `FORK_NAME_RE` (`lib/mirror.mjs:93-104`). Combined with Finding 2 — device A's session root never contains device B's sessions — every push from A deletes B's session files from the mirror tree and commits that deletion (`lib/engine.mjs:93-100`).

The keep-both merge cannot catch this, because a delete-on-one-side / unchanged-on-the-other merges cleanly in git: no conflict, so `conflictedPaths()` never sees the path and `planMerge` is never consulted. With `autoPushOnTurnEnd: true` on two devices, the tip should oscillate: each device's push removes the other's sessions, each device's next push restores its own. Fork files are exempt by name, and git history retains everything (`git log --diff-filter=D`), so this is churn and a confusing tip, not destruction.

The existing suite does not cover it, and it's a near miss: at `test/engine.test.mjs:150-160`, B adopts A's `s3` during the rejected-push reconcile and the assertion runs immediately after that push. The deletion would appear on B's *next* push, which the test doesn't perform.

A test that would show it: after step 7, `await b.engine.push()` once more and assert `sessions/s3/a-new.jsonl` still exists.

### Finding 4 — A modify/delete conflict makes the whole pull fail, and the fix is already in hand (CONFIRMED for the code; not executed)

When `ours` changed and `theirs` is absent, `classifyPath` returns `diverged` with `forkTheirs: true` (`lib/merge.mjs:62`). `#resolveConflicts` then runs `checkoutStage('theirs', …)` (`lib/engine.mjs:264`) → `git checkout --theirs -- <path>` (`lib/git.mjs:334-336`), but a delete/modify conflict has no stage 3, so `#must` throws, `abortMerge()` runs, and the pull returns `ok: false`. Given Finding 3 makes deletions routine, this looks reachable rather than theoretical, and it would repeat on every pull until resolved by hand.

The bytes needed to avoid the round trip are already in memory: `#resolveConflicts` reads stage 1/2/3 blobs into `entries` at `lib/engine.mjs:246-251` and then throws the `theirs` buffer away, re-deriving it via checkout → read → checkout back. Writing the fork file straight from `entry.theirs` would drop two git invocations per conflicted path *and* make the missing-stage case fall out naturally.

### Finding 5 — `sanitizeRemote` misses the most common GitHub token form, and that string reaches the model (CONFIRMED)

`sanitizeRemote` masks the password only when **both** `url.username` and `url.password` are non-empty (`lib/sanitize.mjs:30-33`); otherwise it falls through to credential-looking *query keys* and returns the URL unchanged. A remote of the form `https://ghp_XXXXXXXXXXXXXXXX@github.com/you/sessions.git` — the shape GitHub's own PAT docs hand out, and the shape a credential helper writes — parses as username-only, so it is returned verbatim.

That value is model-visible and user-visible: `collectStatus` puts it in `remote` (`lib/status.mjs:26`), `renderStatus` prints it (`lib/render.mjs:21`), `engine.push()` returns it (`lib/engine.mjs:155`) and `renderPush` prints it (`lib/render.mjs:94`) — and `sync_status` / `sync_push` are model tools, so the token lands in the model request and in the tool-result record.

`redactText` would already catch `ghp_…` via its `TOKEN_PATTERN` (`lib/sanitize.mjs:11`), but `sanitizeRemote` never calls it. Masking userinfo unconditionally (both username and password, whenever either is present) and/or passing the result through `redactText` would close it. This looks like the highest-value single-line change in the plugin.

### Finding 6 — The event gate's `ignorable` arm cannot open on any current build (CONFIRMED against the local harness)

`probeIgnorableAppend` (`index.mjs:66-81`) appends a probe event with `{ ignorable: true }` and reads the marker back. On this checkout it must return `false`: `Session.append` constructs the envelope from `type`/`seq`/`time`/`data` plus only `surfaceOp` and `sourceEventSeqs` taken from `SurfaceIntent` (`packages/core/session/src/index.ts:604-634`). There is no envelope option for `ignorable`; the flag is accepted only on *seed* events (`packages/core/session/src/index.ts:216-244`) and consumed only on the read path (`packages/session/session-persistence/src/coordinator.ts:1060-1064`). So the `{ ignorable: true }` object passed at `lib/gate.mjs:147` is silently dropped, exactly as the plugin's own comment predicts for rc.6 — but the same is true on `master`, not just rc.6.

The gate's other arm is also closed by construction for an out-of-repo plugin: `KNOWN_SESSION_EVENT_TYPES` is generated from `SessionEventMap` declarations *in the harness repository*, and its doc says so explicitly — "Downstream (out-of-repo) plugin events are outside this list by construction; a registration surface for them is deferred until such a consumer exists" (`packages/core/session/src/known-event-types.ts:8-18`).

Net: `sync/push` / `sync/pull` / `sync/conflict` are declared in `types.d.ts` and can never currently be logged, so `README.md:154` and `ARCHITECTURE.md:60` ("turns on automatically once a host records the types") describe a switch with no reachable position today. The gate itself is right and should stay; it's the auto-enable promise that overstates. This plugin is arguably the concrete out-of-repo consumer that note is waiting for — worth saying so upstream.

### Finding 7 — Fork-name producer and guard disagree, and the `pending` device id can slip through (CONFIRMED for the code; the race is narrow and unexecuted)

`forkFileName` accepts a device segment of 1–8 chars (`lib/paths.mjs:105`), but `FORK_NAME_RE` — the pattern that exempts a file from the mirror's delete pass and lists it in `status.forks` — requires exactly 8 (`lib/constants.mjs:65`). Any fork file whose device segment is shorter is therefore *not* protected at `lib/mirror.mjs:96-103` and gets unlinked by the next mirror pass.

Reachable: the engine is constructed with `deviceId: 'pending'` (`index.mjs:553`) and only patched after the storage domain resolves (`index.mjs:560-562`), while `deviceShort` slices 8 chars of the id (`lib/engine.mjs:51`) — `'pending'` is 7. If `autoPullOnStart` fires its effect (`index.mjs:715-721`) before the domain promise settles and that pull produces forks, the fork files are named `…-pending` and lose their protection. The `'unknown'` fallback in both `lib/engine.mjs:51` and `lib/paths.mjs:105` has the same 7-char problem. Making the regex `[0-9a-z]{1,8}` (or padding the device segment to 8) restores the symmetry.

### Finding 8 — The mirror reads live files without the harness's stability loop (CONFIRMED; consequence bounded)

`mirrorSessionRoot` copies with a plain `fs.readFile` (`lib/mirror.mjs:67`) while a harness may be mid-append. The harness's own reader solves this and documents why: `readStableFile` stats, reads, re-stats, and retries while the revision changes, because "a writer appending between stat and readFile would yield a torn physical file" (`packages/session/session-persistence-jsonl/src/index.ts:284-303`).

The blast radius is small: a torn tail is tolerated on load — plaintext yields a `tornMarker` at `committedBytes` (`index.ts:326-330`) and zstd recovers complete frames plus a partial one (`index.ts:385-411`). But the mirrored copy is then a snapshot that silently loses its last events, and a later `append-both` classification of that snapshot is comparing against bytes no writer ever committed. Copying the harness's ~10-line retry loop would remove the whole question.

### Finding 9 — Cross-device restore has harness-side traps worth documenting (CONFIRMED for the harness behavior; PLAUSIBLE that users hit them)

If Finding 2's manual restore is ever documented, three harness rules should be documented with it:

- **Mixed compression poisons the whole root, not one session.** `checkRootEncoding` walks every session directory under the root and throws on the first artifact with the opposite suffix (`packages/session/session-persistence-jsonl/src/index.ts:874-889`; per-session check at `:773-788`). Two devices configured with different `compression` settings, plus one restore, and the root stops loading.
- **The same session id under two project directories is a hard error**: `duplicate JSONL session id "<id>" appears in multiple project directories` (`index.ts:789-791`).
- **Project directory names are slugified from `cwd`** (`packages/session/session-persistence-jsonl/src/format.ts:147-168`), so `/home/u/p`, `/Users/u/p`, and `C:\Users\u\p` are three different directories for the same repository. Restored sessions do not "land in the right project" across OSes.

### Finding 10 — Minor packaging and byte-fidelity notes (CONFIRMED / PLAUSIBLE)

- **CONFIRMED:** `typescript` is a runtime `dependency` (`package.json:98-101`) though it is only used by the `typecheck` scripts; it belongs in `devDependencies`. `zod` is genuinely runtime (`lib/domain.mjs`).
- **PLAUSIBLE (unverified):** the mirror repo sets `core.autocrlf false` (`lib/git.mjs:162`) but writes no `.gitattributes`. A user's global `core.attributesFile` still applies to the mirror repo and could attach text/eol/clean filters to `.jsonl`. Committing `* -text` into the mirror root would make byte fidelity independent of the user's global git config.
- **UNVERIFIED:** repo growth. With `autoPushOnTurnEnd`, every closed turn commits a new full blob for each changed session file. Appended-zstd files share a long common prefix so git's delta compression may handle it well, but I did not measure it, and a long-lived session store could make the sync repo large. Worth a number in the README either way.

先说结论：**这个插件不会自己制造 `corrupt session log: seq gap in committed region`**——我把 `641884f` 的源码读了一遍，全仓库只有三处文件写：`lib/mirror.mjs:47`（写进工作树）、`lib/engine.mjs:268`（写 fork 文件）、`lib/mirror.mjs:101`（删工作树内的文件），`sessionRoot` 只读不写（`lib/mirror.mjs:58`）。这一点很关键：讨论区里 [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359) / [#2257](https://github.com/deepseek-ai/deepseek-harness/discussions/2257) / [#1497](https://github.com/deepseek-ai/deepseek-harness/discussions/1497) / [#2473](https://github.com/deepseek-ai/deepseek-harness/discussions/2473) 那一类损坏，需要有第二个写入方拿着过期游标往活跃日志里追加（harness 侧追加是裸 `open(path,'a')`，没有跨进程锁，`packages/session/session-persistence-jsonl/src/index.ts:650-677`；游标是进程内内存态，`packages/session/session-persistence/src/coordinator.ts:1353-1358`）。你的插件不是那个写入方。

另外几处我觉得做得特别对：

- 合并是**整文件取舍**，从不拼接字节（`lib/merge.mjs:39-63`）。拼接才是制造 seq 重叠的那个动作。
- `isPrefix`（`lib/merge.mjs:25-29`）问的问题正好对上宿主的物理格式：真正的追加就是字节前缀延长，而 `repair()` 截断（`index.ts:691-698`）这类改写会落到 `diverged`，响亮保留两边。方向失败得很正确。

- git 层的动词白名单、拒绝一切强推、`core.autocrlf false`、按仓库串行（`lib/git.mjs:19-61`、`:160-164`、`:103-107`）都很扎实；README 把"字节是明文存在你自己的远端"和 approval 在轮次之间不可用这两条限制直接写出来（`README.md:152`、`:155`），这点比大多数插件强。

读的过程中攒了几条，纯属信息共享，你自己判断值不值得处理：

1. **拉下来的会话回不到会话存储**（`ARCHITECTURE.md:33` 的箭头只有一个方向；五份 README 里都没有 restore/恢复 一节）。也就是说最后一公里要用户自己 `cp` 回 `$DSH_HOME/sessions`——而那一步恰好就是 [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359) 的触发方式：往一个正在被活跃 harness 追加的会话文件上覆盖。插件本身的"绝不覆盖"保证到用户的 `cp` 为止。如果这是有意的保守设计（我觉得挺合理），也许值得在 README 里写一节"怎么在另一台设备上真正用起来"，并带一句"目标会话必须没有 harness 在跑"。（也可能我看漏了回写路径，如果有请纠正我。）
2. **镜像的删除扫描会把对端设备的会话从 tip 上删掉。** `lib/mirror.mjs:93-104` 以本地 `sessionRoot` 为准，凡是工作树里有、本地没有、又不匹配 `FORK_NAME_RE` 的文件一律 `unlink`。结合第 1 点（A 的会话根永远不会有 B 的会话），A 每次 push 都会提交一次"删掉 B 的会话"。keep-both 拦不住它：一侧删除、另一侧未变，在 git 里是干净合并，`conflictedPaths()` 根本看不到这条路径。两台都开 `autoPushOnTurnEnd` 的话，tip 会来回震荡（历史里都还在，`git log --diff-filter=D` 能找回来）。现有测试差一步就能照出来：`test/engine.test.mjs:150-160` 在 B 合并进 `s3` 之后立刻断言，如果那之后再 `await b.engine.push()` 一次，再断言 `sessions/s3/a-new.jsonl` 还在，应该就能复现。
3. **modify/delete 冲突会让整次 pull 失败。** `ours` 有改动、`theirs` 被删时分类是 `diverged` + `forkTheirs`（`lib/merge.mjs:62`），随后 `checkoutStage('theirs', …)`（`lib/engine.mjs:264`）执行 `git checkout --theirs`，但这种冲突没有 stage 3，`#must` 抛错 → `abortMerge` → `ok:false`。考虑到第 2 点会让删除变成常态，这条路径应该不难碰到。顺带一提：`theirs` 的字节其实已经在手上了——`lib/engine.mjs:246-251` 刚用 `readStageBlob('3', …)` 读进来又丢掉了。直接 `fs.writeFile(forkPath, entry.theirs)` 既省掉 checkout→读→再 checkout 回来的两次 git 调用，也顺手把"stage 3 不存在"这种情况自然带过。
4. **`sanitizeRemote` 漏了最常见的一种 GitHub token 形态**（这条我建议优先看）。`lib/sanitize.mjs:30-33` 只在 `username` 和 `password` **都**非空时才打码，所以 `https://ghp_XXXXXXXXXXXXXXXX@github.com/you/sessions.git` 这种"token 放在用户名位、没有密码"的形式会原样返回。而这个字符串是模型可见的：`lib/status.mjs:26` → `lib/render.mjs:21`，以及 `lib/engine.mjs:155` → `lib/render.mjs:94`，而 `sync_status`/`sync_push` 是模型工具。你自己的 `redactText` 里 `TOKEN_PATTERN`（`lib/sanitize.mjs:11`）本来就能抓 `ghp_`，只是 `sanitizeRemote` 没调它。无条件打码 userinfo（只要有一侧存在）或者把结果过一道 `redactText` 应该就够了。
5. **`ignorable` 那条分支目前在任何构建上都开不了。** `Session.append` 组装信封时只取 `type`/`seq`/`time`/`data` 加上 `SurfaceIntent` 的 `surfaceOp`/`sourceEventSeqs`（`packages/core/session/src/index.ts:604-634`），没有 `ignorable` 这个入口；这个标记只在 **seed** 事件上被接受（`index.ts:216-244`），只在读路径上被消费（`coordinator.ts:1060-1064`）。所以 `lib/gate.mjs:147` 传的 `{ ignorable: true }` 会被丢掉——不只是 rc.6，master 上也一样，`probeIgnorableAppend` 必然返回 false。另一条分支同样封闭：`KNOWN_SESSION_EVENT_TYPES` 由仓库内的 `SessionEventMap` 声明生成，注释里直说了"仓库外插件的事件类型按构造就不在这个集合里，注册入口等到出现这样的消费方再说"（`packages/core/session/src/known-event-types.ts:8-18`）。门本身应该保留，但 `README.md:154` / `ARCHITECTURE.md:60` 说的"宿主收录后自动打开"目前没有可达的档位。反过来看：你这个插件大概就是那条注释在等的"仓库外消费方"，值得单独开一贴说这件事。
6. 两条小的：fork 文件名的生成方允许 1–8 位设备段（`lib/paths.mjs:105`），但守卫 `FORK_NAME_RE` 要求正好 8 位（`lib/constants.mjs:65`），而引擎在存储领域就绪前的设备 id 是 `'pending'`（`index.mjs:553`、`lib/engine.mjs:51`，7 位）——如果 `autoPullOnStart`（`index.mjs:715-721`）赶在领域 promise 落定前产生了 fork，那些文件不受 `lib/mirror.mjs:96-103` 的保护，下一次镜像就会删掉。另外镜像用的是裸 `fs.readFile`（`lib/mirror.mjs:67`），而宿主自己读同一批文件时是 stat→read→再 stat 的重试循环，注释写明了原因就是"追加发生在 stat 和 readFile 之间会读到撕裂的文件"（`index.ts:284-303`）；撕裂尾巴在加载时是被容忍的（`index.ts:326-330`、`:385-411`），所以后果有限，但镜像出来的快照会静默少掉最后几条事件。

**English**

Lead conclusion: **this plugin cannot produce `corrupt session log: seq gap in committed region` on its own.** I read the source at `641884f`, and the entire repo contains exactly three filesystem writes — `lib/mirror.mjs:47` (into the worktree), `lib/engine.mjs:268` (fork file), and `lib/mirror.mjs:101` (unlink inside the worktree). `sessionRoot` is read-only (`lib/mirror.mjs:58`). That matters, because the [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359) / [#2257](https://github.com/deepseek-ai/deepseek-harness/discussions/2257) / [#1497](https://github.com/deepseek-ai/deepseek-harness/discussions/1497) / [#2473](https://github.com/deepseek-ai/deepseek-harness/discussions/2473) family needs a second writer appending to a live log at a stale cursor: harness appends are a bare `open(path,'a')` with no cross-process lock (`packages/session/session-persistence-jsonl/src/index.ts:650-677`) and the cursor is in-memory per process (`packages/session/session-persistence/src/coordinator.ts:1353-1358`). Your plugin is not that writer.

Other things I think you got right:

- The merge picks **whole files** and never splices bytes (`lib/merge.mjs:39-63`). Splicing is the operation that manufactures a seq overlap.
- `isPrefix` (`lib/merge.mjs:25-29`) asks exactly the right question for this format: a real append extends the byte prefix, while rewrites like `repair()`'s truncation (`index.ts:691-698`) fall to `diverged` and keep both sides loudly.
- The session-event gate (`lib/gate.mjs:125-131`) is the standout. The read path **refuses to load an entire session** on an unknown, non-ignorable event type (`coordinator.ts:1060-1064`, rationale at `packages/core/session/src/types.ts:412-422`) — and in a cross-device product that would fire on the *other* machine.
- The git layer is solid: verb whitelist, no force-push in any form, `core.autocrlf false` on the mirror, per-repo serialization (`lib/git.mjs:19-61`, `:160-164`, `:103-107`). And the README states the sharp edges up front — bytes are unencrypted in your own remote, `approval` can't work between turns (`README.md:152`, `:155`).

Things I noticed while reading, offered as information:

1. **Pulled sessions never reach the session store.** `ARCHITECTURE.md:33` draws one arrow direction, and none of the five READMEs documents a restore step. So the last mile is a manual `cp` into `$DSH_HOME/sessions` — and that copy is precisely the [#2359](https://github.com/deepseek-ai/deepseek-harness/discussions/2359) trigger if the target session is live in a running harness. The plugin's "never overwrite" guarantee ends where the user's `cp` begins. If the one-directional scope is deliberate (it seems reasonable), a README section on "how to actually use a synced session on the second device", with a "no harness running against that session id" warning, would carry a lot of weight. (Or I missed a write-back path — please correct me.)
2. **The mirror's delete pass removes the other device's sessions from the tip.** `lib/mirror.mjs:93-104` treats the local session root as authoritative and unlinks anything in the worktree that isn't there and isn't fork-named. Combined with (1) — A's session root never holds B's sessions — every push from A commits a deletion of B's files. Keep-both can't see it: delete-on-one-side vs unchanged merges cleanly, so `conflictedPaths()` never reports the path. With `autoPushOnTurnEnd` on two devices the tip should oscillate (history retains everything; `git log --diff-filter=D` recovers it). Your suite comes one step from showing this: `test/engine.test.mjs:150-160` asserts right after B adopts `s3`; another `await b.engine.push()` before asserting `sessions/s3/a-new.jsonl` should reproduce it.
3. **A modify/delete conflict fails the whole pull.** With `ours` changed and `theirs` deleted, `classifyPath` returns `diverged` + `forkTheirs` (`lib/merge.mjs:62`), then `checkoutStage('theirs', …)` (`lib/engine.mjs:264`) runs `git checkout --theirs`, but that conflict has no stage 3 → `#must` throws → `abortMerge` → `ok:false`. Given (2) makes deletions routine, this looks reachable. Related: you already hold the `theirs` bytes — `lib/engine.mjs:246-251` reads stage 3 via `readStageBlob` and then discards it. Writing the fork straight from `entry.theirs` would drop two git calls per conflicted path and make the missing-stage case fall out for free.
4. **`sanitizeRemote` misses the most common GitHub token form** (I'd look at this one first). `lib/sanitize.mjs:30-33` masks only when username **and** password are both non-empty, so `https://ghp_XXXXXXXXXXXXXXXX@github.com/you/sessions.git` — token as username, no password — is returned verbatim. That string is model-visible: `lib/status.mjs:26` → `lib/render.mjs:21`, and `lib/engine.mjs:155` → `lib/render.mjs:94`, with `sync_status` / `sync_push` being model tools. Your own `TOKEN_PATTERN` (`lib/sanitize.mjs:11`) already catches `ghp_`; `sanitizeRemote` just doesn't call `redactText`. Masking userinfo unconditionally whenever either half is present would close it.
5. **The `ignorable` arm of the gate can't open on any build.** `Session.append` builds the envelope from `type`/`seq`/`time`/`data` plus only `surfaceOp` / `sourceEventSeqs` from `SurfaceIntent` (`packages/core/session/src/index.ts:604-634`); there is no envelope option for `ignorable`. The flag is accepted only on *seed* events (`index.ts:216-244`) and consumed only on the read path (`coordinator.ts:1060-1064`). So the `{ ignorable: true }` at `lib/gate.mjs:147` is dropped and `probeIgnorableAppend` returns false — on master too, not just rc.6. The other arm is closed by construction: `KNOWN_SESSION_EVENT_TYPES` is generated from in-repo `SessionEventMap` declarations, and its doc says "Downstream (out-of-repo) plugin events are outside this list by construction; a registration surface for them is deferred until such a consumer exists" (`packages/core/session/src/known-event-types.ts:8-18`). Keep the gate; it's the "turns on automatically" line in `README.md:154` / `ARCHITECTURE.md:60` that currently has no reachable position. Flipping it around: your plugin looks like exactly the out-of-repo consumer that note is waiting for, which seems worth its own thread.
6. Two small ones. Fork names are produced with a 1–8 char device segment (`lib/paths.mjs:105`) but guarded by a regex requiring exactly 8 (`lib/constants.mjs:65`), and the engine's device id is `'pending'` (7 chars) until the storage domain resolves (`index.mjs:553`, `lib/engine.mjs:51`) — if `autoPullOnStart` (`index.mjs:715-721`) produces forks before that, those files lose the `lib/mirror.mjs:96-103` exemption and the next mirror pass deletes them. And the mirror copies with a plain `fs.readFile` (`lib/mirror.mjs:67`), where the harness's own reader retries under a stat→read→stat loop for exactly this reason: "a writer appending between stat and readFile would yield a torn physical file" (`index.ts:284-303`). Torn tails are tolerated on load (`index.ts:326-330`, `:385-411`), so the impact is bounded, but the mirrored snapshot silently loses its last events.

All of the above is from reading the source at `641884f` — I did not install or run the plugin, so the runtime behavior in (2) and (3) is inferred from code, not measured. Corrections welcome.
