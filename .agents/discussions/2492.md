## What the plugin is

A three-state checkpoint/rollback plugin: it records, per checkpoint, (a) the workspace file state via a git or copy snapshot provider, (b) the session event cursor (`record.seq` plus a replay boundary), and (c) a config snapshot. `/rewind <target>` restores them in a fixed order behind an approval gate; `/rewind preview` shows the impact without acting.

The load-bearing design decision, and the reason this thread is worth answering: **session rollback is non-destructive**. It does not rewind the original session's log. It seeds a *new child session*:

- `lib/session.mjs:35-38` — `replaySeedOf(events, boundary)` returns `events.slice(0, boundary + 1)`, or `[]` when there is no boundary.
- `index.mjs:1078-1087` — `replaySession()` computes that seed and returns `ctx.sessions.create(undefined, { seed, meta })` with `meta.parentSession = source.id`.
- `lib/session.mjs:19-26` — `sessionBoundaryAt()` picks the last `turn/end` at or before the cursor, so the seed always ends on a closed turn.
- README.md:239 states this in the plugin's own words: "Session rollback creates a **new child session** seeded from the checkpoint boundary; it never rewrites or truncates the original session."

## What it does well

1. **The rollback model is the right one for this log format, and it is right on purpose.** A dense-positional `seq` log cannot be rewound in place without either rewriting the file or violating the index. The plugin sidesteps the whole problem by branching instead of rewinding. `index.mjs:1044` even words the approval prompt around it: "Create a new child session seeded with events up to the checkpoint boundary; this session is untouched."

2. **The seed slice is exactly what the harness's own `fork()` does.** `lib/session.mjs:37` is `events.slice(0, boundary + 1)`; the harness's `SessionStore._forkSeed` ends with the identical `events.slice(0, boundary + 1)` at `packages/core/session/src/index.ts:1137`. Independent convergence on the first-party primitive.

3. **The comment in `lib/session.mjs:9-11` about `fork` vs. `create({seed})` is technically correct**, which is a rare thing to get right from outside the repo. It claims the `OPEN_TURN` restriction constrains `fork` only, not seed replay. Confirmed: the `OPEN_TURN` throw lives in `_forkSeed` (`packages/core/session/src/index.ts:1130-1134`), while the seed path in the `Session` constructor enforces only JSON-serializability, envelope validity, contiguity, and surface acceptance (`packages/core/session/src/index.ts:516-537`) — no turn-closure check.

4. **The `ignorable`-envelope capability probe is genuinely careful engineering.** `probeIgnorableAppend` (`index.mjs:109-131`) builds a throwaway `SessionStore` on a detached `Context`, appends a probe event with `{ ignorable: true }`, and reads the stamp back. `makeEventGate` (`lib/gate.mjs:139-145`) then refuses to append any type outside `KNOWN_SESSION_EVENT_TYPES` unless the host stamps `ignorable`. This is defending against a *different* way to make a session log unloadable than [#2473](https://github.com/deepseek-ai/deepseek-harness/discussions/2473)'s, and the author identified it correctly: `packages/core/session/src/known-event-types.ts:8-18` says the read path "refuses to interpret a log containing a type outside this set unless the event carries the envelope's `ignorable` marker". Writing `checkpoint/*` events blindly would have been an easy, plausible, and genuinely damaging mistake.

5. **Waterfall listeners all delegate.** `snapshotPassThrough` ends in `return next()` (`index.mjs:702-705`), and the `tools/pre-execute` listener returns `next()` on the non-matching branch (`index.mjs:712`). All three use `{ prepend: true }` to sit ahead of policy without occupying the decision slot (`index.mjs:706-713`) — the comment at `index.mjs:696-697` says so explicitly.

6. **Fail-closed confirmation.** Every path in `confirmRewind` that cannot reach a real answerer returns `allowed: false` (`lib/gate.mjs:69-71`, `:88-90`, `:112-114`, `:121`), including free-text answers (`lib/gate.mjs:85-87`). The `approval`-channel path pre-checks for an open turn and returns an actionable reason rather than calling `approval.request` and throwing (`lib/gate.mjs:104-111`).

7. **Optional services degrade instead of hanging the profile.** `storageDomain` is read with `ctx.get('storageDomain')` (`index.mjs:325`) — matching `packages/AGENTS.md`'s "Optional services use `ctx.get(name)`" rule — and its absence produces a rejected promise with a composition recipe in the message (`index.mjs:326-338`) rather than a pending plugin.

8. **A guard checkpoint is captured before the rewind**, and the replay notice tells the child session how to undo it (`index.mjs:1106-1108`).

## Findings (each labelled, each cited)

### F1 — CONFIRMED: this plugin's session rollback cannot produce a `seq` gap or overlap in the source session.

Three independent reasons, each verified:

- It never appends to the source at a rewound cursor. `replaySession` calls `ctx.sessions.create(undefined, { seed, meta })` (`index.mjs:1086`) with `id === undefined`, so `SessionStore.prepare` mints a fresh id (`packages/core/session/src/index.ts:865-867`). A fresh id means the persistence coordinator takes its "not tracked and NO artifact → a genuinely new session: register meta (lazy) and persist its seed once" case (`packages/session/session-persistence/src/coordinator.ts:1233-1234`) — a new artifact, not an append to the parent's.
- A malformed seed would be refused loudly at construction, not written. `packages/core/session/src/index.ts:525-527` throws ``seed event at index ${index} has seq ${snapshot.seq} (expected ${index}); seed must be contiguous from 0``. The comment above it (`:509-515`) states the intent: a bad seed "cannot construct a live log that no persistence backend could store".
- The seed the plugin supplies is contiguous from 0 by construction: `events.slice(0, boundary + 1)` over a log whose `seq` equals its array index (`Session.seq` is `this.log.length`, `packages/core/session/src/index.ts:565-567`; `append` stamps `seq: this.log.length`, `:629`).

### F2 — CONFIRMED: the plugin's own writes into the source session are ordinary forward appends.

Every plugin write to the live session goes through `maybeAppendSessionEvent` → `session.append(type, data, …)` (`lib/gate.mjs:158`), and `Session.append` stamps `seq: this.log.length` (`packages/core/session/src/index.ts:629`). There is no path in `index.mjs` that writes a caller-chosen `seq`, truncates the log, or rewrites the artifact — a grep for `sessions.create|sessions.fork|seed|\.seq|append|writeEvent|log\.` across all 71617 bytes of `index.mjs` turns up no such site. `index.mjs:494` and `:985` read `session.seq`; they never assign it.

### F3 — CONFIRMED, and worth telling the author: on this harness build the `checkpoint/*` events are silently never written, because the probe correctly returns `false`.

`Session.append` at `packages/core/session/src/index.ts:604-633` takes `(type, data, ...opts)` where `opts[0]` is a `SurfaceIntent`. It reads only `sourceEventSeqs` and `surfaceOp` from it (`:610-613`) and constructs the event from `type`/`seq`/`time`/`data` plus that surface metadata (`:627-633`). **There is no `ignorable` option on `append`.** So `session.append(type, data, { ignorable: true })` drops the key, `event.ignorable` is `undefined`, and `probeIgnorableAppend` returns `false` (`index.mjs:127`).

With the probe false, `makeEventGate` returns `{ append: false }` for every type outside `KNOWN_SESSION_EVENT_TYPES` (`lib/gate.mjs:141-143`). The plugin's four types — `checkpoint/snapshot`, `checkpoint/bound`, `checkpoint/prune`, `checkpoint/rewind` (`lib/constants.mjs:120-125`) — are not in that generated set. Consequence: **every `appendEvent(...)` call in `index.mjs` (:543, :644, :691, :1217, :1234, :1258, :1273, :1321, :1440, :1448) is a no-op on this build.** Checkpoint and rewind activity leaves no trace in the session log; it lives only in the `storageDomain` `checkpoints` table.

This is the *safe* outcome and the gate is doing precisely its job. It is worth surfacing to the author only because the behavior is invisible: a user reading session history will not see that a rewind happened. The one notice that does land is `injectReplayNotice`, which uses `'user/message'` (`index.mjs:1112`) — a known type (`packages/core/session/src/known-event-types.ts:62`) — so the child session does explain itself. That choice looks deliberate and it is the right one.

### F4 — CONFIRMED: registrations are fiber-scoped and disposal is correct, including the three sites that discard the returned disposer.

- Explicit effects: the provider registry (`index.mjs:305-319`), the settings scope watcher (`index.mjs:296-300`), the storage domain close (`index.mjs:333`), and the tool registration (`index.mjs:777`, `toolsCtx.effect(() => toolsCtx.tools.register(...))`).
- Listeners via `ctx.on` (`index.mjs:368`, `:706`, `:707`, `:708`).
- Optional services via `ctx.inject` scoped contexts (`index.mjs:286`, `:717`, `:723`, `:774`).
- The three sites that discard a `register()` return — `ctx.commands.register` (`index.mjs:754`, `:764`) and `projectionCtx.sessionProjections.register` (`index.mjs:718`) — are **not** leaks: both harness registries register the effect on the calling context's fiber themselves. `CommandService.register` returns `this.layers.effect(this.ctx, …, { label: 'commands.register()' })` (`packages/interaction/commands/src/index.ts:245-252`), and `sessionProjections.register` wraps its generator in a labelled effect (`packages/session/session-projection/src/index.ts:213-221`, label at `:220`). Discarding the handle is correct there.

### F5 — PLAUSIBLE (not verified): `probeIgnorableAppend` constructs a `SessionStore` on a `new Context()` that is never disposed.

`index.mjs:111-112` does `new SessionStore(new Context())` then `store.create()`. `SessionStore.create` registers an effect on that context (`packages/core/session/src/index.ts:836`). The context is a fresh throwaway with no persistence attached, so nothing reaches disk and it should be garbage-collectable — but I did not verify that Cordis holds no process-global reference to a bare `Context`, so I cannot call it clean. If the probe runs once per plugin apply, repeated hot reloads would repeat it. Low stakes; mentioning it only because I looked.

### F6 — CONFIRMED: the plugin relies on `events[i].seq === i` without asserting it; the harness's `fork()` asserts it.

`replaySeedOf` slices by array index using `boundary`, which is a `seq` (`lib/session.mjs:37`). That is correct under the harness's contiguity contract. The first-party `_forkSeed` performs the same slice but first checks `boundaryEvent.seq !== boundary` and throws `INVALID_BOUNDARY` (`packages/core/session/src/index.ts:1121-1127`). Not a bug — the invariant genuinely holds (`packages/core/session/src/index.ts:565-567`) — just a place where the harness keeps a belt the plugin does not.

### F7 — CONFIRMED: the plugin does not duplicate or conflict with `dsh-session-checkpoint-policy`, despite the shared word.

`packages/session/session-checkpoint-policy/README.md` describes a **durability** policy: it flushes the event-sourced session before a model adapter receives a request, before a top-level tool body may cause an external side effect, and at each `agent/pre-step` boundary. It has no user-facing restore, no snapshot, no rewind. Its "checkpoint" means "fsync barrier", not "savepoint you can return to". The two are orthogonal, and the plugin neither layers on it nor bypasses it — it never touches persistence directly.

The harness's actual first-party analogue to `/rewind` is the Web conversation view's `forkAt(seq)`, which calls `sessions.fork({ sessionId, atSeq: seq, increaseTitle: true })` and opens the child (`packages/client/ui-conversation/src/client/apply.ts:417-419`). **That is also non-destructive and also produces a child session.** So the plugin's session half overlaps the shipped fork affordance in mechanism, and adds over it: the workspace and config states, addressing by checkpoint rather than raw seq, preview, and the approval gate. That framing is probably more useful to the author than "you duplicated something".

I checked: `Session.append`'s third parameter is a `SurfaceIntent`, and the implementation reads only `sourceEventSeqs` and `surfaceOp` from it (`packages/core/session/src/index.ts:604-633`) — the `ignorable` key is dropped, so the stamp never reads back.

Net effect: `makeEventGate` stays closed (`lib/gate.mjs:141-143`), and none of `checkpoint/snapshot|bound|prune|rewind` ever reach the session log — the ~10 `appendEvent(...)` call sites in `index.mjs` are no-ops on this version.

**That is the safe outcome and exactly what the gate is for** (an unknown required type on disk makes the log unloadable next time — `packages/core/session/src/known-event-types.ts:8-18`; you pre-empted a *different* route to "history unavailable", which I think is the sharpest thing in this plugin). It's just invisible: nothing about checkpoints or rewinds shows up in session history, it all lives in the storageDomain table. Might be worth a README line, or an info log when the gate closes. Sending the rewind notice as `user/message` (`index.mjs:1112`, a known type, so it always lands) is the right call.

**Small things**, none of them important:

- `replaySeedOf` slices by array index using a `seq`, relying on `events[i].seq === i`. That invariant does hold (`packages/core/session/src/index.ts:565-567`); the host's `_forkSeed` still asserts `boundaryEvent.seq !== boundary` anyway (`:1121-1127`). Take it or leave it.
- `probeIgnorableAppend` creates a `new Context()` that is never disposed. One throwaway detached context, probably fine — I didn't verify whether Cordis retains a global reference.
- `dsh-session-checkpoint-policy` doesn't collide with you: its "checkpoint" means a durability flush barrier (before a model request, before a side-effecting tool body, at `agent/pre-step`), not a savepoint you can return to. Same word, different thing.
